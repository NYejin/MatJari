# 소셜 로그인 설계 근거

카카오·구글·네이버 소셜 로그인(V14 `social_account`, 브랜치 `feature/social-login`, 2026-10-12 구현, 병합됨)의 근거만 정리한다. 확정 규칙의 기준은 [CLAUDE.md](../../CLAUDE.md)다. 마이페이지의 소셜 계정 연결·해제(V16)는 [프로필 수정·소셜 계정 연결 설계 근거](profile-edit-design.md)에 있다. 여기서 새 결정을 만들지 않는다. 정지·차단 규칙은 [차단·신고·이용 정지 설계](block-report-design.md), 외부 요청 방어의 같은 사고방식은 [링크 자동 입력 설계](link-autofill-design.md) 참고.

사용자가 정한 것은 두 가지다: 제공자 3개, 같은 이메일의 기존 계정이 있으면 자동 연결하지 않음. 나머지(방식, 일회용 코드 등)는 구현 세션에서 정했다.

## 1. 왜 Spring oauth2-client를 안 쓰고 직접 구현했나

- 앱이 서버 세션 없는 무상태 JWT 구조라, oauth2-client의 세션 기반 인가 요청 저장·로그인 성공 처리와 맞지 않는다.
- 제공자 token/userinfo를 JDK HttpServer 스텁으로 흉내 내는 통합 테스트가 직접 구현 쪽이 쉽다.
- 엔드포인트를 코드에 고정해 임의 주소로 나가는 요청 면을 없앤다(링크 자동 입력의 고정 템플릿과 같은 사고).
- 새 라이브러리를 추가하지 않는다는 제약이 있었다.
- 대가: OAuth 흐름의 검증을 직접 책임져야 한다(아래 5절 검증 지적이 그 비용).

## 2. 흐름과 설계 요소

백엔드가 처리하는 Authorization Code 방식(구글·카카오는 PKCE S256 추가, 네이버는 PKCE 미지원이라 state 쿠키 검증으로 CSRF 방어). 단계 상세는 구현 코드와 구현 세션 설계 기록에 있고, 근거만 적는다.

- **서명된 HttpOnly 쿠키에 state 보관**: 서버 세션이 없으므로 state와 PKCE verifier를 HMAC 서명한 쿠키(Path를 소셜 경로로 한정, SameSite=Lax, 10분)에 둔다. 콜백에서 서명·만료·제공자·state를 상수 시간으로 검증하고, 검증 전에는 코드 교환을 시도하지 않는다. state는 1회용으로 쓰고 콜백이 끝나면 쿠키를 지운다.
- **일회용 로그인 코드**: 콜백이 JWT를 URL에 싣지 않고, 32바이트 랜덤 코드(서버 메모리, 60초, 1회용)를 발급해 프런트가 교환 API로 토큰을 받게 한다. 토큰이 주소·히스토리·서버 로그에 남는 것을 피하려는 것이다. 교환 때 정지를 다시 검사한다.
- **URL 프래그먼트(`#code=`)로 전달**: 프래그먼트는 서버로 전송되지 않아 접근 로그와 Referer에 남지 않는다. 프런트는 읽자마자 주소에서 지운다.
- **리다이렉트 목적지는 설정 고정**: 요청 파라미터로 받지 않아 오픈 리다이렉트가 없다. 실패는 로그인 화면으로 `socialError` 코드를 붙여 보낸다.
- **메모리 저장의 대가**: 코드 저장소·사용된 state·속도 제한이 서버 메모리라 서버 한 대 기준이다. 재시작하면 60초짜리 코드가 사라지는 것은 허용했다.

## 3. 자동 연결 안 함 근거

제공자가 준 검증된 이메일이 이미 `users`에 있으면 가입을 막고 "기존 방식으로 로그인" 안내만 한다(`EMAIL_EXISTS`). 이는 사용자 결정이다. 근거로 확인된 것은 다음과 같다.

- 일반 가입에는 이메일 인증이 없어, 이메일 일치만으로 합치면 타인이 선점한 계정에 소셜 로그인이 붙거나 반대로 계정이 탈취될 수 있다.
- 합치려면 기존 계정의 소유 증명(비밀번호 로그인 후 연결)이 필요하다. 2026-10-13에 마이페이지 연결이 추가됐지만 이는 로그인한 본인의 명시적 연결이고, 같은 이메일로 자동 합치는 것은 여전히 하지 않는다.
- 부작용(기존 한계): 타인이 남의 이메일로 먼저 일반 가입해 두면 그 이메일 주인의 소셜 가입이 `EMAIL_EXISTS`로 막힌다.

## 4. 자리표시 이메일과 계정 모델

- `users.email`과 비밀번호는 NOT NULL을 유지하고 스키마를 바꾸지 않았다. 이메일이 없거나 미검증이면 `{provider}.{sha256 앞 16자 hex}@social.matjari.invalid` 형태의 자리표시 이메일을 쓴다. `.invalid`는 예약된 도메인이라 실제 메일이 아니며, 일반 가입은 `.invalid` 이메일을 거부한다. 제공자 식별자를 직접 쓰지 않고 해시를 쓴 것은 식별자가 이메일 형태에 안전하지 않을 수 있어서다.
- 비밀번호는 무작위 32바이트를 BCrypt로 해시해 저장한다. 아무도 모르는 값이라 소셜 전용 계정은 비밀번호 로그인이 불가능하다.
- `social_account`는 (provider, provider_user_id) 유니크로 소셜 계정과 사용자를 잇고, 이메일·프로필은 저장하지 않는다(최소 수집). 사용자당 제공자 1개는 V16에서 (user_id, provider) 유니크로 보장한다. FK 인덱스는 단일 컬럼이라 [잠금·인덱스 규약](../gotchas/lock-order-and-index-pitfalls.md)과 충돌하지 않는다.
- 이메일이 있어도 카카오는 `is_email_valid`와 `is_email_verified`가 둘 다 true일 때만, 구글은 `email_verified`일 때만 사용한다.

## 5. 검증에서 나온 지적과 수정

Fable 검증 결과는 높음 없음, 중간 4건이었고 모두 수정했다(낮음은 일부만 수정).

1. 콜백에서 미분류 예외가 나면 JSON 오류가 그대로 노출 -> 로그인 화면 302와 쿠키 삭제로 처리.
2. state 쿠키를 재사용할 수 있고 콜백 호출이 무제한 -> state 1회용 처리와 콜백 IP 속도 제한(authorize·exchange·callback 버킷 분리, IP당 분당 30).
3. 프런트가 `socialError`로 객체를 조회할 때 `__proto__` 같은 값에서 크래시 -> [프런트 함정 페이지](../gotchas/frontend-react-pitfalls.md) 2절.
4. 프록시 뒤에서 모든 사용자가 같은 IP로 보여 속도 제한을 공유 -> `getRemoteAddr()`만 신뢰하도록 하고, 프록시 뒤 배포 때 `server.forward-headers-strategy` 설정이 필요함을 한계로 명시.

그 밖에 응답 `Cache-Control: no-store`, 로그에 secret·토큰·code·이메일을 남기지 않는 것을 확인했다.

## 6. 택하지 않은 대안

- **토큰을 콜백 URL 쿼리에 직접 실음**: 로그·히스토리·Referer에 남는다.
- **같은 이메일 자동 연결**: 3절.
- **users에 소셜 컬럼 추가 또는 비밀번호 NULL 허용**: 기존 인증 경로·스키마 변경 위험을 피해 별도 테이블과 무작위 비밀번호를 택했다.
- **세션 기반 Spring oauth2-client**: 1절.

## 7. 알려진 한계

- 로그인 코드 저장소·속도 제한·사용된 state가 메모리(서버 한 대 기준). 다중 인스턴스에서는 별도 저장소가 필요하다.
- 프록시 뒤 배포 때 forward-headers 설정이 필요하다.
- `__Host-` 쿠키 접두를 쓰지 않았다(Path를 소셜 경로로 한정한 설계 때문).
- 네이버 이메일은 검증 여부를 알 수 없어 쓰지 않는다(2026-10-13 결정): 네이버로 가입하면 항상 자리표시 이메일이고 `EMAIL_EXISTS` 판정도 하지 않는다. 공식 문서에서 이메일 소유 확인을 확인하지 못했다(조사 신뢰도 낮음). 실제 키 응답으로 확인하면 되돌릴 수 있다.
- 네이버 client_secret 필수 여부를 시작 때 검증하지 않아, 누락되면 런타임에 `PROVIDER_ERROR`가 난다.
- 본문 전송이 멈추는 경우의 워치독 테스트가 없다.
- 기존 계정에 소셜을 붙이는 연결은 마이페이지(V16)에서 본인이 명시적으로 할 때만 가능하다([프로필 설계](profile-edit-design.md)). 자동 연결은 없다.
- **실제 카카오·구글·네이버 키로는 검증하지 못했다.** 카카오 PKCE와 `is_email_verified`, 네이버 client_secret 필수 여부 등은 스텁 기준 가정이며 실연동 때 확인이 필요하다. 그래서 confidence는 medium이다.
- 테스트(스텁 제공자 기반 백엔드 테스트, MySQL IT, Playwright 스텁 시나리오)는 구현 세션 기록이며 이 위키에서 재실행하지 않았다.
