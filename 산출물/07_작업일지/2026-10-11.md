## 교환 수락 → 교환 완료 구현 (브랜치 `feature/exchange-complete`, 커밋 `52cfb5a`, 08:46, 병합 전)

### 설계 확인에서 사용자가 정한 결정
- 후보 카드 '예약 중' 뱃지는 **하지 않는다(폐기)**. 후보 목록은 예약으로 잠긴 티켓을 지금처럼 뺀다(후보 조회·422 `TICKET_LOCKED` 변경 없음). 예약 중 정보는 예약한 두 사람의 내 매칭 카드에서만 보이고, 예약 전부터 같은 자리로 채팅 중이던 다른 사용자의 카드에는 "(다른 사용자와 예약 중인 좌석)" 문구만 띄운다.
- 교환 이력 조회 API와 마이페이지 '교환 이력' 화면은 **다음 브랜치로 미룬다**(`exchange_history` 테이블은 이번에 채워진다).
- '교환 수락'에 확인 단계를 둔다.
- 교환 완료 시 기존 티켓의 요청은 CLOSED, 다른 채팅은 자동 취소하지 않고 비활성 + 안내(Q-15, 이전 확정).

### 구현 사실
- **V9 `V9__exchange_complete_history.sql`**: `ck_ticket_status`를 ACTIVE/INACTIVE/EXCHANGED 허용으로 확장하고 append-only 테이블 `exchange_history`를 추가했다(old/new ticket 각각 UNIQUE, match/user/performance 단일 컬럼 KEY, FK 5개, CHECK old<>new). 이제 DB는 V1~V9, 11개 테이블이며 다음 마이그레이션은 V10부터다.
- **API** `POST /api/exchange/matches/{id}/complete`(버튼 '교환 수락'): CHATTING이면 409 `MATCH_STATE_CONFLICT`, CANCELED·COMPLETED도 409, RESERVED에서 내가 이미 수락했으면 멱등 200. 첫 수락은 `*_completed_at`만 기록하고, 두 번째 수락이 한 트랜잭션으로 완료한다: 잠금(티켓 id↑, 요청 id↑, 매칭) → 기존 두 티켓 EXCHANGED + flush → 새 티켓 2개 INSERT → `exchange_history` 2행 → 기존 두 요청 CLOSED(`status=OPEN` 조건) → 예약 잠금 삭제 → 매칭 COMPLETED. 다른 CHATTING 매칭은 취소하지 않는다. 마감 검사와 활성 20개 상한 검사는 하지 않는다.
- **flush**: Hibernate는 flush 때 INSERT를 UPDATE보다 먼저 실행하므로, 기존 티켓 UPDATE 직후 flush로 순서를 강제한다(`uk_ticket_active_seat` 충돌 방지). 위키: `wiki/gotchas/lock-order-and-index-pitfalls.md` 7절.
- **오류 `TICKET_EXCHANGED`(409)**: 예약 시 어느 티켓이든 EXCHANGED면 일반 검사보다 먼저, 티켓 내리기에서 EXCHANGED면 반환한다(INACTIVE는 기존대로 멱등 204). 교환으로 받은 새 티켓은 일반 ACTIVE 티켓이다.
- **매칭 응답 필드 4개 추가**: `myTicketExchanged`, `counterpartTicketExchanged`, `myTicketReservedElsewhere`, `counterpartTicketReservedElsewhere`. `myAccepted`/`counterpartAccepted`는 실제 값이 됐다. COMPLETED 응답의 좌석·티켓 id는 교환 전 자리다.
- **내 매칭 화면**: 예약 중 카드에 '교환 수락'(2단계 확인)·'예약 취소', 수락 상태 문구, 교환된 좌석이면 예약하기 비활성 + "이미 교환된 좌석이에요"(양쪽, 거절·채팅 종료는 가능), COMPLETED 카드에 "교환 전 내 자리 → 받은 자리"와 내 티켓 링크.

## 알림 3종 구현 (브랜치 `feature/notifications`, `feature/exchange-complete` 위에 쌓임, 병합 전)

### 사용자 결정
- 닫힌 매칭(CANCELED/COMPLETED)의 알림도 안 읽은 개수·목록에서 제외하지 않는다(회색 '종료된 매칭' 라벨만). 알림이 사라지는 유일한 경로는 '읽은 알림 삭제'.
- 헤더 벨 아이콘을 누르면 바로 아래 말풍선(최신 5건, '모두 읽음', '알림 전체 보기')이 뜨고, `/notifications` 페이지(더 보기 페이징, 모두 읽음, 읽은 알림 삭제 2단계 확인)로 이동한다.
- 실시간(STOMP)은 다음 브랜치 `feature/notifications-realtime`. 이번에는 화면이 보일 때만 30초 폴링(focus·visibilitychange·경로 이동 시 즉시 재조회).

### 구현 사실
- **V10 `notification`**: id, user_id(수신자), type, match_id, dedup_key(NULL 허용), read_at(NULL=안 읽음), created_at, 생성 컬럼 `unread_user_id`(FK 아님). `uk_notification_dedup(dedup_key)`, 단일 컬럼 KEY(user/match/unread), FK 2개(동작 없음), CHECK 2개(type 3종, match_id NOT NULL). 재실행 가능한 프로시저 패턴. 이제 DB는 V1~V10, 12개 테이블, 다음 마이그레이션은 V11부터.
- **알림 3종**: `PROPOSAL_RECEIVED`(수신자=제안받는 쪽, dedup_key `PROPOSAL_RECEIVED:{matchId}`), `MATCH_RESERVED`·`RESERVATION_CANCELED`(수신자=호출자 반대편, dedup_key NULL, 예약↔취소 반복마다 매번 1건). 요구사항 가안의 `(user_id, type, match_id)` 유니크는 재예약 시 예약이 롤백되므로 폐기. 거절·채팅 종료·7일 경과·교환 완료 알림은 이번에 없음.
- **생성**: `ExchangeMatchService` propose/reserve/unreserve 트랜잭션 맨 끝에서 `NotificationService.notify`(MANDATORY, saveAndFlush). 상태가 실제로 바뀐 경우에만 생성. 잠금 순서는 티켓 id↑ → 요청 id↑ → 매칭 → users S → notification.
- **API**: `GET /api/notifications`(page·size·unreadOnly), `GET /api/notifications/unread-count`(`total`, `byType`), `POST /{id}/read`(204 멱등), `POST /read-all?type=`, `DELETE /api/notifications/read`(`{deleted:n}`, 읽은 것만). 남의 알림은 404. 읽음·삭제는 잠금 없는 SELECT 후 500개씩 IN 벌크(범위 UPDATE/DELETE 금지).
- **화면**: 알림 클릭 시 읽음 처리 후 `/exchange/matches?role=RECEIVED&matchId=N`(새 제안) 또는 `/exchange/matches?matchId=N`로 이동하고 MatchesPage가 URL 쿼리로 탭 선택·카드 스크롤·강조. `Header.tsx`는 벨 추가로 md 경계 넘침을 막으려 이름 최대 폭을 `md:max-w-[168px]`에서 `md:max-w-[104px]`로 줄였다(계산상 확인, 브라우저 실측 미실시).
- 근거·함정은 위키 `wiki/decisions/notification-design.md`, `wiki/gotchas/lock-order-and-index-pitfalls.md` 8~9절.

## 채팅 구현 (브랜치 `feature/chat`, `feature/notifications` 병합 후 `2954b72` 위에 쌓임, 병합 전)

커밋: `9f56d59`(화면), `48d5e17`(V11 스키마·저장소), `6f566f7`(전송·조회·읽음 REST), `3bb70b5`(STOMP 인증·푸시), `8b662e5`(프론트 리뷰 반영), `fc20c82`(백엔드 리뷰 반영).

### 사용자 결정
- 보내기는 REST POST, 받기는 STOMP 사용자 큐(`/user/queue/chat`)만 쓴다. 클라이언트 STOMP SEND는 전부 거부한다.
- 읽음은 마지막 읽은 메시지 포인터다. 매칭 카드에 안 읽은 개수 뱃지, 내가 보낸 마지막 메시지 아래에 상대가 읽었으면 '읽음'을 표시한다.
- 시스템 메시지는 저장하지 않고 채팅 화면 상단 상태 배너로 보여준다.
- CANCELED·COMPLETED 매칭은 둘 다 읽기 전용이다(참여자 열람 허용, 쓰기 409 `MATCH_STATE_CONFLICT`). CHATTING·RESERVED는 읽기·쓰기 허용(교환된 좌석·다른 예약 매칭 포함).
- 문서 근거로 확정한 항목: 1000자(코드 포인트), 무기한 보관·삭제/수정 불가, 텍스트만(이미지·첨부 없음), 연결은 채팅 화면에 있는 동안만, 새 메시지 알림 행 없음, 헤더 메시지 아이콘 없음, 새 메시지는 `exchange_match.updated_at` 불변, 차단은 이번 범위 밖.

### 구현 사실
- **V11 `V11__chat_message.sql`**: `chat_message`(append-only; match_id, sender_id, content VARCHAR(1000), client_message_id, created_at; `uk_chat_message_client (client_message_id, sender_id)`, FK 2개, CHECK 2개)와 `chat_read_state`(PK (match_id, user_id), `last_read_message_id` 단조 증가·FK 아님, FK 2개). 재실행 가능한 프로시저 패턴. 이제 DB는 V1~V11, 14개 테이블, 다음 마이그레이션은 V12부터(차단 `user_block`은 V12).
- **REST**(참여자만, 비참여자·없는 매칭 404): `POST /api/exchange/matches/{id}/messages`(201, 같은 `clientMessageId` 재전송 200, 다른 매칭에서 쓴 id는 409 `CLIENT_MESSAGE_ID_REUSED`, 종료 409, 속도 제한 429 `CHAT_RATE_LIMITED`: 사용자별 슬라이딩 윈도 5초 5건·60초 60건), `GET .../messages?before=&size=30` / `?after=&size=100`, `PUT .../messages/read`(204, 올라갔을 때만 상대에게 READ 푸시). 매칭 응답에 `unreadChatCount` 추가.
- **전송 트랜잭션**: 매칭 행 `FOR UPDATE`를 첫 쿼리로 잡고(UPDATE 안 함) 멱등 조회, 종료 확인, 속도 제한, INSERT 후 커밋 뒤 전파한다. 읽음 포인터 갱신은 호출자 트랜잭션 밖(autocommit)에서 한다(트랜잭션 안에서는 갭 잠금 교착이 재현됨). 메시지 조회는 `FORCE INDEX (idx_chat_message_match)`. 근거는 위키 `wiki/gotchas/lock-order-and-index-pitfalls.md` 10절.
- **STOMP**: `/ws`(SockJS 없음), 커스텀 `StompAuthChannelInterceptor`(CONNECT는 Authorization 네이티브 헤더만), SUBSCRIBE는 `/user/queue/chat` 정확 일치만·세션당 1개, 사용자당 연결 5개, 만료 세션은 스위퍼가 1008로 닫음, Origin 허용 목록은 설정 `seatswap.websocket.allowed-origins`(`*` 포함 시 시작 거부). 확인한 사실은 위키 `wiki/research/stomp-jwt-auth.md` '구현 후 확인 결과'.
- **프론트**: `/exchange/matches/:matchId/chat`, `@stomp/stompjs`, 지수 백오프 재연결과 `after` 커서로 빈 구간 채우기, IME 조합 중 전송 금지, 코드 포인트 카운터, 상단 상태 배너, 종료된 매칭은 입력 비활성, 매칭 카드에 '채팅' 링크·안 읽은 뱃지. Header·public·480px 레이아웃은 수정하지 않았다.

### 테스트
- 백엔드 기본 595건 통과(skip 140 = MySQL IT, 실패 0). 임시 MySQL IT 포함 612건 통과(전송·예약 토글·교환 완료·티켓 등록·알림 읽음 혼합 스트레스 교착 0, 동시 전송 160건 누락 0, STOMP 통합 10건).
- 프론트 tsc·build 통과. 브라우저 점검은 하지 않았고, 프론트 테스트 러너는 없다.

### 코드 리뷰·검증 결과
- Opus 리뷰: 높음 없음, 중간 3건(재연결 백오프, 포커스 탈취, 구독 무제한)과 낮음 8건을 수정했다(`8b662e5`, `fc20c82`).
- Fable 최종 검증: 높음·중간 없음(구독 제한 확인), 낮음은 반영했다.

### 알려진 한계
- 모바일 이중 스크롤은 완전히 해소됐다고 보장하지 못한다(AppLayout 높이 규칙).
- 미인증 소켓이 최대 약 40초 유지될 수 있다(운영 프록시 연결 한도로 흡수 예정).
- 토큰 만료·사용자 변경 후 최대 30초 푸시가 유지된다. 차단·제재 구현 시 해당 사용자 세션 강제 종료 훅이 필요하다.
- 응답·푸시에 상대 `senderId`(users.id)가 노출된다. 차단·신고 브랜치에서 `mine`으로 대체할지 검토한다.
- 속도 제한·연결 제한은 단일 인스턴스 메모리다.
- 하트비트 미응답 종료와 16KB 초과 프레임 거부는 확인하지 못했다.

## 실시간 알림 푸시 (브랜치 `feature/notifications-realtime`, `feature/chat` 병합(PR #43, `0f1719b`) 위에 쌓임, 병합 전)

커밋: `45def5e`(백엔드 푸시·STOMP 구독 규칙), `386bede`(프론트 앱 공용 연결·벨 즉시 갱신·폴링 완화).

### 결정
- 알림 푸시는 **신호만** 보낸다. 알림 문구·상대 닉네임·좌석은 싣지 않고, 화면이 신호를 받으면 REST로 다시 읽는다.
- 푸시는 **커밋 뒤**에만 보낸다. 롤백이면 보내지 않고, 전파가 실패해도 저장에는 영향이 없다(폴링이 보완).
- 연결 범위: 로그인한 앱 전체가 탭당 연결 1개를 공유한다. 채팅 화면에서만 연결하던 이전 규칙을 이 브랜치에서 바꿨다.
- 구독 목적지는 `/user/queue/chat`·`/user/queue/notifications` 두 개이고, 목적지당 구독 1개다. 같은 목적지 중복 구독은 거부하고 세션을 1008로 닫는다.
- 새 채팅 메시지는 여전히 알림 행을 만들지 않고 헤더 메시지 아이콘도 없다(채팅 푸시 규칙 불변).
- 토스트는 만들지 않았다.

### 구현 사실
- 백엔드: `NotificationPushPublisher`(인터페이스)·`NotificationPushPublisherImpl`(`convertAndSendToUser`). `NotificationService.notify`가 INSERT 뒤 `afterCommit`에 등록한다. 요구사항 계획의 `@TransactionalEventListener(AFTER_COMMIT)` 대신 `TransactionSynchronization`을 썼다. `StompAuthChannelInterceptor`는 구독 허용 목적지를 두 개로 넓히고 목적지당 중복·이미 쓰인 구독 id 재사용·변형 목적지를 거부한다. DB 변경 없음(V12 아님).
- 프론트: `api/realtimeHub.ts`가 앱 공용 연결을 참조 카운트로 관리한다. 벨 훅 `useUnreadNotifications`와 채팅 훅 `useChatSocket`이 각자 참조를 잡고, 마지막 참조가 풀리면 닫는다. 토큰 재발급 시 재연결, 지수 백오프 1~30초. 연결된 상태에서 채팅 화면이 열리면 구독 직후 `onConnected`가 한 번 불려 빈 구간을 채운다.
- 화면: 신호를 받으면 벨 개수를 즉시 다시 읽고, 말풍선이 열려 있으면 목록을 조용히 다시 읽는다. `/notifications`는 목록을 바꾸지 않고 "새 알림이 있어요. 눌러서 불러오기" 버튼(`role="status"`)만 띄운다.
- 폴링: 연결 중에는 5분마다 안전 확인만 하고, 끊기면 화면이 보일 때 30초 폴링과 focus·visibilitychange·경로 이동·읽음/삭제 직후 즉시 재조회로 돌아간다. (재)연결 직후에도 개수를 즉시 다시 읽는다.

### 테스트
- 백엔드 기본 + 임시 MySQL IT 포함 617건 통과(실패 0, skip 0). 새 테스트는 `NotificationServicePushTest`(커밋 뒤 1회, 롤백 시 미전송, 전파 실패 삼킴), `StompAuthChannelInterceptorTest`(알림 큐 구독, 두 큐 동시 구독, 목적지당 중복·변형 거부), `StompChatMysqlIT`(제안받은 사용자의 모든 탭만 수신, 제안한 사람·제3자 미수신)이다.
- 프론트 `tsc`·`build` 통과. ESLint 설정과 프론트 테스트 러너는 없다.

### 알려진 한계
- 브라우저와 실제 `@stomp/stompjs` 수동 점검은 하지 않았다(헤더 폭, 벨 말풍선, 알림 흐름 포함).
- 다른 탭에서 읽음 처리한 결과는 다른 탭에 푸시하지 않는다(focus·visibilitychange·5분 확인으로 보정).
- 토큰 만료 뒤 최대 30초 푸시가 계속될 수 있고, 미인증 소켓은 최대 약 40초 유지될 수 있다. 연결·속도 제한은 단일 인스턴스 메모리다.
- 토스트 미구현. 차단·제재 구현 시 해당 사용자 세션 강제 종료 훅이 필요하다(채팅 한계와 같음).
