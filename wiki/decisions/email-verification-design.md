# 가입 이메일 인증번호 설계 근거

일반 회원가입 전에 이메일로 6자리 인증번호를 보내 이메일 소유를 확인하는 기능(V19 `email_verification`, 브랜치 `feature/email-verification`, 2026-10-13 구현)의 근거를 정리한다. 확정 규칙의 기준은 [CLAUDE.md](../../CLAUDE.md)의 '가입 이메일 인증번호' 절이다.

사용자가 정한 것은 "일반 가입도 소셜 로그인처럼 인증이 필요하니 메일로 인증번호를 보내는 절차를 추가한다"는 방향이다. 코드 방식, 저장 구조, 제한 수치, 발송 수단은 구현 세션에서 정했다.

## 1. 왜 필요한가

- 인증 없이 가입하면 남의 이메일로 계정을 미리 만들 수 있다. 소셜 가입은 검증된 이메일이 이미 `users`에 있으면 `EMAIL_EXISTS`로 막으므로([social-login-design.md](social-login-design.md)), 선점 가입이 그 사람의 소셜 가입을 막는 수단이 된다. 네이버 이메일을 쓰지 않기로 한 이유와 같은 종류의 문제다.
- 오타·가짜 이메일 계정이 쌓이고, 나중에 비밀번호 찾기를 붙일 때 이메일이 검증돼 있지 않으면 쓸 수 없다.

## 2. 선택한 구조: 가입 전에 인증, 가입 요청에 코드 동봉

흐름은 '인증번호 받기' → 메일의 6자리 코드 → 가입 요청의 `emailCode`다. 별도 '확인' API와 검증 토큰(서명된 통과 증명)은 만들지 않았다. 코드를 가입 요청에서 한 번에 확인하고 소비하므로 상태가 줄고, 검증 통과 증명을 위조하거나 재사용하는 경로가 없다.

저장은 `email_verification` 테이블 하나다. PK가 `email`이라 이메일당 행이 1개이며 다시 보내면 같은 행을 덮어쓴다. 평문 코드는 저장하지 않고 HMAC-SHA256(키는 환경변수, 입력은 이메일+코드)만 둔다. 6자리 숫자는 해시만으로도 DB 접근자가 전수 대입으로 풀 수 있으므로 키 있는 HMAC을 썼다.

`users.email_verified` 컬럼은 추가하지 않았다. 인증을 통과한 이메일로만 계정이 만들어지므로 앞으로의 새 계정은 모두 검증된 이메일이고, 기존 계정에 소급 인증하는 것은 범위 밖이다.

## 3. 시도 횟수와 롤백 (핵심 함정)

가입 서비스 트랜잭션 안에서 코드를 확인하므로 틀린 시도를 그 트랜잭션에서 올리면, 틀려서 예외가 나는 순간 롤백돼 횟수가 올라가지 않는다. 그러면 무제한으로 추측할 수 있다. 그래서 순서를 이렇게 정했다.

1. 다른 입력 검증과 이메일 중복 확인을 모두 끝낸다(다른 오류로 시도 횟수를 쓰지 않게, 코드 확인은 가입 서비스의 마지막 검증 단계).
2. `REQUIRES_NEW` 트랜잭션에서 `attempts = attempts + 1`을 먼저 올린다(`WHERE expires_at > now AND attempts < 5`로 원자적, 0행이면 만료·횟수 초과). 이 증가는 가입이 롤백돼도 남는다.
3. 같은 가입 트랜잭션에서 `DELETE … WHERE email=? AND code_hash=? AND expires_at > now`로 소비한다. 0행이면 불일치. 가입이 이후 단계(저장 실패 등)에서 롤백되면 행이 되살아난다.

'먼저 올리고 나중에 판정'이라 병렬로 여러 추측을 보내도 횟수 상한이 지켜진다. 소비를 `DELETE`의 행 수로 판정하므로 같은 코드를 동시에 두 요청이 쓰려 해도 하나만 성공한다(1회용). 처음에 `FOR UPDATE`로 읽는 안은 `REQUIRES_NEW`가 같은 행을 기다려 자기 대기 교착이 되므로 쓰지 않았다.

## 4. 발송 제한

- 재발송 대기 60초(DB의 `sent_at` 기준, 429 `EMAIL_CODE_COOLDOWN`).
- 10분 창에서 IP당 10회·이메일당 5회, 시간당 전체 200회(429 `EMAIL_CODE_RATE_LIMITED`). 전체 상한은 메일 폭탄과 발송 서비스의 일일 한도를 지키기 위한 것이다. 메모리 슬라이딩 윈도라 단일 인스턴스 기준이다.
- 대기 판정을 속도 제한 횟수보다 먼저 한다(대기 중 요청이 한도를 갉아먹지 않게).
- 메일 발송이 실패하면 행을 지워 바로 다시 요청할 수 있게 하고 503 `EMAIL_SEND_FAILED`를 준다.

## 5. 발송 수단과 운영 안전장치

발송은 `EmailSender` 인터페이스 뒤에 두고 설정 `seatswap.mail.mode`로 고른다. `log`(기본)는 메일 내용(코드 포함)을 로그에 찍는 개발용이고 `smtp`는 Spring `JavaMailSender`로 실제 보낸다. 운영에서 log 모드로 뜨면 코드가 로그에 남으므로, 백엔드 주소(`seatswap.social.backend-base-url`)가 루프백이 아닌데 log 모드면 기동을 거부한다(인증 자체를 끄는 환경변수가 탈출구다). 소셜 설정의 운영 판정과 같은 기준을 썼다.

SMTP 공급자는 정하지 않았다. 시연용은 Gmail SMTP(앱 비밀번호), 운영은 SES·Resend 등을 쓰고 모두 환경변수로만 바꾼다.

## 6. 택하지 않은 대안

- **가입 후 인증(계정 먼저 생성, 미인증 상태)**: 미인증 가짜 계정이 DB에 쌓이고 `EMAIL_EXISTS` 선점 문제가 그대로라 택하지 않았다.
- **메일 링크 방식**: 프런트 라우트·토큰 구조가 더 필요하고, 코드 입력은 한 화면에서 끝난다.
- **검증 통과 토큰 발급**: 별도 API·서명·만료·재사용 방지가 더 필요해 가입 요청에 코드를 동봉하는 쪽이 단순하다고 판단했다.
- **Redis·메모리 저장**: 서버 재시작에 약하고 DB가 이미 있다. 대신 만료 행 정리는 발송 때 하는 가벼운 방식으로 했다.

## 7. 검증

- 실제 MySQL 통합 테스트 `EmailVerificationMysqlTest` 8건: 발송→가입, 해시만 저장·1회용, 코드 없음·형식 오류·다른 이메일의 코드, 틀린 시도 5회 뒤 맞는 코드도 거부하고 새 코드로 복구, 만료, 재발송 대기 429와 가입된 이메일 400, 발송 실패 503과 즉시 재시도, 검증 순서(닉네임 오류는 시도 횟수 미사용), 슬라이딩 윈도.
- 로컬 jar(8081)와 vite(5174)로 Playwright 점검: 인증번호 없이 제출→안내, 받기→다시 받기 대기 표시, 틀린 코드→오류, 맞는 코드→가입·자동 로그인, 가입된 이메일 오류, 이메일을 바꾸면 인증번호 칸 숨김, 즉시 재요청 API 429.

## 8. 알려진 한계

1. 실제 SMTP로는 미검증이다(log 모드와 목 발송기로만 점검). Gmail SMTP는 일일 한도와 스팸함 분류 문제가 있어 시연용이고, 운영은 도메인 인증(SPF·DKIM)이 있는 발송 서비스가 필요하다.
2. 속도 제한은 단일 인스턴스 메모리다. IP 키는 `getRemoteAddr()`라 프록시 뒤에서는 프록시 주소로 합쳐진다(소셜 제한과 같은 한계).
3. 만료·소비되지 않은 행은 다음 발송 때만 정리돼, 발송이 없으면 행이 남는다(이메일당 1행이라 양은 작다).
4. 이메일 변경과 비밀번호 찾기는 없다(이 기능이 그 기반이다).
5. 가입 동의 기록이 없다는 기존 한계는 그대로다.
6. 이메일이 이미 가입돼 있는지 인증번호 요청 응답으로 알 수 있다(가입 화면의 중복 안내와 같은 정보이며, 이메일 열거는 속도 제한으로만 완화한다).
