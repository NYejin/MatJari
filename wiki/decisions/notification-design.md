# 알림 3종 설계 근거 (동기 INSERT 선택)

> 갱신(2026-10-13): V15에서 알림 유형이 6종으로 늘었고(`RESERVATION_PROPOSED`·`RESERVATION_REJECTED`·`CHAT_MESSAGE`), `MATCH_RESERVED`는 '상대가 예약을 수락'으로 의미가 바뀌었으며, 채팅·예약 제안 알림은 (수신자, 매칭)당 1행을 재사용한다. 아래 3종 기준 서술(새 제안만 dedup_key, 예약 계열 NULL 등)의 변경분은 [예약 제안/수락과 채팅 알림 설계](reserve-propose-design.md)가 기준이다.

알림 3종(새 제안, 상대가 예약, 상대가 예약 취소)의 구현(V10, 브랜치 `feature/notifications`, 미병합)에서 무엇을 놓고 어떻게 골랐는지의 근거다. 확정 규칙 본문은 [CLAUDE.md](../../CLAUDE.md), 용어는 [용어집](../glossary.md), 잠금 규칙과 함정은 [잠금 순서와 인덱스·유니크 키 함정](../gotchas/lock-order-and-index-pitfalls.md) 8절이 기준이다. 이 페이지는 새 결정을 만들지 않는다.

## 생성 시점: 동기 INSERT vs 커밋 후 이벤트

| 안 | 장점 | 단점 |
|---|---|---|
| A. 상태 전이와 같은 트랜잭션 끝에서 동기 INSERT (선택) | 상태가 바뀐 경우에만 알림이 남고, 롤백되면 알림도 사라져 일관된다. 구조가 단순하다 | notification 쓰기가 잠금 경로에 들어가므로 잠금 순서를 지켜야 한다(users S 잠금) |
| B. 커밋 후 이벤트(`AFTER_COMMIT`)로 별도 트랜잭션에서 INSERT | 핵심 트랜잭션의 잠금 범위가 줄어든다 | 알림 INSERT 실패나 서버 종료 시 알림이 유실될 수 있고, 재시도·아웃박스를 따로 만들어야 한다 |

선택 이유(구현 기록 기준): 알림 유실 없이 상태 변경과 함께 원자적으로 남기는 쪽을 택하고, 교착 위험은 "트랜잭션 맨 끝에서 쓰기, 수신자당 1건, 읽음·삭제는 잠금 없는 SELECT 후 IN 벌크"로 줄였다. 임시 MySQL 스트레스 테스트에서 교착(1213)은 0건이었다. 커밋 후 이벤트 방식은 실시간 푸시 전송에만 쓰는 것으로 나중에 반영됐다(아래 '실시간 푸시' 절, [STOMP 조사](../research/stomp-jwt-auth.md)). 이 비교의 실측 성능 수치는 없다.

## dedup_key

요구사항 가안의 `(user_id, type, match_id)` 유니크는 재예약 때 예약이 롤백되는 함정이 있어 `dedup_key` 단일 유니크로 대체했다(자세한 재현 조건은 함정 페이지 8절). 새 제안만 키를 갖고 예약·예약 취소는 NULL이다.

## 사용자 결정 3개 (구현 세션 기록)

1. **닫힌 매칭 알림도 제외하지 않는다.** 취소·완료된 매칭의 알림도 안 읽은 개수와 목록에 남기고 회색 '종료된 매칭' 라벨만 붙인다. 알림이 사라지는 유일한 경로는 사용자의 '읽은 알림 삭제'다.
2. **화면 구성**: 헤더 벨 아이콘을 누르면 바로 아래 말풍선(최신 5건, '모두 읽음', '알림 전체 보기')이 뜨고, '알림 전체 보기'로 `/notifications` 페이지(더 보기 페이징, 모두 읽음, 읽은 알림 삭제 2단계 확인)로 간다.
3. **실시간은 별도 브랜치로 분리**: 알림 3종 구현 때는 화면이 보일 때만 30초 폴링(포커스·가시성 변화·경로 이동 시 즉시 재조회)만 했고, STOMP 실시간 푸시는 `feature/notifications-realtime`에서 이어서 구현했다(다음 절).

## 실시간 푸시 (`feature/notifications-realtime`, 2026-10-11, 미병합)

DB 변경은 없다(V12 없음). 아래는 구현 사실이며 새 결정이 아니다. 확정 규칙은 [CLAUDE.md](../../CLAUDE.md)를 본다.

- **신호만 싣는다**: 새 알림이 생기면 수신자의 모든 세션(탭)에 `/user/queue/notifications`로 `{type:"NOTIFICATION_CREATED", notificationId, notificationType, matchId}`만 보낸다. 알림 문구·상대 닉네임·좌석은 싣지 않고, 화면이 신호를 받으면 REST(안 읽은 개수, 목록)로 다시 읽는다. 이유로 추정되는 점은 푸시 경로에 개인 정보를 덜 싣고 읽음·삭제 상태의 기준을 REST 한 곳에 두는 것이다(구현 기록에 명시된 이유는 아니라 추정).
- **전파 시점**: `NotificationService.notify`가 INSERT 뒤 `afterCommit`에 전송을 등록한다. 롤백이면 보내지 않고, 전송이 실패해도 저장·응답은 유지되며 예외는 삼키고 로그만 남긴다(폴링이 보완). 알림 쓰기가 트랜잭션 맨 끝이라는 잠금 규칙은 그대로다. 위 비교의 B안(커밋 후 이벤트)을 저장이 아니라 전송에만 쓴 셈이다.
- **연결·구독**: 로그인한 앱 전체가 탭당 STOMP 연결 1개를 공유하고, 헤더 벨 훅과 채팅 훅이 참조 카운트로 함께 쓴다. 구독 규칙은 [함정 페이지 10절](../gotchas/lock-order-and-index-pitfalls.md)과 [채팅 설계 근거](chat-design.md) 참고.
- **폴링 완화**: 연결이 살아 있으면 30초 폴링 대신 5분마다 안전 확인만 하고, 끊겨 있으면 이전처럼 화면이 보일 때 30초 폴링한다. (재)연결 직후에는 즉시 안 읽은 개수를 다시 읽는다.
- **화면**: 벨 뱃지가 즉시 갱신된다. 벨 말풍선이 열려 있으면 목록을 조용히 다시 읽고, `/notifications` 페이지는 목록을 바꾸지 않고 "새 알림이 있어요. 눌러서 불러오기" 버튼만 띄운다. 토스트는 없다.
- **한계**: 브라우저·실제 `@stomp/stompjs` 수동 점검은 하지 않았다. 다른 탭의 읽음 처리는 푸시하지 않는다(focus·가시성 변화·5분 확인으로 보정). 토큰 만료 뒤 최대 30초 푸시가 이어질 수 있고, 연결·속도 제한은 단일 인스턴스 메모리다.
- 7일 경과 알림은 여전히 미구현이다.

## 이번에 하지 않은 것

거절·채팅 종료·7일 경과·교환 완료 알림은 만들지 않았다. 요구사항 문서의 알림 3종 범위와 열린 질문은 [후속요구사항 문서](../../산출물/04_요구사항정의서/후속요구사항_제안알림_교환됨_공연정보입력.md) 참고.
