# 관리자 페이지(공연 수정 제안·좌석 소유 인증) 설계 근거

구현 세션(2026-10-12, 브랜치 `feature/admin`, 커밋 `e608c5a`·`96a5623`·`6c04c08`·`04fecf7`, 병합됨)에서 정리한 근거다. 결정 본문은 [CLAUDE.md](../../CLAUDE.md)(공연 등록 절의 '수정은 관리자 페이지 수정 제안', 티켓 절의 '내 티켓 인증')가 기준이고 여기에는 근거와 대안만 둔다. 용어는 [용어집](../glossary.md).

## 범위가 정해진 과정

- 관리자 기능의 범위를 묻는 질문에 사용자가 "다"라고 답했다. 이를 **공연 수정 제안 처리와 좌석 소유 인증(내 티켓 인증) 확인을 둘 다 만든다**는 뜻으로 해석했다. 이는 해석이며 사용자가 두 항목을 따로 확인한 것은 아니다(그래서 confidence는 medium).
- 수정 대상을 묻는 질문에는 "상관없음"이라 답해, 추천안인 **제목·공연장만**으로 확정했다. 회차와 링크는 수정 대상이 아니다.
- 관리자 지정 방식은 기존 결정(DB에서 `users.role='ADMIN'` 직접 부여)을 그대로 쓴다. 신고 처리용 관리자 기능은 이번 범위가 아니다(요구사항 Q-21, 신고 착수 시 확인).

## 세부 선택과 이유

- **수정 대상은 제목·공연장만**: 회차는 티켓·희망 회차·마감과 얽혀 있어 바꾸면 교환 데이터에 파급이 크다. 링크는 중복 확인 키라서 같은 이유로 제외했다. 제목·공연장은 텍스트일 뿐이라 다른 테이블이 참조하지 않는다.
- **공연을 바꾸는 경로는 하나**: 엔티티의 `applyApprovedEdit`(관리자 승인)뿐이다. "등록 후 아무도 수정 못 한다"는 확정 결정과 충돌하지 않고, 그 결정이 말한 '수정 제안'의 구현이다. 승인 시 이전 값을 제안 행에 스냅샷으로 남긴다.
- **승인 = 현재 그 좌석의 활성 티켓을 시스템이 내린다**: 이미 같은 좌석이 등록돼 있다는 409의 원인은 실제 소유자가 아닌 사람이 먼저 등록한 경우다. 해소하려면 먼저 등록된 티켓을 비워야 하므로, 관리자 승인이 기존 티켓 내리기(요청 CLOSED, CHATTING 매칭 시스템 취소)와 같은 효과를 낸다. 예약 잠금 중이면 승인하지 않는다(409 `TICKET_RESERVED`). 요청자는 이후 일반 등록으로 직접 등록하며 **자동 등록은 하지 않는다**(소유권 판단과 등록 행위를 분리).
- **사진은 처리 후 삭제**: 예매내역 사진에는 예매번호·이름 같은 개인정보가 담길 수 있다. 승인·거절 모두 **커밋 뒤** 파일을 지우고 `image_deleted_at`만 남긴다. 삭제 실패는 처리 결과를 되돌리지 않는다(결과와 파일 정리를 묶으면 파일 오류로 승인이 막힌다). 저장은 서버 로컬 디스크이고 웹에서 직접 서빙하지 않으며, 조회는 본인·ADMIN만 허용한다.
- **알림 테이블을 쓰지 않는다**: `notification`은 (V12 당시) 유형 CHECK가 3종이었고(V15에서 6종) `match_id`가 필수라 이 기능에 맞지 않는다. 제안자·요청자는 각자 `/my/edit-proposals`, `/my/seat-claims`에서 결과를 본다. 근거 구조는 [알림 설계](notification-design.md).
- **PENDING만 유일하게 하는 방법**: 사용자(·좌석)당 대기 1건을 상태 전이로 값이 바뀌는 컬럼에 걸어야 해서 생성 컬럼+UNIQUE를 썼다. 함정은 [함정 페이지 11절](../gotchas/lock-order-and-index-pitfalls.md).

## 택하지 않은 대안

- **회차 수정까지 허용**: 위 이유로 교환 데이터 파급이 크고 마감·희망 회차 재검증이 필요해 제외했다.
- **승인 시 자동 등록**: 요청자의 티켓을 시스템이 대신 만들면 사진 한 장으로 등록까지 끝나 오남용 여지가 커진다. 직접 등록으로 남겨 기존 검증(상한·중복·마감)을 그대로 거친다.
- **알림 테이블 확장(유형 추가)**: 유형이 매칭에 묶인 구조라 `match_id` NULL 허용 등 스키마 변경이 필요하다. 실시간·미읽음 흐름까지 넓어지므로 이번에는 목록 확인으로 대신했다. 필요해지면 후속에서 재검토한다.

## 후속: 신고·차단 관리

신고 처리·이용 정지·차단 현황 관리자 기능은 이 페이지의 범위 밖이었고 이후 [차단·신고·이용 정지 설계 근거](block-report-design.md)에서 다뤘다(Q-21 확정).

## 한계

- 커밋 뒤 사진 삭제 실패나 서버 종료로 남은 파일은 정리 작업(`SeatClaimImageCleanupService`, 2026-10-13)이 주기적으로 지운다: 처리됐는데 기록이 없는 사진, 요청 행이 없는 고아 파일(저장 직후의 틈을 위해 60분 지난 것만). PENDING 사진은 지우지 않는다. 서버 한 대 기준이며 설정은 `matjari.upload.cleanup.*`.
- 관리자 좌석 인증 목록의 holder 조회가 N+1이다(최대 100건).
- 관리자가 자기 제안·자기 인증 요청을 승인하는 것은 409 `SELF_REVIEW`로 막는다(거절은 허용). 승인 시점에 좌석을 요청자 본인이 가졌다면 본인 티켓은 내리지 않고 승인만 완료한다(resolved 없음). 승인 트랜잭션은 READ COMMITTED로 돌려 예약 잠금 검사가 낡은 스냅샷을 읽지 않게 한다(검증에서 발견한 TOCTOU).
- 이미지 저장소가 서버 로컬 디스크라 다중 인스턴스에서 쓸 수 없다.
- EXIF를 제거하지 않는다(처리 후 삭제로 대응).
- 프론트 관리자 가드는 프로필 조회 후 판단해 로딩 중 잠깐 확인 중 표시가 뜬다(서버는 `/api/admin/**` hasRole("ADMIN")으로 별도 차단).
- 브라우저 점검은 하지 않았다(`tsc`·빌드와 백엔드 테스트만). 테스트 수치는 구현 세션 기록이며 이 위키에서 재실행하지 않았다.

## 회차 수정 제안 (2026-10-14, V20)

- 배경: 처음에는 수정 제안이 제목·공연장만 다뤘고 회차는 대상이 아니었다(공연 등록 때 회차를 잘못 넣으면 고칠 길이 없었다). 사용자가 회차 수정을 요청해 제안에 회차 변경(`ADD`·`CHANGE`·`REMOVE`)을 넣었다. 규칙의 본문은 CLAUDE.md '공연 수정 제안' 절이고 여기에는 판단 근거만 둔다.
- **JSON 컬럼 한 개로 저장한 이유**: 자식 테이블이면 처리된 제안의 회차 FK가 회차 삭제를 막거나 끊어진다. 변경 목록은 항상 제안과 함께만 읽고 따로 조회·집계하지 않는다. 대신 형식·충돌 검증은 전부 서비스가 한다(생성과 승인 두 시점에 같은 함수).
- **삭제를 '사용 중이 아닌 회차'로 제한한 이유**: 티켓·교환 희망 조건·좌석 인증 요청이 FK로 회차를 가리키므로 어차피 지울 수 없고, 억지로 지우면 사용자 데이터가 사라진다. 시각 변경은 회차 id를 유지해 이들을 그대로 둔다.
- **시각 맞바꾸기 거부**: (공연, 시각) unique 제약 때문에 단계별 갱신이 중간에 깨진다. 임시 값을 쓰는 우회보다 하나씩 나눠 제안하게 하는 편이 단순하고 안전하다고 판단했다.
- **승인 충돌은 409 `SESSION_EDIT_CONFLICT`로 막고 제안은 PENDING 유지**: 제안한 뒤 승인하기 전에 회차에 티켓이 걸릴 수 있다. 자동으로 일부만 반영하지 않고 관리자가 거절하게 한다.
- 알려진 한계: 시각 맞바꾸기는 두 번에 나눠야 한다. 지난 시각 검사는 제안을 만들 때만 한다(승인 때 지났어도 막지 않는다).

## 관리자 권한 확장 (2026-10-19, V22)
- 결정(사용자): 공연 내리기(숨김, 삭제 없음), 제목·공연장·회차·구역 직접 수정, 이용자 관리 전부(직접 정지·해제, 역할 부여·해제, 강제 탈퇴). 숨긴 공연은 목록·검색에서 빠지고 새 티켓·새 교환 요청·새 제안만 막으며 진행 중인 매칭은 끝까지 간다.
- 구조: `performance.hidden_at/hidden_by_id/hidden_reason`(CHECK로 셋이 함께), `admin_action_log`(추가 전용, 대상은 FK 아님). 회차 규칙은 `SessionChangePlanner`로 뽑아 수정 제안 승인과 관리자 직접 수정이 같은 코드를 쓴다. 직접 정지는 `user_sanction.report_id`=NULL로 기존 제재 생성 코드를 공용화했고, 강제 탈퇴는 `WithdrawService` 정리 코어를 재사용한다.
- 안전장치와 이유: 자기 역할 변경 불가·마지막 관리자 보호(관리자가 0명이 되는 사고), 관리자 대상 정지·강제 탈퇴 불가(먼저 역할을 내려야 한다), 강제 탈퇴는 확인 문구 직접 입력(되돌릴 수 없어서), 모든 조치에 사유·처리자·시각 기록.
- 잠금: 공연 조치는 공연 행 FOR UPDATE가 첫 쿼리, 역할 변경은 활성 ADMIN 행을 id 순으로 잠근 뒤 대상 users 행, 조치 기록은 트랜잭션 맨 끝.
- 한계: 직접 정지 동시 요청 시 활성 제재가 둘 생길 수 있음(해제로 무해), 관리자 목록 JPQL의 MySQL 실DB 검증 없음, 기존 처리(신고 처리·인증·제안 승인)는 이 기록 테이블에 남지 않는다.
