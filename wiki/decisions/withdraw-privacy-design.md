# 회원탈퇴·개인정보처리방침 설계 근거

회원탈퇴(`DELETE /api/users/me`, V17 `users.withdrawn_at`), 공개 개인정보처리방침(`/privacy`), 푸터·가입 화면 안내의 근거를 정리한다(브랜치 `feature/withdraw`, 2026-10-13 구현, 병합됨). 확정 규칙의 기준은 [CLAUDE.md](../../CLAUDE.md)다. 이 페이지는 **왜 이렇게 했나**와 **아직 정해지지 않은 것**을 적는다. 구현 세부는 백엔드 README '회원탈퇴·개인정보처리방침 (V17)' 절에 있다.

사용자가 정한 것은 세 가지다(2026-10-13): ①진행 중 교환은 예약 중이어도 모두 자동 정리하고 탈퇴시킨다 ②채팅·신고·제재 기록은 지우지 않고 익명화해 유지하며 방침에 명시한다 ③운영자 정보는 자리표시로 두고 빌드 환경변수로 받는다. 나머지(익명화 세부, 잠금 순서, 보관 기간 문구)는 구현 중에 정했고, 아래에 근거와 대안을 남긴다.

## 1. 익명화 범위와 이유

| 대상 | 처리 | 이유 |
|---|---|---|
| 이메일 | `withdrawn.{id}@withdrawn.seatswap.invalid`로 바꾼다 | 원래 이메일을 비워 같은 이메일로 재가입할 수 있게 한다. id를 넣어 기존 UNIQUE(email)를 그대로 쓴다 |
| 닉네임 | `탈퇴한 회원` | 채팅·교환 이력·관리자 화면은 users에서 닉네임을 읽으므로 따로 고치지 않아도 '탈퇴한 회원'으로 보인다 |
| 비밀번호 | 무작위 32바이트의 BCrypt 해시, `password_login_enabled`=0 | 비밀번호로 다시 로그인할 수 없게 한다. 해시가 있어도 로그인 수단 판단은 플래그로 한다(V16 결정) |
| 소셜 연결(`social_account`) | 전부 삭제 | 제공자 식별자가 탈퇴 뒤에도 남으면 같은 계정 연결을 통해 추적·재연결이 가능하다. 삭제하면 같은 소셜 계정으로 새 가입이 된다 |
| 활성 티켓·OPEN 요청·열린 매칭 | INACTIVE·CLOSED·시스템 취소, 예약 잠금 해제 | 탈퇴한 사람이 다른 사람의 교환을 잠근 채 남지 않게 한다(사용자 결정 ①) |
| PENDING 좌석 인증 요청 | 거절(처리자는 본인, 메모 기재), 사진은 커밋 뒤 삭제 | 본인 좌석 증명 사진은 처리 대상이 없어지면 남길 이유가 없다 |
| 채팅 메시지·읽음 상태 | 보존 | 상대방의 대화 기록이자 신고 근거다. 지우면 상대방 쪽 기록이 훼손된다(사용자 결정 ②) |
| 교환 이력(`exchange_history`) | 보존 | 거래 기록은 분쟁 대응에 필요하다. 이력 화면에는 상대 정보가 없다 |
| 차단·신고·제재 | 보존 | 부정 이용 방지와 신고된 쪽의 권리를 위해 남긴다(사용자 결정 ②) |
| PENDING 공연 수정 제안 | 보존 | 공연 정보에 관한 제안이며 관리자가 처리해야 한다. 제안자 칸은 '탈퇴한 회원'으로 보인다 |
| 받은 알림(`notification`) | 삭제 | 수신자 본인에게만 보이는 데이터라 탈퇴 뒤에는 볼 사람이 없다. 상대에게 가는 알림은 만들지 않는다 |
| `role` | 유지 | ADMIN은 탈퇴할 수 없다. 관리자는 DB에서 역할을 USER로 내린 뒤에만 탈퇴한다(409 `ADMIN_CANNOT_WITHDRAW`) |
| 열린 세션(액세스 토큰, STOMP) | 즉시 무효(401), 커밋 뒤 STOMP 연결 종료 | 탈퇴 뒤에 계속 쓸 수 있으면 안 된다 |

원칙은 "개인을 식별하는 값과 본인만 쓰는 데이터는 지우고, 상대방과 제3자의 권리가 걸린 기록은 주체를 익명화해 남긴다"다.

## 2. 대안 비교

| 안 | 내용 | 결과 |
|---|---|---|
| A | users 행 물리 삭제 | FK(채팅·교환 이력·차단·신고·제재)가 깨지거나 CASCADE로 기록이 사라진다. 분쟁·신고 근거가 없어진다. 기각 |
| B | 익명화(행 유지, 식별 값만 제거) | 채택. FK와 기록을 살리고 개인 식별 값만 없앤다 |
| C | 채팅 메시지 삭제 | 상대방의 대화 기록과 상대방이 낸 신고의 근거가 사라진다. 기각 |
| D | 탈퇴를 막고 사용자가 먼저 교환을 정리하게 함 | 개인정보 삭제 요구를 운영 사정으로 막는 구조다. 상대의 예약 잠금이 탈퇴자 때문에 풀리지 않을 수 있다. 사용자 결정(자동 정리)으로 기각 |
| E | 진행 중 교환을 자동 정리(채택) | 상대방의 잠금이 풀리고 새 교환이 막힌다. 열린 채팅은 상대에게 '탈퇴한 회원'으로 남는다 |
| F | 교환 이력 삭제 | 거래 기록이 사라져 분쟁에 대응할 수 없다. 기각 |
| G | 소셜 연결을 남기고 재가입 차단 | 제공자 식별자가 탈퇴 뒤에도 남는다. 같은 소셜 계정으로 새로 가입할 수 없어 기각 |
| H | 익명 데이터의 자동 파기 스케줄 | 보관 기간의 법적 근거가 확정되지 않았다. 지금은 보류하고 방침에는 '운영 기간 동안 보관, 종료 때 파기'로 적었다(§5, 한계 5) |

## 3. 잠금 순서: 설계 초안을 바꾼 이유

설계 초안은 "탈퇴는 users 행을 FOR UPDATE로 **먼저** 잡는다"였다. 구현하고 나서 바꿨다.

- 제안(propose)은 티켓을 잠근 뒤 `exchange_match`를 INSERT한다. 이때 FK 검사를 위해 users 행에 공유 잠금을 요청한다.
- 탈퇴가 users를 먼저 X로 잡고 티켓을 기다리면, 제안은 티켓을 쥔 채 users를 기다리고 탈퇴는 users를 쥔 채 티켓을 기다린다. 교착이다.
- 이용 정지(`ACCOUNT_SUSPENDED` 처리)도 같은 이유로 users 잠금 없이 취소를 한다.

그래서 실제 순서는 **인증 요청 → 티켓 id↑ → 매칭 id↑ → 요청 → users → 알림**이다(요청을 매칭 뒤에 잡는 것은 알려진 좁은 교착 창이며, 이때는 503이 나고 재시도한다). users를 맨 뒤에서 잡으면 제안과 교착하지 않는다. 대신 users를 잡기 전과 잡은 뒤에 두 번 정리해야 한다.

- 1차 정리(users 잠금 전): 열린 매칭·티켓·요청·인증 요청을 위 순서로 정리한다.
- users 잠금: 탈퇴 여부를 확인한다. 이미 탈퇴했으면 401로 끝낸다.
- 2차 정리(users 잠금 뒤): 1차와 users 잠금 사이에 생긴 활성 티켓과 열린 매칭을 마저 정리한다.

users 잠금을 잡은 뒤에는 새 활성 티켓·PENDING 인증·소셜 연결이 생기지 않는다. 티켓 등록, 인증 요청, 공연 수정 제안, 소셜 연결 경로가 모두 users FOR UPDATE로 시작하고 탈퇴 여부를 보기 때문이다. 이 규칙은 [잠금 순서 함정 페이지](../gotchas/lock-order-and-index-pitfalls.md) 15절에도 적었다.

### 교착 창 두 개 (감지기 의존)

완전히 막지는 못했다. MySQL이 교착을 감지하면 해당 요청이 503으로 실패하고 재시도하면 된다. 불변식은 깨지지 않는다.

- 창 A: 본인이 두 탭에서 요청 수정·삭제와 탈퇴를 동시에 실행한다. 요청 수정은 요청→매칭 순서로, 탈퇴는 티켓→매칭→요청 순서로 잠근다.
- 창 B: 1차 정리와 users 잠금 사이에 본인이 새 티켓을 등록하고, 상대가 그 티켓에 제안한다. 밀리초 단위의 창이다.

`WithdrawMysqlTest`(탈퇴 vs 제안·예약 수락/철회·교환 수락·탈퇴끼리·소셜 연결 확정·티켓 등록, 15라운드)에서 교착 없이 불변식(활성 티켓 0, 열린 매칭 0, OPEN 요청 0, 잠금 행 = 2×RESERVED, social_account 0, 알림 0, PENDING 인증 0, 익명화 이메일 형식)이 유지되는 것을 확인했다.

## 4. 방침 페이지의 구성

- 표준 작성지침의 목차 순서를 따랐다: 처리 목적 → 처리 항목 → 14세 미만 → 보유 기간(표) → 파기 → 제3자 제공(없음) → 위탁(없음) → 권리 행사 → 쿠키 → 보호책임자 → 안전성 확보 조치 → 변경·시행일.
- 쿠키 항목에는 소셜 로그인의 한시 쿠키 `ss_oauth`(Max-Age 600초)와 localStorage 토큰을 적었다.
- 운영자·문의 이메일·시행일은 `VITE_PRIVACY_OPERATOR`·`VITE_PRIVACY_CONTACT_EMAIL`·`VITE_PRIVACY_EFFECTIVE_DATE`로 받는다. 비어 있으면 `[운영자 정보 설정 필요]`·`[시행일 설정 필요]`로 강조해 공개 운영 전에 빠뜨리지 못하게 했다.
- "제공자 프로필 닉네임을 초기 닉네임으로 사용한다"는 문장을 넣었다(소셜 가입 때 닉네임을 가져온다).
- 이용 정지 중에도 탈퇴 API는 허용한다(결정 2026-10-13, 한계 1). 비밀번호 로그인이 맞으면 403 본문의 `withdrawToken`(탈퇴 전용 10분 토큰)으로 탈퇴한다. 방침 §8은 소셜 전용 정지 사용자에게 문의처를 안내한다.
- 가입 화면에는 체크박스 없이 "가입하면 동의한 것으로 봐요, 만 14세 미만은 가입할 수 없어요" 한 줄과 방침 링크만 둔다. 동의 기록은 DB에 남지 않는다(한계 6).
- 보관 기간의 법적 근거, 익명화의 법적 충분성, 외부 위탁 여부는 방침에 단정하지 않았다. 이 한계들은 **방침 페이지가 아니라 이 문서에만 둔다**. 방침은 공개 문서라 미확정 법적 판단을 적지 않는다.

## 5. 보유 기간 조사 요약 (2026-10-12, 법률 자문 아님)

조사 결과는 자문 전의 권장 초안이며, 법령 원문 확인은 하지 못했다.

확인된 것(신뢰 높음~중간)
- 개인정보 보호법 제21조: 보유 기간이 지나거나 목적을 이루면 지체 없이 파기한다. 예외는 다른 법령의 보존 의무뿐이고, 예외로 보존하는 정보는 다른 개인정보와 분리해 관리한다.
- 전자상거래법 시행령 제6조(거래 기록): 계약·청약철회 기록 5년, 대금결제·재화공급 5년, 소비자 불만·분쟁처리 3년, 표시·광고 6개월. 다만 결제나 청약 접수를 하지 않는 이 서비스에 직접 적용되는지는 확인하지 못했다.
- 휴면계정 제도는 2023년 9월 개정으로 폐지된 것으로 보인다(2차 자료).
- 개인정보 처리방침의 필수 항목은 개인정보 보호법 제30조 1항의 8가지다. 표준 작성지침 목차는 위 §4와 같다.
- 만 14세 미만은 법정대리인 동의가 필요하다(제22조 6항). 이 서비스는 가입을 받지 않는다고 적었다.
- 소셜 식별자: 구글 `sub`는 고유하고 재사용되지 않지만, 이메일은 바뀔 수 있어 식별자로 쓰지 않는다. 카카오는 앱별 회원번호를 권장한다. 네이버는 확인하지 못했다.

미확인
- law.go.kr 원문 직접 확인.
- 통신비밀보호법의 로그 보관 규정(근거를 찾지 못함). 접속기록 보관은 안전성 확보조치 기준의 취급자 접속기록(1년 이상)이며 이용자 로그와 별개다.
- 신고·제재 이력의 법적 보존 근거(근거 없음. 민법 766조 3년은 참고일 뿐이다).
- 익명화의 법적 충분성.
- 네이버 제공 항목.

권장 초안과 실제 구현

| 항목 | 권장 초안 | 구현·방침 |
|---|---|---|
| 이메일·닉네임·소셜 식별자 | 탈퇴 시 파기·익명화 | 구현(§1) |
| 교환 매칭·이력 | 일정 기간 보관(5년 참고, 적용 불확실, 정책으로 정하고 방침에 명시) | 방침은 '운영 기간 동안 보관, 종료 때 파기'. 기간 숫자는 정하지 않았다 |
| 채팅 메시지 | 무기한은 위험, 기간 설정 필요 | **기간을 정하지 않았다.** 방침은 운영 기간 동안 보관으로 적었다(§6, 추가 관찰 1) |
| 신고·제재 이력 | 제재 종료 후 일정 기간(3년 참고, 근거 미확인) | 방침은 운영 기간 동안 보관으로 적었다 |
| 로그인·접속 기록 | DB에 저장하지 않는지 확인 필요 | 조사 시점에는 접속 로그를 DB에 저장하지 않는 것으로 보았으나 확인하지 못했다. 서버 로그의 보관 기간은 정하지 않았다 |
| 예매내역 사진 | 처리 후 즉시 삭제 | 처리 뒤 커밋 뒤 1회 삭제를 시도한다. 실패하면 로그만 남긴다(한계 3) |

## 6. 알려진 한계 8개 (전부)

1. **이용 정지 중 탈퇴는 비밀번호 계정에게만 화면까지 열려 있다**(결정 2026-10-13: 허용; 제한 로그인은 같은 날 구현). `JwtAuthenticationFilter`의 정지 예외에 `DELETE /api/users/me`를 추가했고 `loadUserByIdAllowingSuspended`로 로딩한다. 정지 중 로그인은 여전히 403이지만 **비밀번호가 맞은 경우에만** 403 본문에 탈퇴 전용 토큰 `withdrawToken`(JWT `type=withdraw`, 10분)을 더한다. 이 토큰은 필터가 `DELETE /api/users/me`에서만 인증으로 인정하고 재발급·STOMP·다른 API에는 쓸 수 없다. 로그인 화면이 "이 계정 탈퇴하기"를 보여 주고 탈퇴 모달이 비밀번호를 다시 받아 일반 탈퇴 검증(비밀번호·분당 5회·ADMIN 거절)을 그대로 거친다. 토큰은 저장하지 않고 화면 메모리에만 둔다. 한계: 소셜 전용 정지 사용자는 비밀번호 로그인이 없어 이 경로를 쓸 수 없고 방침 §8의 문의처로 요청한다.
2. **소셜 전용 계정은 소셜 재인증을 거쳐 탈퇴한다**(2026-10-13 구현). 연결된 제공자 중 지금 켜져 있는 것이 있으면 확인 문구 `탈퇴합니다`에 더해 **그 계정으로 방금 다시 인증한 일회용 코드**(`reauthCode`)가 있어야 한다. 흐름은 연결 모드를 재사용한다: `POST /api/users/me/social/{provider}/reauth`(이미 연결된 제공자만)가 링크 티켓을 발급하고 콜백이 `/me#linkCode=`로 코드를 돌려주며, 이 코드를 연결 확정이 아니라 탈퇴에 쓴다(코드의 사용자 = 요청 사용자이고 `social_account(user, provider, providerUserId)`가 있어야 하며 불일치여도 코드는 소진). 연결된 제공자가 모두 꺼져 있으면 재인증 수단이 없어 확인 문구만으로 허용한다(주인이 탈퇴할 길을 막지 않는다). 한계: 재인증 코드는 연결 확정 코드와 같은 저장소·형식이라 목적을 구분하는 표지가 없다(연결 시작은 아직 연결되지 않은 제공자만, 재인증은 이미 연결된 제공자만 허용하므로 서로 바꿔 쓸 수 없다). 제공자의 "방금 인증"은 60초 코드 수명으로 갈음한다(제공자에 재인증 강제 파라미터는 쓰지 않는다).
3. **인증 사진 삭제는 1회 시도 + 정리 작업이다**(2026-10-13 보강). 커밋 뒤 삭제에 실패하면 로그만 남기지만, `SeatClaimImageCleanupService`가 주기적으로(기본 1시간, 기동 5분 뒤 첫 실행) 처리됐는데 기록이 없는 사진과 요청 행이 없는 고아 파일(저장 직후 INSERT 전의 틈을 위해 60분 지난 것만)을 지운다. PENDING 사진은 지우지 않고 서버 한 대 기준이다. 정리 사이에도 처리된 요청의 사진 조회는 불가능하다(410).
4. **교착 창 2개는 감지기에 의존한다.** 교착이 나면 503이 나오고 재시도하면 된다(§3). 불변식은 깨지지 않는다.
5. **보관 기간의 법적 근거가 확정되지 않았다.** 자동 파기 스케줄도 없다. 익명화의 법적 충분성도 미확인이다. 공개 운영 전에 전문가 검토가 필요하다(법률 자문이 아니다). 이 항목은 방침 페이지에 쓰지 않는다(§4).
6. **가입 시 동의 기록과 14세 미만 확인 수단이 없다.** 문구만 있다. 소셜 로그인 화면에는 방침 안내 문구가 없고 푸터 링크로 갈음한다.
7. **외부 위탁 여부는 배포 형태에 따라 달라진다.** 방침의 '외부 위탁 없음'은 클라우드 호스팅·메일 등 배포 형태가 정해지면 다시 확인해야 한다. JWT 클레임에는 원래 이메일이 남지만 본인 브라우저에만 있고 로그아웃 때 지워진다. 인증 요청 거절 처리자 칸에는 '탈퇴한 회원'이 표시된다.
8. **탈퇴 속도 제한은 서비스 내부 메모리다.** 사용자당 분당 5회(성공과 실패를 모두 센다, 429 `WITHDRAW_RATE_LIMITED`)이며 재시작하면 초기화되고 단일 인스턴스를 가정한다.

### 추가 관찰 (위 8개에 없는 것, 확인 필요)

조사 과정에서 드러난 것이며 검증 목록에는 없다. 판단은 사용자와 정한다.

1. **채팅 기간 미정.** 기존 결정은 채팅 메시지를 무기한 보관한다. 조사는 이것을 위험으로 봤다. 방침은 '운영 기간 동안'으로 적었으므로 실제 기간 제한과 맞지 않을 수 있다.
2. **재가입으로 차단·정지를 우회할 수 있다.** 차단과 정지는 user id 기준이라, 탈퇴 뒤 같은 사람이 새 계정으로 가입하면 적용되지 않는다. 휴대폰 인증 같은 식별 수단이 없어서 지금 구조로는 막을 수 없다. 탈퇴한 계정의 신고·제재 기록은 남지만 우회를 막는 기록은 아니다.
3. **관리자 신고 처리는 탈퇴자의 채팅을 근거로 볼 수 있다.** 신고가 열린 상태에서 신고된 쪽이 탈퇴하면 채팅 근거는 그대로 남는다. 탈퇴한 대상에게는 새 제재를 걸 수 없다(409 `TARGET_WITHDRAWN`).

## 휴대폰 인증 검토 (2026-10-13, 보류)

재가입 시 차단·정지가 적용되지 않는 문제(식별 수단 없음)를 막으려는 목적으로 조사했고, **이번에는 붙이지 않기로 했다.**
- 본인확인기관(PASS·NICE·KCB·포트원 본인인증)은 사업자 계약이 필요한 것으로 보이며 개인 운영자의 가입 조건·테스트 방법은 확인하지 못했다.
- SMS OTP는 가능하다(예: Solapi 단문 건당 18원, 발신번호는 본인 명의 번호 인증 필요, 로컬은 스텁으로 테스트). 그러나 번호 소유 확인일 뿐 실명 확인이 아니라 1인 1계정 목적은 불완전하다(번호 여러 개로 우회).
- 번호를 받으면 개인정보처리방침 항목·위탁(SMS 대행사)·동의 기록·보유 규칙이 바뀌어야 하고(지금 방침은 동의 기록 없음), 번호는 HMAC-SHA256(서버 키는 DB 밖)으로만 저장해야 한다. 외부 계정·키 없이는 실제 발송을 검증할 수 없다.
- 구조를 열어 둘 때의 안: `PhoneVerificationSender` 어댑터 + 개발용 스텁 + 운영에서만 제공자 키 주입(키가 없으면 기능 비활성).
