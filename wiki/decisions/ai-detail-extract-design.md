# AI 회차·구역 읽기 설계 근거

공연 등록 2단계의 'AI로 회차·구역 읽기'(`POST /api/performances/ai-extract`, V21 `performance_zone`, 브랜치 `feature/ai-extract-backend`, 2026-10-18)의 근거를 정리한다. 확정 규칙은 [CLAUDE.md](../../CLAUDE.md)의 'AI 회차·구역 읽기' 절이 기준이고, 이 페이지는 **왜 이렇게 했나**, **무엇을 조사했나**, **무엇이 미확인인가**만 적는다. 법률 자문이 아니다. 조사 내용 중 법·약관 부분은 요약이며 원문을 이 저장소에 두지 않았고, 출처 URL·접근일은 기록하지 못한 것이 많다(그 부분은 '미확인'으로 표시했다).

## 1. 목적

- 링크 미리보기는 회차 시각을 읽지 못한다(Ajax). 그 빈자리를 [링크 자동 입력 설계 근거](link-autofill-design.md) 6절이 'AI 상세정보 출처를 붙일 자리'로 열어 두었고, 이 기능이 그 자리를 채운다.
- 읽는 것은 회차(날짜·시각)와 좌석 구역(이름, 선택으로 모양)이다. 구역은 티켓 등록·교환 조건에서 드롭다운으로 고르게 해 오타와 표기 흔들림을 줄이는 데 쓴다.
- **공연 등록 때만, 한 공연당 한 번** 부른다(같은 링크의 결과는 168시간 보관: 메모리 + DB `ai_extract_cache`(V23), 2026-10-21에 24시간 메모리 캐시에서 변경). 결과는 사용자가 확인·수정한 뒤에만 등록되고, 틀려도 등록은 막히지 않는다. 자동 등록은 없다.

## 2. 처리 순서

1. 기존 SSRF 규칙대로 `SourceKeyResolver` 키로 고정 템플릿 URL만 요청해 상세 페이지를 받는다(사용자 URL을 요청하지 않는다).
2. 본문 텍스트에서 `SessionTextParser`가 규칙으로 회차를 읽는다. 결과가 있으면 AI 회차보다 우선한다.
3. (멜론만) 세로로 긴 상세 이미지를 내려받아 `ImageSlicer`가 겹치게 자른다(기본 1,000px 폭·1,400px 높이·20% 겹침, 최대 24조각).
4. 1차 호출: 모든 조각을 보내 회차, 구역 이름, 좌석표 위치를 받는다.
5. 모양(2026-10-19 변경): 좌석표를 잘라 `ShapeSegmenter`로 실제 도형 후보(블록 합치기·구멍 메우기·볼록 껍질)를 찾고, 원본·번호 표시·도형별 확대 타일 세 이미지로 AI(`label`)가 도형마다 구역 이름을 답한다. 3회 병렬 다수결, 같은 구역의 붙은 조각은 한 블록으로 합친다. 실패하면 기존 AI 좌표 호출(2차)로 대체. AI 좌표는 실제와 평균 IoU 0.378로 부정확했고, 작은 글자(10px)를 읽지 못해 이름이 어긋나 확대 타일을 더했다.
6. 서버가 날짜·시각·이름·좌표를 다시 검증하고 병합한다(`DetailExtractionService`, `PerformanceZoneSanitizer`). AI 응답은 신뢰하지 않는다.

### 2.1 설계에 빌린 아이디어

- **군중 검출 자료**(작은 물체가 큰 이미지에 흩어진 문제)에서 가져온 것: 큰 이미지를 **겹치는 타일**로 자르면 경계에 걸린 대상을 놓치지 않는다, 겹침 때문에 생긴 **중복은 병합**한다, 타일 **경계의 어긋난 결과는 버린다**. 대응은 이렇다. 겹침 20%(조각 간격 아래 겹침 높이보다 낮은 글자 줄은 어느 조각에든 온전히 들어간다), 같은 회차·같은 구역 이름은 한 번만 남기는 중복 제거(프롬프트에서도 "겹친 조각에 두 번 보여도 한 번만"을 요구, 서버가 `zoneKey`·날짜+시각으로 한 번 더 제거), 검증을 통과하지 못한 값은 버림.
- **RAG 평가 자료**의 교훈: 모델·조각 크기·프롬프트를 바꿔 비교할 때는 **같은 입력·같은 정답으로** 비교해야 하고, **표본이 작으면 결론을 믿지 않는다.** 그래서 지금의 시험 결과(5절)는 '동작 확인'이지 정확도 측정이 아니며, 정확도 평가는 후속으로 남겼다.
- 위 두 자료는 아이디어 출처이고, 본문을 이 위키에 옮기지 않았다. 출처 URL·접근일은 기록하지 못했다(미확인).

## 3. 선택지와 이유

### 3.1 모델

- 기본은 Anthropic **Haiku 5.5**(`claude-haiku-5-5`, 설정 `matjari.ai.model`). 이 일은 글자 읽기와 단순 구조화라 가장 싼 모델로 먼저 시험하는 것이 비용 규칙과 맞다.
- 정확도가 부족하면 **Sonnet 5.5**(`claude-sonnet-5-5`)로 설정만 바꿔 올릴 여지를 둔다. 올릴지는 평가 세트가 생긴 뒤 같은 조건 비교로 정한다(후속).
- 출력은 JSON 스키마(structured outputs)로 받는다. 개수·크기 제약 키워드(`minItems/maxItems` 등)는 API가 거절하므로 스키마에 쓰지 않고 서버 검증으로 대신한다.

### 3.2 무료 티어(Gemini 등)를 쓰지 않은 이유

- 무료 티어는 입력이 **모델 학습이나 사람 검토에 쓰일 수 있다**는 조건이 붙는 것으로 조사됐다. 공개 상세 이미지만 보내므로 큰 문제는 아니지만, 서비스에 붙이는 이상 그 조건을 기본으로 받아들이고 싶지 않았다.
- 서비스 약관에 **소비자용이 아니다·18세 이상** 같은 조항이 있어, 개인 포트폴리오 서비스에 쓰는 것이 허용되는지 해석 위험이 있다. 이 해석은 확인하지 못했다(미확인).
- 위 두 이유 모두 약관 본문을 대조한 것이 아니라 조사 요약에 기댔다.

### 3.3 Claude 구독(Max)과 API는 별개

- Claude 구독(Max)과 API(Console)는 **결제가 따로**다. 구독 한도로 서비스 백엔드를 돌릴 수 없다.
- 구독 로그인(OAuth 토큰)을 서비스 백엔드에 쓰는 것은 **약관상 금지**다. 그래서 Console API 키(`ANTHROPIC_API_KEY`)를 쓴다. 개발·운영 키를 따로 두고 `.env`에만 넣는다(커밋 금지).

## 4. 법·약관 조사 요약 (법률 자문 아님)

| 항목 | 요약 | 확인 정도 |
|---|---|---|
| 인공지능기본법 제31조 | 생성형 AI를 쓰는 서비스는 이용자에게 **사전 고지**하라는 취지로 이해했다. 그래서 AI 결과 영역에 "AI가 읽은 결과입니다. 맞는지 확인하고 필요하면 고쳐 주세요."를 항상 보이고, 약관 5조의2·개인정보처리방침 7의2에 AI 이용 문구를 두었다 | 조문 취지만 확인, 시행 시점·세부 의무·적용 범위는 미확인 |
| Anthropic 상업 약관 | API 입력·출력을 **모델 학습에 쓰지 않는 것**이 기본, API 데이터는 **기본 30일 이내 삭제**로 이해했다 | 조사 요약, 약관 본문 대조는 미확인 |
| 한국 지원 | 한국에서 API를 쓸 수 있는 것으로 확인했다 | 조사 요약, 변동 가능 |
| 개인정보 | 프롬프트에는 **공개 상세 페이지의 이미지·본문만** 넣고 이용자 식별 정보(계정·이메일 등)는 보내지 않는다. 그래서 개인정보 국외 이전 쟁점은 크지 않다고 판단했다 | 코드로 확인(전송 내용), 법적 판단은 미확인 |
| 상세 이미지 저작권 | 이미지는 요청 처리 중 메모리에서만 쓰고 저장하지 않는다. 다만 제3자 이미지를 외부 AI에 보내는 행위의 이용약관·저작권 판단은 하지 않았다 | **미확인.** [포스터 표시 설계 근거](poster-display-design.md) 3절과 같은 한계 |

공개 운영 전에 약관과 방침 문구를 전문가에게 검토받아야 한다(CLAUDE.md '한계'에도 있다).

## 5. 구역 규칙

- 같은 이름은 **한 구역**이다(사용자 결정). 이름 비교는 티켓 구역 키와 같은 `SeatKeyNormalizer.zoneKey`로 한다.
- 구역은 이름(공백 정리 후 1~30자)과 선택 모양을 갖는다. 모양은 **다각형 조각 최대 8개**(꼭짓점 3~40개, 좌표 0~1000 정수)의 배열이고, 같은 이름이 지도에 여러 곳에 있으면 한 구역의 여러 조각이 된다. 8조각을 넘는 분량은 버린다.
- 모양이 규칙에 어긋나면 **모양만 버리고 이름은 남긴다.** 구역은 최대 100개.
- 서버는 목록에 없는 구역도 거절하지 않는다. 구역 목록은 입력 보조일 뿐이고 매칭 판정은 여전히 (구역, 열, 번) 텍스트 키로 한다. 매칭 코드는 구역 모양에 의존하지 않는다.
- DB: `performance_zone`(공연당 `name_key` 유일, FK 전용 단일 컬럼 인덱스 분리, 모양은 JSON과 CHECK로 조각 1~8·꼭짓점 3~40·16 KiB 이하), `performance.seatmap_aspect`(가로/세로 비율). 좌표 값 형식과 범위는 DB가 아니라 서비스가 검증한다(MySQL 8.0.16 호환을 위해 `JSON_SCHEMA_VALID`를 쓰지 않음). 상세는 V21 파일 머리 주석.
- 좌석표 트랙은 동결 상태인데 이것은 **사용자 결정(2026-10-18)에 따른 예외**다. 원본 이미지는 저장하지 않고 모양 좌표만 저장한다.

## 6. 시험 결과 (작은 표본, 정확도 측정 아님)

- 대상: 실제 멜론 공연 페이지 2건과 `213943`번 공연. 앞의 RAG 평가 교훈대로 표본이 작아 일반화하지 않는다.
- 회차와 구역 **이름은 정확**했다.
- 모양: 가운데 구역은 윤곽에 맞았고, **번호가 붙은 구역의 모양은 근사**였다(경계가 대충 맞는 수준).
- 응답 시간은 약 27초(1차 + 2차 호출 포함).
- 호출당 비용은 약 $0.01 이하로 **추정**했다(토큰 수 기준 계산, 청구서 대조는 하지 않았다).
- 이 수치는 모델·조각 크기·프롬프트를 바꿔 본 비교가 아니다. 같은 조건 비교는 평가 세트가 생긴 뒤에 한다.

## 7. 호출 제한과 안전

- 사용자당 하루(KST) 2회, 전체 하루 40회, 동시 2개. 메모리 기반이라 재시작하면 초기화된다. 캐시 적중과 AI를 부르지 않은 경우는 횟수에 세지 않는다. 초과는 429 `AI_RATE_LIMITED`.
- 키가 없거나 `matjari.ai.enabled=false`면 AI 없이 본문 규칙 결과만 준다(`aiEnabled:false`). AI가 실패하면 규칙 결과가 있을 때 200+`aiError:true`, 없으면 503 `AI_UNAVAILABLE`.
- 이미지 안의 글자는 데이터로 취급하고 도구는 쓰지 않는다. 이미지는 허용 호스트(`cdnticket.melon.co.kr`) 정확 일치·https 등 규칙으로 받고, 로그에는 시간·토큰 수·조각 수·결과 개수만 남긴다.

## 8. 알려진 한계

1. 멜론 상세 이미지만 읽는다. YES24는 상세 영역이 Ajax라 후속, 티켓링크는 이미지 주소를 얻을 수 없어 제외.
2. 구역이 많은 복잡한 지도(원형 경기장 등)는 정확도가 떨어질 수 있다. 측정한 적은 없다.
3. 모양 좌표는 근사다. 번호 구역은 특히 그렇다. 지금은 저장만 하고 화면 선택에는 쓰지 않는다.
4. 호출 제한·캐시가 메모리라 재시작·다중 인스턴스에서 맞지 않는다.
5. 시험이 작은 표본이다(6절). 비용·시간은 추정값이다.
6. 약관·방침 문구와 법·약관 해석은 전문가 검토 전이다(4절의 미확인 항목).

## 9. 후속

- 정확도 평가 세트와 튜닝: 실제 상세 이미지 20~30개에 정답을 붙여 모델(Haiku/Sonnet)·조각 크기·프롬프트를 **같은 조건으로** 비교한다. 평가용 이미지는 저장소에 올리지 않는다.
- 구역 모양을 클릭해 고르는 SVG 선택 화면.
- YES24 상세 이미지 읽기.
- 이미 등록된 공연의 구역 채우기와 구역 목록 수정(관리자).
- 검증된 정답을 프롬프트 예시로 쓰는 방식.
