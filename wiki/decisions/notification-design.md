# 알림 3종 설계 근거 (동기 INSERT 선택)

알림 3종(새 제안, 상대가 예약, 상대가 예약 취소)의 구현(V10, 브랜치 `feature/notifications`, 미병합)에서 무엇을 놓고 어떻게 골랐는지의 근거다. 확정 규칙 본문은 [CLAUDE.md](../../CLAUDE.md), 용어는 [용어집](../glossary.md), 잠금 규칙과 함정은 [잠금 순서와 인덱스·유니크 키 함정](../gotchas/lock-order-and-index-pitfalls.md) 8절이 기준이다. 이 페이지는 새 결정을 만들지 않는다.

## 생성 시점: 동기 INSERT vs 커밋 후 이벤트

| 안 | 장점 | 단점 |
|---|---|---|
| A. 상태 전이와 같은 트랜잭션 끝에서 동기 INSERT (선택) | 상태가 바뀐 경우에만 알림이 남고, 롤백되면 알림도 사라져 일관된다. 구조가 단순하다 | notification 쓰기가 잠금 경로에 들어가므로 잠금 순서를 지켜야 한다(users S 잠금) |
| B. 커밋 후 이벤트(`AFTER_COMMIT`)로 별도 트랜잭션에서 INSERT | 핵심 트랜잭션의 잠금 범위가 줄어든다 | 알림 INSERT 실패나 서버 종료 시 알림이 유실될 수 있고, 재시도·아웃박스를 따로 만들어야 한다 |

선택 이유(구현 기록 기준): 알림 유실 없이 상태 변경과 함께 원자적으로 남기는 쪽을 택하고, 교착 위험은 "트랜잭션 맨 끝에서 쓰기, 수신자당 1건, 읽음·삭제는 잠금 없는 SELECT 후 IN 벌크"로 줄였다. 임시 MySQL 스트레스 테스트에서 교착(1213)은 0건이었다. 커밋 후 이벤트 방식은 실시간(STOMP) 푸시를 붙이는 다음 브랜치에서 푸시 전송에만 쓸 수 있는지 다시 볼 수 있다([STOMP 조사](../research/stomp-jwt-auth.md)). 이 비교의 실측 성능 수치는 없다.

## dedup_key

요구사항 가안의 `(user_id, type, match_id)` 유니크는 재예약 때 예약이 롤백되는 함정이 있어 `dedup_key` 단일 유니크로 대체했다(자세한 재현 조건은 함정 페이지 8절). 새 제안만 키를 갖고 예약·예약 취소는 NULL이다.

## 사용자 결정 3개 (구현 세션 기록)

1. **닫힌 매칭 알림도 제외하지 않는다.** 취소·완료된 매칭의 알림도 안 읽은 개수와 목록에 남기고 회색 '종료된 매칭' 라벨만 붙인다. 알림이 사라지는 유일한 경로는 사용자의 '읽은 알림 삭제'다.
2. **화면 구성**: 헤더 벨 아이콘을 누르면 바로 아래 말풍선(최신 5건, '모두 읽음', '알림 전체 보기')이 뜨고, '알림 전체 보기'로 `/notifications` 페이지(더 보기 페이징, 모두 읽음, 읽은 알림 삭제 2단계 확인)로 간다.
3. **실시간은 다음 브랜치**: STOMP 실시간 알림은 `feature/notifications-realtime`에서 하고, 이번에는 화면이 보일 때만 30초 폴링(포커스·가시성 변화·경로 이동 시 즉시 재조회)한다.

## 이번에 하지 않은 것

거절·채팅 종료·7일 경과·교환 완료 알림은 만들지 않았다. 요구사항 문서의 알림 3종 범위와 열린 질문은 [후속요구사항 문서](../../산출물/04_요구사항정의서/후속요구사항_제안알림_교환됨_공연정보입력.md) 참고.
