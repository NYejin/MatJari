# 공연 포스터 표시 설계 근거

공연 포스터 표시(`GET /api/performances/{id}/poster`, 미리보기 응답의 `posterUrl`, 프런트 `PosterImage`)의 근거를 정리한다(브랜치 `feature/poster`, 2026-10-13 구현, DB 변경 없음). 확정 규칙의 기준은 [CLAUDE.md](../../CLAUDE.md)의 '공연 포스터 표시' 절이다. 이 페이지는 **왜 이렇게 했나**와 **아직 확인하지 못한 것**을 적는다. 구현 세부는 백엔드 README '공연 포스터 표시' 절과 프런트 README에 있다.

사용자 지시(2026-10-12)는 두 가지였다. 포스터를 공연 정보 오른쪽에 띄울 것, 저작권 판단은 메인이 법률 정보를 찾아 정할 것. 아래 1절이 메인이 정한 것이다. 법률 자문이 아니다.

## 1. 정해진 것

- 서버는 포스터 이미지를 **저장·복제·프록시하지 않는다.** 링크 페이지의 `og:image`(없으면 JSON-LD `Event.image`의 첫 값)에서 **이미지 주소 문자열만** 읽는다.
- 브라우저가 원 사이트의 이미지 주소를 직접 불러온다(인라인 링크). 서버가 이미지를 요청하지 않으므로 이미지 쪽 SSRF 면이 없다.
- 주소는 사이트별로 고정된 허용 호스트와 https만 인정한다. 그 밖이면 포스터 없음으로 처리한다.
- DB에 주소를 저장하지 않는다. 미리보기를 다시 불러 10분 캐시로 얻는다.
- 출처는 텍스트로만 표기하고 새 링크는 두지 않는다. 공연 상세에 원래 있던 티켓팅 링크만 남는다.
- 로드 실패(핫링크 차단 포함)나 주소가 없으면 포스터 영역 전체를 숨긴다. 대체 링크는 두지 않는다(사용자 지시 2026-10-12). 차단을 우회하지 않는다.
- 설정 스위치 `matjari.poster.enabled`(기본 true)를 둔다. 사이트에서 중단을 요청하면 즉시 끈다.

## 2. 대안 비교

| 안 | 내용 | 결과 |
|---|---|---|
| A | 서버가 이미지를 내려받아 저장(디스크·DB)한 뒤 우리 주소로 제공 | 이미지를 복제·전송하는 주체가 서비스가 되어 저작권 쟁점이 직접 생긴다. 보관 기간도 생긴다. 기각 |
| B | 서버 프록시(이미지를 중계하는 엔드포인트) | 서버가 이미지를 전송한다는 점은 A와 같다. 사용자가 준 URL을 서버가 요청하게 되어 이미지 SSRF 면이 생긴다. 기각 |
| C | 인라인 링크: 주소만 읽고 브라우저가 원 사이트에서 직접 불러온다 | **채택.** 서버가 이미지를 받지 않으므로 SSRF 면이 없다. 대신 저작권 판단이 미확인 상태로 남는다(3절) |
| D | 텍스트 링크만 두고 포스터는 표시하지 않는다 | 조사 연구자의 보수적 권고였고 인라인이 차선이었다. 사용자가 포스터 표시를 지시했으므로 기본안에서는 기각. 스위치를 끄면 이 상태가 된다 |
| E | 이미지 주소를 `performance` 테이블에 컬럼으로 저장 | 링크가 바뀌거나 만료되면 깨진다. 저장된 주소는 공연이 이용되는 동안 계속 남는다. 기각. 미리보기 재조회와 10분 캐시로 대체 |

## 3. 저작권 조사 요약 (법률 자문 아님)

- 조사 보고(researcher, 2026-10-12)의 요약이다. 단순 링크는 복제·전송이 아니라는 판례 방향이 일관된다고 했다. 인용한 판례 번호는 대법원 2009다76256, 2012도13748, 2017도19025다. 조사 보고의 요약을 옮긴 것이고 원문은 대조하지 않았다. 출처 URL과 접근일은 기록하지 않았다.
- 이미지를 내 화면에 직접 보이게 하는 **인라인(임베디드) 링크**는 확정 판례가 없고 학설상 쟁점이다.
- 미확인: 포스터 자체의 저작물성, 티켓 3사(YES24·티켓링크·멜론) 이용약관 본문.
- 조사 보고의 권고는 '표시 안 함 + 텍스트 링크', 차선은 '인라인 링크'였다. 메인은 사용자 지시에 따라 인라인을 택하고, 위험은 한계로 기록하며 스위치를 둔다.
- 따라서 이 기능은 공개 운영 전에 약관과 저작권을 확인해야 한다. 확인 질문은 요구사항 문서 §7 Q-26이다.

## 4. 허용 호스트와 자리표시

- 허용 목록은 2026-10-13 실측으로 사이트별 고정했다. YES24 `tkfile.yes24.com`, 티켓링크 `image.toast.com`, 멜론 `cdnticket.melon.co.kr`.
- 호스트를 고정하는 이유: 주소 문자열을 받아 그대로 `<img>`에 넣으므로, 허용 목록이 없으면 임의의 외부 주소가 화면에 나온다. 사이트별로 묶어 다른 사이트의 허용 호스트도 거부한다. 프런트 `PosterImage`도 같은 목록으로 한 번 더 검증한다(방어용 이중 확인).
- 자리표시: YES24는 포스터가 없을 때 og:image로 `_noimage.gif`를 준다. 그 주소의 호스트는 허용 목록에 있어서 호스트 검사만으로는 걸러지지 않는다. 그래서 경로에 `noimage`가 든 주소를 거부한다. 자세한 재현 조건은 [링크 가져오기 함정](../gotchas/link-fetch-pitfalls.md) 3절에 있다.
- 주소 규칙: https만(`//`는 https로 보정), userinfo·비표준 포트·공백·제어 문자·비ASCII 문자·2048자 초과 거부.

## 5. 실패 처리와 우회를 하지 않는 이유

- 로드 실패(핫링크 차단 포함)나 주소 없음이면 포스터 영역(캡션 포함)을 숨긴다. 원래 있던 티켓팅 링크만 남는다.
- 차단을 우회하지 않는다. Referer 위조와 서버 대리 다운로드는 원 사이트가 막은 접근을 뚫는 행위이며, 서버가 다시 이미지를 전송하게 만든다.
- `referrerpolicy="no-referrer"`로 우리 페이지 주소를 원 사이트에 보내지 않는다.
- 출처 캡션은 "포스터 이미지 출처: {YES24|티켓링크|멜론티켓} · 저작권은 원 권리자에게 있어요"이며 텍스트만이다.
- 삭제·표시 중단 요청은 개인정보처리방침의 문의처로 받는다. 방침 문구는 아직 넣지 않았다.

## 6. 속도 제한과 스위치

- 상세 화면용 조회는 미리보기와 같은 캐시(10분)·사이트 분당 30회·동시 4개를 쓴다. 사용자 제한은 별도로 분당 `matjari.poster.user-per-minute`(기본 60)이다.
- 제한에 걸리면 429가 아니라 조용히 null을 준다. 포스터는 부가 정보이므로 공연 정보 화면을 막지 않는다.
- 스위치 `matjari.poster.enabled`(기본 true, 환경변수 `MATJARI_POSTER_ENABLED`)가 false면 포스터 주소를 요청하지도 응답하지도 않는다.

## 7. 알려진 한계

1. 인라인 링크의 저작권 판단에 확정 판례가 없고, 포스터 저작물성과 티켓 3사 이용약관은 확인하지 못했다. 공개 운영 전 약관 확인과 전문가 검토가 필요하다. 요청이 오면 스위치를 끈다.
2. 허용 호스트는 2026-10-13 실측 기준이다. 사이트가 CDN을 바꾸면 포스터가 안 뜬다. 화면은 숨김으로 처리되어 깨지지 않는다.
3. YES24는 포스터가 없는 공연이 많다.
4. 인터파크는 robots.txt 때문에 지원하지 않는다.
5. 사이트가 핫링크를 막으면 포스터는 보이지 않는다.
6. 삭제·표시 중단 요청은 방침 문의처로 받는데, 방침에는 아직 관련 문구가 없다.

## 8. 열린 질문

- 요구사항 문서 §7 Q-26 하나다: 티켓 3사 이용약관과 인라인 링크 저작권을 확인하고 전문가 검토를 받을지. 법률 판단은 이 위키의 몫이 아니다.
