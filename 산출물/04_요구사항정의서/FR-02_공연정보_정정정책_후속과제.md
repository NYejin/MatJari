## 0. 2026-10-07 부분 결정

> **정정 (2026-10-07 방향 전환)**: 좌석표 트랙 동결로 아래 '관리자 정식 등록·수정 로그' 방향은 **백로그**로 미뤘다(사용자가 다시 지시하기 전에는 시작하지 않음). 관련 코드는 삭제되어 git 태그 `archive/seatmap-track-20261007`에 보관되어 있다. **(2026-10-08 5차 답변으로 현재 규칙 정정)** 공연은 등록 후 **아무도 수정·삭제할 수 없고** 회차 추가·수정·삭제도 없다. 변경은 관리자 페이지의 '수정 제안'(제목·공연장만, 관리자 승인 시에만 반영)으로만 하며 구현됨(2026-10-12, V12). 아래 서술 중 '등록자 수정·삭제' 내용은 과거 규칙이다. 아래 분석과 선택지는 보존한다.

CLAUDE.md의 "좌석표 등록 흐름" 결정으로 방향이 정해졌다. 아래 4절의 선택지 중 B(관리자)가 중심이 되고, 로그를 더한다.

- 공연장·공연은 **관리자가 정식 등록**한다. 정식 등록 전 사용자 입력은 `DRAFT` 상태로 보며, 정식 등록되면 `OFFICIAL`이 된다. 관리자는 DB에서 ADMIN 역할을 직접 부여하는 방식으로 시작한다.
- 모든 수정은 **수정 로그**(누가·언제·전후 값)로 남긴다.
- 악의적 수정은 **사용자 신고나 관리자 확인이 있을 때에만 제재**한다. 자동 제재는 없다.
- OFFICIAL 좌석표의 정정은 같은 정정 2건 이상이면 자동 반영, 1건이면 검토 대기 (A안의 규칙을 좌석표에 한해 채택).
- 링크 자동 입력은 제목·공연장·날짜 범위만 채우고 사용자가 확인 후 등록하므로, 허위 정보는 위 정식 등록·수정 로그로 대응한다.
- **아직 미정**: 공연 제목·공연장·회차 시각의 정정을 누가 어떤 화면에서 하는지, 등록자 수정 권한을 정식 등록 후 어떻게 제한하는지, 회차 스팸·공연장 중복 정리, 예매처별로 갈라진 공연 합치기, 신고 엔티티 설계(`db-schema-architect` 경유).

## 1. 문제 (과거 규칙 기준, 2026-10-08 이전 서술)

> 아래 1~2절은 등록자 수정·삭제가 가능하던 시절의 분석이다. 현재는 공연을 아무도 수정·삭제할 수 없고 변경은 관리자 '수정 제안'으로만 하며 구현됨(2026-10-12, V12). 공연장 테이블은 없고 공연장은 `performance.venue_name` 텍스트다.

공연은 먼저 등록한 사람(등록자)만 제목·공연장을 고칠 수 있고, 티켓팅 링크(`sourceUrl`)는 아무도 바꿀 수 없다.
같은 링크로 다시 등록하면 409와 함께 기존 공연으로 안내된다. 따라서 **처음 등록할 때 제목·공연장·회차가 틀리게 입력되면
다른 사용자가 바로잡을 방법이 없다.** 오타뿐 아니라 일부러 잘못 등록해 공연을 선점하는 경우도 같은 결과다.

## 2. 과거 동작 (2026-10-08 이전, 폐기된 규칙)

| 대상 | 추가 | 수정 | 삭제 |
|---|---|---|---|
| 공연 | 로그인 사용자 누구나 | 등록자만 (공연장 변경은 소속 회차에 티켓이 없을 때만) | 등록자만, 티켓이 없을 때만 |
| 회차 | 로그인 사용자 누구나 | 공연 등록자만, 그 회차에 티켓이 없을 때만 | 공연 등록자만, 그 회차에 티켓이 없을 때만 |
| 공연장 | 로그인 사용자 누구나 | 불가 | 불가 |

- (과거 규칙, 2026-10-08 폐기) 등록자가 잘못 등록했다면 직접 수정하거나, 티켓이 없을 때는 삭제 후 재등록할 수 있었다. 현재는 아무도 수정·삭제할 수 없고 관리자 수정 제안으로만 바꾼다.
- 등록자가 아닌 사용자가 잘못된 정보를 발견했을 때의 수단은 없다.

## 3. 같이 정리해야 할 관련 문제

- **회차 스팸**: 회차는 누구나 추가할 수 있는데 공연당 개수 상한이 없고, 추가한 본인은 삭제할 수 없다. 정리는 공연 등록자만 할 수 있다.
- **공연장 무제한 생성**: 누구나 만들 수 있고 삭제·수정이 불가능하다. 이름만 다른 중복 공연장이 쌓이면 좌석맵(공연장 단위 재사용)이 갈라진다.
- **같은 공연이 예매처별로 갈라짐**: 공연 중복을 링크 기준으로 판정하므로, 같은 공연이 여러 예매처에서 팔리면 공연이 둘로 등록되어
  서로 티켓을 교환할 수 없다. "같은 공연장 + 비슷한 제목" 안내는 아직 구현하지 않았다 (`Performance` 주석에만 있음).
- **링크 자동 입력 도입 시**: 사용자가 확인한 뒤 등록하더라도 허위·악의적 수정은 막지 못한다.
  CLAUDE.md의 "링크 기반 공연정보 자동 입력" 결정에서도 방지책을 추후 결정으로 남겨 두었다.

## 4. 선택지

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 정정 신고 2건 자동 반영 | 좌석맵 오류 보정과 같은 방식. 같은 정정 내용이 2건 이상이면 자동 반영, 1건이면 검토 대기 | 프로젝트 원칙과 일관됨, 관리자 불필요 | 신고 엔티티·판정 로직 추가(스키마 변경), 신규 계정 여러 개로 악용 가능 |
| B. 관리자 정정 | 관리자 역할(ADMIN)과 정정 화면·API 추가 | 판단이 확실함 | 역할·권한·화면 작업이 큼, 운영자가 계속 필요 |
| C. 정정 요청 후 등록자 승인 | 다른 사용자가 정정을 제안하고 등록자가 수락 | 구현이 비교적 단순 | 등록자가 응답하지 않거나 악의적이면 해결되지 않음 |
| D. 보류 (현재) | 지금 상태 유지 | 작업 없음 | 위 문제가 그대로 남음 |

## 5. 결정 시 고려할 점

- 정정 대상 필드: 제목, 공연장, 회차 시각 (링크는 불변 유지 권장).
- 티켓이 붙은 회차·공연은 지금처럼 변경을 막는 규칙을 유지한다 (교환 중인 좌석의 기준이 바뀌면 안 됨).
- 신고·정정 기록은 새 엔티티가 필요하므로 `db-schema-architect`를 먼저 거치고 erd-conventions 기준선을 갱신한다.
- 악용 방지: 같은 사용자의 중복 신고, 신규 가입 직후 계정, 등록자 본인 신고 처리.
- 정정이 반영되면 영향을 받는 사용자(등록자·해당 공연 티켓 보유자) 알림이 필요한지.
