# SeatSwap 작업일지

## 2026-10-12

## 링크 기반 공연정보 자동 입력 (브랜치 `feature/link-autofill`, master `1b666ed` 위, 병합 전)

### 실측 (2026-10-12)
- 세 사이트의 공개 페이지 raw HTML을 직접 받아 구조를 확인했다. YES24와 티켓링크는 JSON-LD `Event`, 멜론은 JSON-LD·og:title이 없고 본문 HTML에서 읽는다.
- 실제 3개 페이지에 파서를 돌려 제목·공연장·기간이 맞게 나오는 것을 확인했다. 공연장이 비어 있는 상품(멜론·티켓링크 일부)도 확인했다.
- 회차 시각은 세 사이트 모두 공개 HTML에 없고 Ajax(예매 달력)로만 온다는 것을 확인했다.
- robots.txt: ticket.yes24.com·ticket.melon.com은 규칙 대신 오류 페이지를 돌려줘 규칙이 없는 것으로 해석했다. 티켓링크는 상품 상세를 허용하고 예매·내 정보·검색 경로를 금지한다. 인터파크는 금지라 제외했다.

### 결정
- 회차는 자동으로 채우지 않는다. 기간이 있으면 회차 입력 근처에 기간 안내만 한다. 요구사항의 '제목·공연장·회차' 중 회차는 자동 입력 대상에서 빠진다. Ajax를 읽는 것은 CLAUDE.md의 '내부 API 조사는 하지 않는다' 규칙에 걸리므로 하지 않는다.
- 자동 등록은 하지 않는다. 미리 채우기 후 사용자 확인, 직접 입력은 항상 가능하다.
- 대상은 YES24·티켓링크·멜론이다. 인터파크는 제외한다.
- SSRF 방어: 사용자가 준 URL은 요청하지 않고, 고정 템플릿 3종으로만 URL을 만든다.

### 구현
- 백엔드: `GET /api/performances/preview?sourceUrl=`(로그인 필요). `service/linkinfo/PageFetcher`·`LinkInfoParsers`·`PerformancePreviewService`, `dto/response/PerformancePreviewResponse`, `PerformanceController`에 `/preview`, `GlobalExceptionHandler`에 429 핸들러, 설정 `seatswap.linkinfo.*`. 의존성 `org.jsoup:jsoup:1.18.3` 추가.
- 응답은 200 항상 `{status, site, title, venueName, periodStart, periodEnd}`. 링크 형식 오류는 400, 사용자당 분당 10회 초과는 429 `PREVIEW_RATE_LIMITED`.
- 사이트별 분당 30회·동시 실행 4개를 넘으면 즉시 FETCH_FAILED. 결과 캐시는 10분·최대 200개이며 OK·NO_INFO만 저장한다.
- 프론트: 등록 1단계의 중복 확인이 미등록이면 preview를 이어서 호출한다(15초 제한, 실패가 등록을 막지 않음). 2단계에 제목·공연장을 채우고 확인 안내를 보인다. 같은 링크는 다시 부르지 않는다. 회차 근처에 기간 안내를 보인다.
- DB 변경 없음. 마이그레이션 번호는 그대로 V12부터이며, V12는 차단(`user_block`)용이다.

### 검증
- 백엔드 기본 모드 632건 통과, 실패 0, MySQL IT 141건 건너뜀. 신규 32건(파서 10, PageFetcher 9, 서비스 8, 컨트롤러 슬라이스 5). 외부 인터넷 접속 테스트는 만들지 않았고, 파서는 실측 구조를 줄인 fixture로 검증했다.
- 프론트 `tsc`·빌드 통과.
- 위 수치는 작업 세션의 보고값이다. 이 기록을 쓸 때 같은 수치를 재실행해 확인하지는 않았다.

### 알려진 한계
- 사이트 HTML이 바뀌면 NO_INFO가 된다(어댑터 취약성).
- 속도 제한·캐시·세마포어는 단일 인스턴스 메모리다.
- 검증한 IP로 연결을 고정(pinning)하지 않는다. 대상이 코드에 고정된 공개 도메인 3개라는 전제에 기댄다.
- 회차 시각은 읽지 못한다.
- 티켓링크·멜론 상품 페이지는 공연장이 비어 있을 수 있다.
- 브라우저 수동 점검은 하지 않았다.

## 관리자 페이지 (브랜치 `feature/admin`, master `17ddd0c` 위, 병합 전)

### 결정
- 관리자가 처리하는 대상은 두 가지다. ① 공연 수정 제안(수정 대상은 **제목·공연장만**, 회차·링크 제외) ② 내 티켓 인증(좌석 소유 인증 요청, 예매내역 사진 1장).
- 공연 수정 제안은 관리자 승인으로만 공연에 반영된다(이전 값 스냅샷). 등록 후 공연을 바꾸는 유일한 경로다.
- 내 티켓 인증의 승인은 **현재 그 좌석의 활성 티켓을 시스템이 내리는 것**이다. 요청자는 이후 일반 티켓 등록으로 직접 등록한다(자동 등록 없음).
- 사진은 승인·거절 뒤 커밋 뒤에 파일을 지우고 처리 시각만 남긴다(개인정보 최소화). 웹에서 직접 서빙하지 않는다.
- 알림은 만들지 않는다. 결과는 제안자·요청자가 `/my/edit-proposals`, `/my/seat-claims`에서 본다.
- 신고 처리용 관리자 기능(요구사항 Q-21)은 이번 범위가 아니다. 관리자 권한은 기존대로 DB에서 `users.role = 'ADMIN'`을 직접 부여한다.

### 구현
- 커밋(`feature/admin`): e608c5a(V12 스키마), 96a5623(프론트: 관리자 가드·관리자 목록 화면·내 요청 목록), 6c04c08(수정 제안 백엔드), 04fecf7(좌석 인증 백엔드).
- 백엔드: `V12__admin_edit_proposal_seat_claim.sql`(테이블 16개), 엔티티 `PerformanceEditProposal`·`SeatClaim`, 컨트롤러 `PerformanceEditProposalController`·`AdminPerformanceEditProposalController`·`SeatClaimController`·`AdminSeatClaimController`, 사진 저장소 `SeatClaimImageStore`(서버 디스크, `seatswap.upload.dir`). `TicketService.deactivateLocked`를 추출했다(기존 동작 불변).
- 프론트: `AdminRoute`(ADMIN만), `/admin`(대시보드), `/admin/performance-edit-proposals`, `/admin/seat-claims`, `/my/edit-proposals`, `/my/seat-claims`, `/seat-claims/new`, 공연 상세 수정 제안 폼, 헤더 '관리자' 링크(ADMIN만).

### 설계 메모 (잠금·인덱스)
- 'PENDING은 1건' 유니크는 생성 컬럼(PENDING일 때만 사용자 id) + UNIQUE로 강제했다. 처리되면 NULL이 되어 다시 제안·요청할 수 있다. FK 인덱스는 단일 컬럼이고 갱신 컬럼을 섞지 않는다(CLAUDE.md 개발 규칙).
- 좌석 키 보조 유니크 인덱스로 티켓에 FOR UPDATE를 걸면 PK부터 잠그는 `deactivate`와 교착이 난다. 그래서 티켓 id를 잠금 없이 읽고 PK로 잠근 뒤 상태를 다시 판단한다.
- 잠금 순서: 수정 제안은 제안 행 → 공연 행, 좌석 인증 승인은 인증 요청 행 → 티켓 id↑ → 요청 id↑ → 매칭.

### 검증
- 백엔드 전체(임시 MySQL IT 포함) 708건 통과, 실패 0, skip 0. V12 스키마 `AdminSchemaMysqlTest` 6건, 수정 제안 24건(동시 승인 10라운드×8스레드에서 1건만 성공 등), 좌석 인증 31건(동시 승인·거절, 승인+소유자 내리기+제3자 제안+예약 혼합 경합에서 교착 0 등).
- 프론트 `tsc`·빌드 통과. 브라우저 점검은 하지 않았다.
- 위 수치는 작업 세션의 보고값이다. 이 기록을 쓸 때 같은 수치를 재실행해 확인하지는 않았다.

### 알려진 한계
- 커밋 뒤 사진 삭제가 실패하거나 서버가 종료되면 고아 파일이 남는다(정리 스케줄러 없음).
- 관리자 좌석 인증 목록의 holder 조회는 N+1이다(최대 100건).
- 관리자가 자기 제안·자기 인증 요청을 승인하는 것은 409 `SELF_REVIEW`로 막는다(거절은 허용). 승인 시점에 좌석을 요청자 본인이 가졌다면 본인 티켓은 내리지 않고 승인만 완료한다(resolved 없음). 승인 트랜잭션은 READ COMMITTED로 돌려 예약 잠금 검사가 낡은 스냅샷을 읽지 않게 한다(검증에서 발견한 TOCTOU).
- 이미지 저장소는 서버 로컬 디스크라 다중 인스턴스에서는 쓸 수 없다. 사진의 EXIF는 제거하지 않는다(처리 후 삭제로 대응).
- 프론트는 사용자 role을 프로필 조회 뒤에 판단하므로 로딩 중 잠깐 '권한을 확인하는 중'이 보인다.
