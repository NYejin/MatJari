# 차단·신고·이용 정지 설계 근거

차단·신고·관리자 신고 처리·이용 정지(V13, 브랜치 `feature/block-report`, 2026-10-12 구현, 병합됨)의 근거만 정리한다. 확정 규칙은 [CLAUDE.md](../../CLAUDE.md)(알림·차단·신고·관리자 절)가 기준이고, 여기서 새 결정을 만들지 않는다. 이 작업으로 사용자가 정한 6개 기능이 모두 구현됐다. 용어는 [용어집](../glossary.md).

## 1. 차단: 방향은 하나, 효과는 양방향

- 저장은 blocker→blocked 한 방향이지만 후보 제외·새 제안 불가·열린 매칭 취소는 둘 중 누가 차단했든 똑같이 적용한다. 한쪽만 막으면 차단당한 쪽 후보에는 계속 상대가 보이거나 제안이 들어가 차단의 의미가 없어서다.
- 상대에게 알리지 않는다. 후보에서 조용히 사라지고, 열린 매칭은 기존 시스템 취소(`canceled_by_id` NULL)와 같은 표시다. 차단 사실이 드러나는 문구를 만들지 않았다.
- 재매칭 불가는 차단 때만이라는 기존 규칙([CLAUDE.md](../../CLAUDE.md) 제안·취소 절)을 그대로 구현했다. 신고만으로는 자동 차단하지 않는다. COMPLETED 매칭과 교환 이력은 건드리지 않는다.
- 차단 해제해도 취소된 매칭은 되살리지 않는다(다시 제안은 가능).

## 2. 신고: 자동 제재 없음

- 신고는 접수만 하고 자동 제재·자동 차단·대상 통지가 없다. 처리는 관리자가 한다(RESOLVED 또는 DISMISSED). 신고자에게는 처리 상태만 보이고 메모·제재 내용은 숨긴다.
- 채팅 근거: 신고된 매칭의 채팅을 관리자만 열람한다. 메시지 무기한 보관 규칙([채팅 설계](chat-design.md))과 이어지며, 화면에 처리 목적 외 사용 금지 안내를 둔다.

## 3. Q-21 확정

CLAUDE.md에는 "신고 처리용 최소 관리자 기능의 범위"가 열린 질문이었다. 사용자의 요청("차단/신고를 만들고 동시에 관리할 수 있는 관리자 기능도 같이")으로 **신고 목록·상세(채팅 근거)·처리, 이용 정지, 차단 현황 조회(읽기 전용)** 까지로 정해졌다. 기존 관리자 페이지의 범위 해석은 [관리자 설계](admin-design.md) 참고. 정리 전 요구사항 문서 쪽 Q 번호 갱신 여부는 이 입력에서 확인하지 못했다.

## 4. 정지 강제를 `loadUserById` 한 곳에서 한 이유

- 모든 인증 요청은 JWT 필터에서 `CustomUserDetailsService.loadUserById`를 거쳐 요청마다 DB를 1회 조회한다. 여기서 활성 제재를 확인하면(`AccountSuspensionChecker`) 컨트롤러별 검사 누락 없이 모든 인증 API가 403 `ACCOUNT_SUSPENDED`로 막힌다. 로그인(비밀번호가 맞은 뒤에만 검사)·토큰 재발급·STOMP CONNECT도 같은 경로로 막는다.
- 로그아웃은 정지 중에도 가능해야 해서 `/api/auth/logout`(무동작 204)을 새로 두었다.
- 비용은 요청마다 활성 제재 조회 1회가 더해지는 것이다(`idx_user_sanction_user` 사용). 캐시는 두지 않았다. 정지 반영이 즉시여야 해서이며, 성능 수치는 확인하지 못했다.
- **STOMP**: CONNECT 때 정지를 검사하고, 이용 정지를 걸면 커밋 뒤 대상의 열려 있는 STOMP 연결을 모두 닫는다(`closeAllOf`, 1008; 검증에서 지적된 강제력 공백을 닫음). 차단은 연결을 닫지 않고 열린 매칭 취소로 쓰기·푸시를 막는다.

## 5. 열린 매칭 시스템 취소 설계

`OpenMatchCanceller`(`cancelBetween`/`cancelAllOf`, MANDATORY 트랜잭션)는 차단과 정지가 공유하는 계약이다. 잠금 순서와 함정은 [함정 12절](../gotchas/lock-order-and-index-pitfalls.md)에 있다.

- 대상 매칭 id를 잠금 없이 읽고, 관련 티켓 id 오름차순 → 매칭 id 오름차순 `FOR UPDATE`, 상태 재확인 뒤 CANCELED와 잠금 삭제. 기존 규약(티켓→요청→매칭, [함정 1절](../gotchas/lock-order-and-index-pitfalls.md))을 지키되 요청 상태는 건드리지 않아 요청 잠금은 생략했다.
- 호출 트랜잭션은 READ_COMMITTED다. 티켓 잠금 뒤에 매칭 목록을 다시 읽어야 최신을 보기 때문이다. 호출 전에 `ExchangeMatch` 엔티티를 로드하지 않는다(영속성 컨텍스트에 낡은 상태가 남는 것을 피함).

## 6. 택하지 않은 대안

- **임의 userId 차단 API**: 아무 사용자 id나 차단할 수 있으면 id 열거·스토킹성 악용 여지가 생긴다. 채팅 화면에서 매칭을 통해서만 상대가 정해지게 했다. 이 선택의 단점은 매칭 없이는 미리 차단할 수 없다는 점이다.
- **신고 자동 제재**(건수 임계치 등): 허위 신고로 정상 사용자가 정지될 수 있어 관리자 판단을 거치게 했다.
- **users 테이블 `status` 컬럼**: 기간 만료·해제 이력·사유·처리자를 담기 어렵고 users 행 갱신이 잠금 순서(users는 티켓 뒤)에 얽힌다. 별도 `user_sanction` 행과 조회 시 판단을 택했다.
- **스케줄러로 정지 해제**: 만료를 조회 시 `ends_at > now`로 판단하면 스케줄러·누락 해제·시각 오차가 없다. 해제 이력은 `revoked_at`으로 남긴다.

## 7. 한계

- 차단은 STOMP 연결을 닫지 않는다(4절). 이용 정지만 커밋 뒤 닫는다.
- 차단 상한 200·신고 상한 10은 해당 쪽에서 사용자 행을 잠그지 않아 동시 요청 시 근소 초과가 가능하다.
- 같은 대상을 동시에 제재하면 한쪽이 교착으로 503(BUSY)이 날 수 있다. 중복 제재는 생기지 않는다.
- 채팅 DTO의 상대 숫자 id(`senderId`) 노출은 그대로다.
- `OpenMatchCanceller` 주입은 `ObjectProvider`를 쓴다(순환 의존 회피 목적으로 추정, 확인하지 못함).
- 브라우저 수동 점검은 하지 않았다(`tsc`·빌드·백엔드 테스트 781건 통과는 구현 세션 기록이며 이 위키에서 재실행하지 않았다).
- 남은 것: 7일 경과 알림(보류, 2026-10-13 사용자 결정), 브라우저 점검. `trust_score` 컬럼 정리는 2026-10-13 V18(`feature/remove-trust-score`, 미커밋)로 끝냈다.
