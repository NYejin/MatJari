## 공연 수정 제안에 회차 수정 + 연속 기간 날짜 전체 자동 입력 (브랜치 `feature/session-edit-proposal`, V20)

### 사용자 요청
- 공연 수정 제안에 **회차 정보 수정**을 넣는다(지금까지는 제목·공연장만 제안 가능).
- 공연 기간이 연속이면 **첫날부터 끝날까지 모든 날짜**를 회차 입력에 자동으로 채울 수 있게 한다(그전에는 2일 이하만).
- 질문 없이 알아서 설계·구현·테스트까지 진행하고, 두 요청은 PR 답변 한 번으로 정리한다.

### 설계 결정(사용자에게 묻지 않고 정함)
- 회차 변경은 `ADD`(추가)·`CHANGE`(시각 변경)·`REMOVE`(삭제) 세 종류이고 제안 한 건에 최대 20개. 제목·공연장 없이 회차만 제안해도 된다.
- 저장은 `performance_edit_proposal.session_changes`(JSON) 한 컬럼이다. 자식 테이블을 만들지 않은 이유: 처리된 제안이 감사 기록으로 남아야 하는데 회차가 나중에 삭제될 수 있어 FK를 걸 수 없고, 변경 목록은 제안과 함께만 읽힌다. V20이 컬럼을 추가하고 `ck_performance_edit_proposal_change` CHECK를 '제목·공연장·회차 변경 중 하나 이상'으로 고쳤다(공백 규칙은 그대로).
- 삭제는 티켓·교환 희망 회차·좌석 인증 요청이 걸리지 않은 회차만 허용한다(FK 때문에 어차피 지울 수 없고, 사용자 데이터가 사라지는 일을 막는다). 시각 변경은 회차 id를 그대로 두어 티켓·희망 조건을 유지한다.
- 검사는 제안을 만들 때와 관리자가 승인할 때 같은 함수로 한다. 시각 맞바꾸기(A→B 시각, B→A 시각)는 unique 제약 때문에 중간 상태가 깨지므로 거부하고 하나씩 나눠 제안하게 한다. 승인 때 상태가 달라졌으면 409 `SESSION_EDIT_CONFLICT`로 막고 제안은 PENDING으로 남겨 거절하게 한다.
- 날짜 후보 상한은 공연 등록 한 번의 회차 상한(100)과 맞춘 100일로 정했다. 100일을 넘는 기간은 후보를 만들지 않는다.

### 구현
- 백엔드: `V20__edit_proposal_session_changes.sql`, `PerformanceEditProposal.sessionChanges`(+`SessionChange` 레코드), `PerformanceEditProposalService`(파싱·검증·승인 반영), `PerformanceSession.changeStartsAt`, `PerformanceSessionRepository.findInUseIds`, DTO(`SessionChangeRequest`·`SessionChangeView`), `PerformancePreviewResponse.MAX_PERIOD_DAYS_FOR_CANDIDATES`=100.
- 프런트(서브에이전트 2개, 각자 worktree): 공연 상세 제안 폼의 `SessionEditor`(회차별 시각 입력·삭제 토글·추가 줄·사전 검사), `SessionChangesView`(관리자·내 제안 화면의 변경 블록), 공연 등록 2단계의 '기간 전체 채우기'·'시각 한번에 넣기'.

### 검증
- 백엔드: 실제 MySQL 통합 테스트에 회차 변경 7건 추가(추가·변경·삭제 승인 반영과 기존 시각 기록, 제목+회차 동시, 입력 검증 12종, 변경 없음, 사용 중 회차 422, 승인 사이 충돌 409, 관리자 목록 표시), 컨트롤러 슬라이스 2건, 날짜 후보 경계(7일·100일·101일) 단위 테스트. 전체 테스트 결과는 PR 본문에 적는다.
- 브라우저(로컬 jar + vite + Playwright): 제안자가 회차 변경·삭제·추가를 제안 → 내 제안 화면 표시 → 관리자 화면 표시·승인 → 회차 목록 반영, 승인 뒤에도 기존 시각 표시. 10일짜리 기간 응답으로 '기간 전체 채우기' 10줄·'시각 한번에 넣기'.

### 알려진 한계
- 하루에 여러 회차(낮·밤)는 날짜 후보가 날짜당 하나라 같은 날짜를 줄로 직접 추가해야 한다. 공연 기간 안에 쉬는 날이 있으면 줄을 삭제해야 한다.
- 회차 시각을 서로 맞바꾸는 제안은 한 번에 못 하고 두 번에 나눠 해야 한다.

## CI/CD (브랜치 `feature/ci-cd`)

사용자 질문: 집 PC로 서버를 돌려도 GitHub Actions로 자동 CI/CD가 가능한가. 저장소는 public이다. 알아서 구성하라고 해서 질문 없이 만들었다.

### 결정
- CI는 GitHub 서버, CD는 내 PC의 self-hosted runner(PC가 먼저 GitHub에 접속하므로 포트 개방이 필요 없다).
- public 저장소에서 self-hosted runner는 외부 PR 코드가 내 PC에서 실행될 위험이 있어, 배포 워크플로는 `pull_request`로 돌지 않고 `workflow_run`(master 푸시의 CI가 성공했을 때만)으로 돌게 했다. 사용자가 해야 하는 설정(포크 PR 승인 요구, 브랜치 보호)은 README에 적었다.
- 배포는 개발 작업 폴더가 아니라 **배포 전용 clone**에서 한다(작업 중인 브랜치를 건드리지 않고, 추적 파일 수정이 없어 pull이 안전하다). compose 프로젝트 이름이 고정이라 같은 컨테이너·볼륨을 쓴다.
- 배포 범위는 backend·web 재빌드만. DB·터널·`.env`는 건드리지 않는다.

### 구현
`.github/workflows/ci.yml`, `.github/workflows/deploy.yml`, `MatJari/deploy/deploy.ps1`(`-DryRun` 지원, pull → compose up → 응답 확인), `MatJari/README.md` '자동 배포(CI/CD)' 절.

### 검증
- 워크플로 YAML 구문 확인, `deploy.ps1 -DryRun` 실행 확인. 실제 배포는 운영 중인 서버를 바꾸므로 실행하지 않았다.
- CI와 같은 조건(깨끗한 체크아웃, Linux 컨테이너, 최대 연결 수를 올린 임시 MySQL)으로 백엔드 전체 테스트를 시뮬레이션했다(결과는 PR 본문). GitHub 서버에서 실제로 도는 것은 첫 PR에서 확인해야 한다.
- 알려진 한계: runner 설치와 Actions 변수 설정은 사용자가 GitHub 화면에서 직접 해야 하고, 이 환경에서는 GitHub Actions를 실행해 볼 수 없다.

## 이미지 방식 배포로 교체 (브랜치 `feature/image-deploy`)

사용자가 runner 방식의 GitHub 경고(public 저장소에서 self-hosted runner 비권장)를 보고 이미지 방식(B)을 택했다.

### 결정
- CI(GitHub 서버)가 master 푸시에서 테스트 통과 후에만 이미지 2개를 ghcr.io에 올린다(`latest`, `sha-xxxxxxx`). PR·포크 실행에서는 `publish`가 돌지 않아 이미지를 올릴 수 없다. 패키지 쓰기 권한은 이 job에만 준다.
- 집 PC는 GitHub 코드를 실행하지 않는다. 스케줄러가 5분마다 `update.ps1`로 pull → 바뀐 컨테이너만 교체. 이미지가 같으면 재시작하지 않으므로 자주 돌려도 안전하다.
- 운영 compose는 `build:` 대신 `image:`(`IMAGE_PREFIX`·`IMAGE_TAG`)를 쓰고, 소스 빌드는 `docker-compose.build.yml` 덧붙이기로 남겼다. 되돌리기는 `IMAGE_TAG`를 이전 sha 태그로 고정한다.
- 개인정보처리방침 값(`VITE_PRIVACY_*`)은 화면 번들에 굳으므로 CI의 Actions 변수로 받아 이미지를 만들 때 넣는다.

### 구현
`ci.yml`에 `publish` job, `deploy.yml` 삭제, `MatJari/deploy/update.ps1`(pull·교체·응답 확인·로그·동시 실행 방지·`-DryRun`), `register-update-task.ps1`(작업 스케줄러 등록), `docker-compose.prod.yml` 이미지화, `docker-compose.build.yml`, `.env.example`(`IMAGE_TAG`), README·CLAUDE.md 갱신.

### 검증
- YAML 구문, compose 설정(`config`) 확인. 로컬 이미지 저장소(registry)와 별도 프로젝트 이름의 시험 스택으로 `update.ps1`을 실제 실행: 첫 배포, 변경 없음, 새 이미지 교체(web만 재생성)를 확인했다(결과는 PR 본문). ghcr.io 푸시와 GitHub Actions 실행은 이 환경에서 불가하다.
- 알려진 한계: ghcr 패키지의 기본 공개 여부는 첫 푸시 뒤 GitHub 화면에서 확인해야 한다.

## 채팅 화면 UI 개편 (브랜치 `feature/chat-ui-redesign`)

사용자 요청: ①예약 뒤 채팅창에 작게 안내를 넣는다. ②당근마켓 채팅 화면을 참고해 채팅 UI를 개선한다(색상 말고 배치만 참고).

### 결정
- 웹 검색으로는 당근마켓 채팅 화면의 구조를 확인하지 못해, 배치는 일반적인 메신저·거래 채팅 구조를 기준으로 잡았다. 색상·로고·아이콘은 가져오지 않고 기존 토큰을 그대로 쓴다.
- 화면 전체 높이를 쓰는 채팅형 레이아웃: 헤더(← 뒤로, 닉네임, ⋯ 메뉴에 차단·신고) / 거래 정보 카드(자리 요약, 상태 뱃지, 예약 동작) / 접이식 안전 안내 / 메시지 목록(여기만 스크롤) / 하단 입력줄.
- 말풍선: 시간은 말풍선 옆, 같은 보낸 사람·같은 분의 연속 메시지는 마지막에만 시간 표시, '읽음'은 내 마지막 메시지 시간 위, 날짜 구분은 알약. 입력창은 최대 5줄까지 늘어나고 보내기 버튼은 원형, 글자 수는 900자부터 표시.
- 예약 후 안내는 저장하는 채팅 메시지가 아니라 거래 정보 카드의 작은 안내 문구다(시스템 메시지는 저장하지 않는 규칙 유지). RESERVED이고 종료되지 않았을 때만 보이고 '내 매칭 목록'은 링크다.
- 상대 아바타는 사용자 지시("아바타 설정하는 것도 없어서 쓸데없는 기능")로 제외했다. 첨부용 '+' 버튼도 만들지 않았다.

### 구현
`pages/ChatPage.tsx`(JSX·className 중심, 입력창 자동 높이용 효과만 추가), `components/ChatSafetyActions.tsx`(`menu` prop 추가, 기본값은 기존 동작), `components/AppLayout.tsx`(채팅 경로에서만 전체 높이 고정). 전송·수신·읽음·예약 로직과 접근성 속성은 그대로다. 프런트 서브에이전트(worktree)가 구현했다.

### 검증
- `npm run build`(tsc 포함) 통과. API를 모킹한 Playwright로 데스크톱(1280x800)·모바일(390x844)에서 채팅 중·예약 제안·예약 중·종료 채팅·⋯ 메뉴·신고 모달을 확인했고 페이지 자체 스크롤이 없다.
- 확인하지 못한 것: 실서버·STOMP 연동, 실제 모바일 키보드·IME 높이 변화, 새 메시지 N개 버튼·이전 메시지·전송 실패 UI의 스크린샷, 스크린 리더 실사용.

### 채팅 UI 2차 개선과 내 채팅 목록 (같은 브랜치 `feature/chat-ui-redesign`)

사용자가 당근마켓 채팅 화면 캡처 3장을 주며 형태·레이아웃만 참고하라고 했고(색상 제외), 입력창의 스크롤 제거와 '내 채팅' 목록 페이지·마이페이지 버튼을 추가로 요청했다.

- **입력창 스크롤 제거**: 원인은 최소 높이·패딩·줄 높이·테두리가 겹쳐 한 줄에서도 내용 높이가 넘친 것이었다. 테두리를 바깥 알약으로 옮기고 스크롤바를 숨겼다(5줄 초과 시에도 막대 없이 스크롤).
- **입력줄**: 알약 입력창 안쪽에 종이비행기 아이콘 보내기 버튼(채워진 원형 버튼 제거).
- **⋯ 메뉴**: 모바일은 바텀 시트(신고하기·차단하기·닫기), 데스크톱은 드롭다운. 신고·차단 모달 동작은 그대로.
- **거래 정보 카드**: 첫 줄에 상태 뱃지와 굵은 요약, 오른쪽 끝에 '예약 제안'/'예약 수락' 버튼. 좁은 화면에서 요약이 잘리지 않고 줄바꿈된다.
- **내 채팅(`/my/chats`)**: 옛 프로젝트 Nested의 메시지 목록(필터 토글·카드 목록)을 참고해 새로 작성. 매칭 목록 API 재사용, 종료 채팅 포함, 안 읽음 먼저. 상대 아바타·대화 삭제는 없다. 한계는 CLAUDE.md '채팅' 절 참고(마지막 메시지 미리보기·최근 대화순은 백엔드 필드가 필요해 후속).
- **검증**: `npm run build` 통과, API 모킹 Playwright로 모바일·데스크톱 확인. 실서버·실제 모바일 키보드 동작은 확인하지 못했다.

### 채팅 UI 다듬기 (같은 브랜치, 사용자 피드백 반영)
- 거래 카드의 '내'/'상대'가 구역과 구분되지 않아 라벨을 작은 알약으로 바꿨다(처음엔 `내 자리`/`상대 자리`였다가 사용자 제안으로 `내`/`상대`로 줄이고 글자 크기도 줄임, 색은 연한 톤). 자리 요약은 한 줄에 들어가면 한 줄이고 넘치는 순간 상대 자리가 다음 줄로 내려간다. 내 채팅 목록 카드도 같은 방식.
- 상태 뱃지(채팅 중·예약 중·교환 완료·종료)는 헤더의 상대 닉네임 오른쪽으로 옮겼다.
- '예약 제안'을 누르면 카드 안에서 확인 영역이 펼쳐져 버튼이 왼쪽 아래로 내려가고 채팅창이 줄어들던 문제: 확인 단계를 하단 시트(데스크톱은 가운데 대화상자)로 옮기고 카드의 버튼은 제자리에 둔다.
- 서로 다른 회차(날짜·시각·구역이 다른 두 자리) 교환 화면을 API 모킹으로 점검: 채팅 거래 카드(일시가 다르면 `내 … · 상대 …`로 둘 다 표시), 내 채팅 목록, 내 매칭 카드(두 자리의 일시가 각각 표시)가 모바일·데스크톱에서 정상이다. 실제 서버를 거친 end-to-end와 후보 목록·교환 이력 화면은 이번에 확인하지 않았다.
- 교환 방향 표현(사용자 요청): 내 자리 → 상대 자리 화살표를 두 자리 사이에 두고 도착 자리(상대·받은 자리)를 크고 진하게, 내 자리·교환 전 자리는 작고 연하게 바꿨다(채팅 거래 카드, 내 채팅, 내 매칭 카드, 교환 이력). 화살표는 옅게(투명도) 크게 하고, 내 매칭 카드는 넓은 화면에서 `내 자리 | → | 상대 자리` 3열 그리드로 화살표 자리를 확보했다. 모바일 채팅 카드에서 자리 요약이 줄바꿈되면 화살표는 첫 줄 끝에 남는다.
- 추가금 표시(사용자 요청): 내 매칭 카드·후보 카드에서 추가금이 없을 때(X·ANY)는 행을 숨기고 받고/낼 조건(POS·NEG)만 보인다.
