## 링크 기반 공연정보 자동 입력 (브랜치 `feature/link-autofill`, master `1b666ed` 위, 병합 전)

### 실측 (2026-10-12)
- 세 사이트의 공개 페이지 raw HTML을 직접 받아 구조를 확인했다. YES24와 티켓링크는 JSON-LD `Event`, 멜론은 JSON-LD·og:title이 없고 본문 HTML에서 읽는다.
- 실제 3개 페이지에 파서를 돌려 제목·공연장·기간이 맞게 나오는 것을 확인했다. 공연장이 비어 있는 상품(멜론·티켓링크 일부)도 확인했다.
- 회차 시각은 세 사이트 모두 공개 HTML에 없고 Ajax(예매 달력)로만 온다는 것을 확인했다.
- robots.txt: ticket.yes24.com·ticket.melon.com은 규칙 대신 오류 페이지를 돌려줘 규칙이 없는 것으로 해석했다. 티켓링크는 상품 상세를 허용하고 예매·내 정보·검색 경로를 금지한다. 인터파크는 금지라 제외했다.

### 결정
- 회차는 자동으로 채우지 않는다. 기간이 있으면 회차 입력 근처에 기간 안내만 한다. 요구사항의 '제목·공연장·회차' 중 회차는 자동 입력 대상에서 빠진다. Ajax를 읽는 것은 CLAUDE.md의 '내부 API 조사는 하지 않는다' 규칙에 걸리므로 하지 않는다.
- 자동 등록은 하지 않는다. 미리 채우기 후 사용자 확인, 직접 입력은 항상 가능하다.
- 대상은 YES24·티켓링크·멜론이다. 인터파크는 제외한다.
- SSRF 방어: 사용자가 준 URL은 요청하지 않고, 고정 템플릿 3종으로만 URL을 만든다.

### 구현
- 백엔드: `GET /api/performances/preview?sourceUrl=`(로그인 필요). `service/linkinfo/PageFetcher`·`LinkInfoParsers`·`PerformancePreviewService`, `dto/response/PerformancePreviewResponse`, `PerformanceController`에 `/preview`, `GlobalExceptionHandler`에 429 핸들러, 설정 `seatswap.linkinfo.*`. 의존성 `org.jsoup:jsoup:1.18.3` 추가.

### 설계 메모 (잠금·인덱스)
- 'PENDING은 1건' 유니크는 생성 컬럼(PENDING일 때만 사용자 id) + UNIQUE로 강제했다. 처리되면 NULL이 되어 다시 제안·요청할 수 있다. FK 인덱스는 단일 컬럼이고 갱신 컬럼을 섞지 않는다(CLAUDE.md 개발 규칙).

## 차단·신고·관리자 신고 관리 (브랜치 `feature/block-report`, master `0011666` 위, 병합 전)

### 결정
- 사용자 요청: 차단·신고 기능과 그것을 관리하는 관리자 기능을 함께 만든다. 요구사항 Q-21(신고 처리용 최소 관리자 기능의 범위)은 이 요청으로 확정했다: 신고 목록·상세(채팅 근거 열람)·처리(조치·기각) + 이용 정지 + 차단 현황 조회.
- 차단은 방향이 하나(차단한 쪽 → 차단당한 쪽)이고 효과는 양방향이다. 서로 후보에서 빠지고 새 제안이 막히며, 둘 사이의 열린 매칭(CHATTING·RESERVED)은 차단 시점에 시스템 취소하고 예약 잠금을 푼다. 차단당한 쪽에는 알리지 않는다. 차단은 채팅 화면에서만 시작한다(임의 userId 차단 API 없음). 해제해도 취소된 매칭은 되살리지 않는다. 상한 200.
- 신고는 채팅 화면에서만 한다(닫힌 매칭에서도 가능). 사유 5종(`ABUSE`·`FRAUD`·`NO_SHOW`·`FAKE_SEAT`·`OTHER`), 상세 500자(OTHER는 필수). 같은 매칭 OPEN 1건, 사용자당 OPEN 10건. 신고만으로 자동 차단·자동 제재는 없다.
- 이용 정지는 관리자가 신고를 처리하며 건다. 기간 7일·30일·무기한, 사유 필수. 정지 중에는 로그인·토큰 재발급·인증 API·STOMP CONNECT가 403 `ACCOUNT_SUSPENDED`이고, 후보에서 빠지며, 정지를 거는 순간 열린 매칭을 모두 시스템 취소한다. 기간 만료는 조회 시점에 판단한다(스케줄러 없음). 관리자(ADMIN)는 제재 대상이 아니다.
- 신고 근거 보존을 위해 신고된 매칭의 채팅 메시지는 관리자가 열람한다(화면 상단에 처리 목적 외 사용 금지 안내).

### 구현
- 커밋(`feature/block-report`): 38bc304(열린 매칭 시스템 취소 인터페이스 `OpenMatchCanceller`, 차단·정지 공용 계약), aedeeb9(V13 스키마 `user_block`·`abuse_report`·`user_sanction`), 029e60c(차단 백엔드, 차단·신고 화면, 후보 양방향 제외, 시스템 취소 구현), fac47bd(신고·정지 백엔드, 관리자 처리 API, 정지 계정 403 강제, 신고 근거 채팅 열람, 제재 해제).
- 백엔드: `BlockController`·`BlockService`, `ReportController`·`AbuseReportService`, `AdminModerationController`·`AdminModerationService`, `AccountSuspensionChecker`(요청마다 정지 검사, `CustomUserDetailsService.loadUserById`에서 호출), `OpenMatchCancellerImpl`. 후보 SQL에 차단 제외(NOT EXISTS 두 개로 나눔)와 정지 사용자 제외를 추가했다.

### 잠금 설계 메모
- 열린 매칭 시스템 취소는 티켓 id↑ → 요청 id↑ → 매칭 id↑ 순으로 잠근다. 호출 트랜잭션은 READ COMMITTED다.
- 차단·신고·제재의 INSERT는 트랜잭션 마지막에 둔다. 제재는 대상의 신고 행들을 먼저 잠가 같은 대상의 동시 제재를 직렬화한다.
- 차단 제외 SQL은 `NOT EXISTS` 두 개로 나눠 쓴다. OR로 묶으면 옵티마이저가 `user_block` 전체 인덱스 스캔을 고른다(EXPLAIN 근거).

### 검증
- 백엔드 전체(임시 MySQL IT 포함) 781건 통과, 실패 0, skip 0. V13 스키마 7건, 차단 17건(취소 범위, 차단과 예약·티켓 내리기·제안 경합 20라운드에서 교착 0, `cancelAllOf` 경합), 신고·제재 약 45건(OPEN 중복·동시 신고, 처리 경합에서 1건만 성공, 정지 중 로그인·API·재발급 403, 해제·만료 뒤 복귀, ADMIN 거부, 채팅 근거 범위).
- 프론트 `tsc`·빌드 통과. 브라우저 점검은 하지 않았다.
- 위 수치는 작업 세션의 보고값이다. 이 기록을 쓸 때 같은 수치를 재실행해 확인하지는 않았다.

### 알려진 한계
- 검증(Fable) 지적 반영: 이용 정지를 걸면 커밋 뒤 대상의 STOMP 연결을 닫는다(`closeAllOf`). 차단은 연결을 닫지 않고 매칭 취소로 쓰기를 막는다. 제재 없는 resolve는 그 신고 행만 잠근다.
- 알려진 한계(검증 지적, 미조치): 차단 트랜잭션 수 ms 안에 새 티켓 등록→요청→제안이 모두 끝나는 이론적 경합에서 차단 직후 매칭 하나가 CHATTING으로 남을 수 있다(예약·교환 수락 재검사는 후속); 후보 제재 제외 시각 리터럴은 목록·총계에서 초 경계 1건 어긋날 수 있다.
- 차단 상한 200과 신고 상한 10은 동시 요청에서 근소하게 넘을 수 있다(사용자 행을 잠그지 않음).
- 같은 대상을 동시에 제재하면 한쪽이 교착으로 503이 될 수 있다(중복 제재는 생기지 않는다).
- 신고 처리 결과는 신고자에게 상태만 보인다.
- 채팅 응답의 상대 숫자 id(`senderId`) 노출은 그대로다.
- 브라우저 수동 점검은 아직 하지 않았다.
