# 링크 기반 공연정보 자동 입력 설계 근거

공연 등록 1단계에서 링크를 받아 제목·공연장·공연 기간을 미리 채우는 기능(브랜치 `feature/link-autofill`, 2026-10-12 구현, 병합됨, DB 변경 없음)의 근거다. 확정 규칙 본문은 [CLAUDE.md](../../CLAUDE.md)의 "링크 기반 공연정보 자동 입력" 절이 기준이고, 여기에는 실측 결과와 대안 비교만 둔다. 함정은 [링크 가져오기 함정](../gotchas/link-fetch-pitfalls.md), 용어는 [용어집](../glossary.md) 참고.

## 1. 실측 결과 (2026-10-12, 공개 페이지 raw HTML)

| 사이트 | 제목·공연장·기간을 읽는 곳 | 비고 |
|---|---|---|
| YES24 | 서버 렌더된 JSON-LD `Event`(name, location.name, startDate/endDate 날짜만) | |
| 티켓링크 | JSON-LD `Event` 동일 구조 | robots.txt가 상품 상세를 허용하고 예매·내 정보 등 일부 경로만 금지 |
| 멜론 | JSON-LD·og:title 없음. 본문의 제목 요소, 공연장 항목, 기간 영역 | 공연장이 빈 상품이 있음 |
| 인터파크 | 읽지 않음 | robots.txt 때문에 제외(`UNSUPPORTED_SITE`) |

로그인·캡차 우회와 내부 API 호출은 하지 않았다. 실제 페이지 3개에 파서를 돌려 제목·공연장·기간이 맞게 나옴을 확인했다. 외부 접속 테스트는 만들지 않고 파서는 실측 구조를 줄인 fixture로 검증한다.

## 2. 회차(시각)는 읽을 수 없다

세 사이트 모두 회차 목록과 시각은 공개 HTML이 아니라 예매 달력의 Ajax로만 온다. 그래서 회차는 채우지 않고, 기간이 있으면 회차 입력 근처에 안내만 보여준다. 요구사항 문서가 "제목·공연장·회차"로 적었던 범위 중 회차는 이 실측으로 불가가 확정되었다. 회차를 읽으려면 내부 API 조사가 필요한데 이는 하지 않기로 한 범위라 다루지 않는다.

## 3. 핵심 결정: 사용자 URL을 요청하지 않는다 (SSRF 구조적 차단)

서버가 사용자가 준 주소로 요청을 보내면 내부망·메타데이터 주소 등으로의 SSRF 위험이 생긴다. 그래서 사용자 URL 자체는 요청하지 않는다. 기존 `SourceKeyResolver`가 링크에서 뽑은 키(`yes24:{숫자id}` 등)가 지원 사이트의 형식일 때만 진행하고, 요청 URL은 **코드에 고정된 템플릿 3종에 id만 끼워** 직접 만든다. 일반 `url:` 키, 인터파크, 잘못된 id는 요청 없이 `UNSUPPORTED_SITE`다.

이 위에 방어를 겹쳤다. https만 허용, 리다이렉트 불추종(3xx는 실패), 응답 전 DNS 해석 결과가 전부 공인 IP인지 확인, 연결·전체 시간 제한, 본문 2 MiB 상한, `text/html`만 수락, 쿠키·인증 없음, 식별 가능한 User-Agent. 사용자당 분당 10회 제한, 사이트별 분당 30회·동시 4개 제한, 결과 10분 캐시(최대 200개)로 외부 사이트에 부담을 주지 않는다.

이유는 지원 사이트가 3개뿐이고 서버가 읽을 값(제목·공연장·기간)이 사이트 구조로 정해지기 때문이다. 임의 URL을 받을 필요가 없는데 받으면 방어 면적만 커진다.

## 4. 택하지 않은 대안: 사용자 URL 요청 + IP pinning

임의 URL을 받아 DNS 해석 후 **검증한 IP로 연결을 고정(pinning)** 하는 방식이다. 택하지 않은 이유는 다음과 같다.

- 지원 대상이 고정된 3개 도메인이라 임의 URL 지원의 이익이 없다.
- JDK `HttpClient`는 연결 IP를 지정하기 어렵다([함정 페이지](../gotchas/link-fetch-pitfalls.md)). 제대로 하려면 호스트명 대신 IP로 접속하면서 SNI·Host를 따로 맞추는 저수준 구현이나 다른 클라이언트가 필요하다.
- 리다이렉트마다 재검증, IPv6·IPv4-mapped·CGNAT 등 우회 경로를 끝까지 막아야 하는 부담이 크다.

고정 템플릿이면 이 부담이 구조적으로 사라진다. 이는 결정의 이유일 뿐 새 결정이 아니다.

## 5. 한계 (확인된 것과 미확인)

- 검증한 IP로 연결을 고정하지 않는다. 대상 도메인이 코드에 고정된 공개 도메인 3개라 공격자가 DNS를 바꿀 수 없다는 **전제**에 의존한다. 도메인이 탈취되거나 대상이 늘면 재검토가 필요하다.
- 사이트 HTML이 바뀌면 `NO_INFO`가 된다(어댑터 취약성).
- 속도 제한·캐시·세마포어는 단일 인스턴스 메모리다. 다중 인스턴스가 되면 따로 두어야 한다.
- 링크 형식 오류(400)도 사용자 제한 1회로 센다.
- 티켓링크·멜론에서 공연장이 비어 있을 수 있다.
- 브라우저 점검은 하지 않았다(미확인).

## 6. 회차 날짜 후보와 AI 확장 구조 (2026-10-13, `feature/session-prefill`)

시각은 읽지 못하지만(§2) **날짜는 공연 기간에서 얻을 수 있다.** 그래서 공연 기간이 100일 이하인 공연의 연속된 모든 날짜를 후보로 채운다(처음에는 2일 이하만이었다가 2026-10-14에 확대, 아래 6.1). 규칙의 본문은 CLAUDE.md '링크 기반 공연정보 자동 입력' 절과 백엔드 README '회차 날짜 후보' 절이 기준이고, 여기에는 판단 근거와 대안만 둔다.

### 6.1 후보 날짜 범위를 2일에서 100일로 넓힌 이유 (판단, 구현 상수 `MAX_PERIOD_DAYS_FOR_CANDIDATES`=100)

- 2026-10-14 사용자 요청: 연속된 공연 날짜면 첫날부터 끝날까지 모두 회차 입력에 자동으로 채우고 싶다. 처음 판단(아래 세 항목, 2일 이하만)은 '틀릴 가능성'과 '노이즈'를 이유로 보수적으로 잡은 것이었다.
- 넓히되 노이즈는 화면에서 줄였다: 한 번에 채우는 버튼('기간 전체 날짜로 회차 채우기')과 '모든 회차 시각 한번에 넣기'로 100줄을 일일이 입력하지 않게 하고, 쉬는 날은 줄을 삭제하게 한다. 날짜만 있고 시각이 없는 줄이 남으면 다음 단계로 못 간다.
- 상한 100일은 공연 등록 한 번의 회차 상한(100)과 같다. 그보다 긴 기간은 후보를 만들지 않는다.
- 아래는 2일 이하로 제한했을 때의 원래 판단 기록이다.

- 기간이 짧을수록 가능한 날짜가 적어 미리 채운 날짜가 틀릴 가능성이 낮다.
- 3일 이상(뮤지컬 등)은 기간 안 어느 날이 회차인지, 하루에 몇 회차인지 링크에서 알 수 없다. 날짜를 펼치면 후보가 수십 개가 되어 노이즈가 커진다.
- 기간이 없거나 시작>종료면 날짜를 만들지 않는다.

### 6.2 택하지 않은 대안

- **기간 전체를 날짜로 펼치기**: 뮤지컬처럼 긴 공연에서 후보가 많아져 기각했다.
- **회차 자동 등록**: 시각이 없으면 회차를 만들 수 없고, 잘못된 회차가 들어가는 위험이 있어 기각했다. 사용자가 시각을 고르고 '회차 추가'를 눌러야 회차가 된다.
- **시각까지 자동 채우기**: 세 사이트 모두 회차 시각이 Ajax라 링크 HTML로는 읽을 수 없다(§2). Ajax를 읽으면 CLAUDE.md의 '내부 API 조사는 하지 않는다' 규칙에 걸린다.

### 6.3 AI 상세정보 출처를 붙일 자리 (구조만, 구현 없음)

- 응답 `sessionCandidates`는 `{date, time}` 형태이고 `time`은 지금 항상 null이다. 나중에 상세정보를 읽는 출처(AI 등)가 붙으면 **같은 DTO로** 날짜와 시각을 채워 내려주면 되고, 날짜 칸 채우기 화면은 그대로 쓴다.
- 프런트는 아직 `time`을 읽지 않는다(날짜만 `date`로 쓴다). 시각 칸을 채우는 것은 출처가 정해진 뒤 한다.
- 출처를 붙일 때 다시 정해야 할 것: 상세정보를 읽는 경로(사용자 URL 요청 금지와 고정 템플릿 원칙을 유지하는지), 외부 호출의 속도 제한과 비용, 실패 시 빈 후보로 두는 규칙, 뮤지컬처럼 기간이 긴 공연의 회차 수. 이 결정은 착수 지시가 온 뒤에 한다.

### 6.4 한계

- 시각은 직접 입력한다. 3일 이상 공연은 날짜 후보가 없다.
- 하루에 여러 회차(낮·밤)인 2일 공연은 날짜당 후보가 1개라 같은 날짜를 직접 추가해야 한다.
- 공연 기간과 실제 회차 날짜가 다를 수 있다(휴연일 등). 화면은 "확인 후 고쳐 주세요"로 안내한다.
- 브라우저 점검은 Playwright 수준이다(티켓링크 2일 공연, 모의 미리보기로 회차 추가 흐름).
