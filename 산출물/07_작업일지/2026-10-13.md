## 2026-10-13

## 예약 제안·수락 + 채팅 알림 + 벨 위치 (브랜치 `feature/reserve-propose`, master `9bc9570` 위, 병합 전)

### 결정 (사용자 지시, 2026-10-12)
- 예약 방식 변경: 한 명이 예약하면 즉시 RESERVED가 되던 방식(2026-10-08 8차 답변, 2026-10-10 구현)을 뒤집는다. 이제 '예약 제안 → 상대 예약 수락'이어야 RESERVED가 된다. 예약 취소 때 CHATTING으로 돌아가는 규칙은 그대로다.
- 예약하기 버튼은 채팅 화면에서만 보인다. 내 매칭 카드에는 예약 버튼이 없고 제안 여부 문구와 '채팅' 버튼만 둔다. RESERVED 카드의 '예약 취소'·'교환 수락'과 거절·채팅 종료 제한 안내는 유지한다.
- 채팅 새 메시지도 헤더 알림 벨에 표시한다(이전 "채팅 알림 행 없음" 결정을 뒤집음). 헤더 메시지 아이콘은 두지 않는다. 알림 행은 (수신자, 매칭)당 1행을 재사용한다.
- 알림 벨 위치: 데스크톱(768px 이상)은 '내 매칭' 바로 오른쪽(관리자 링크 앞), 햄버거 폭에서는 햄버거 버튼 왼쪽. 벨 인스턴스는 하나이고 폭에 따라 위치만 옮긴다(`useIsDesktop`).
- 예약 제안은 새 상태가 아니라 CHATTING 매칭의 부가 정보다. 제안은 티켓을 잠그지 않고 매칭 행만 잠근다.

### 구현
- DB: `V15__reserve_proposal_chat_notification.sql`. `exchange_match.reserve_proposed_by_id`·`reserve_proposed_at`(CHECK 3종: 둘 다 NULL이거나 둘 다 NOT NULL, CHATTING이 아니면 NULL, 제안자는 참여자). `notification.type` CHECK를 6종으로 넓히고 `ck_notification_chat_dedup`을 추가했다. 테이블 수는 20 그대로다.
- 백엔드: 예약 제안(`POST /api/exchange/matches/{id}/reserve`), 예약 수락(`reserve/accept`), 예약 거절(`reserve/decline`), 제안 철회(`reserve/withdraw`)를 추가했다. 예약 취소(`unreserve`)는 그대로다. 수락은 기존 예약 잠금 로직(티켓 id↑ → 요청 id↑ → 매칭)을 재사용하며 `reserved_by_id`는 제안자가 된다. 응답에 `reservationProposal`(NONE·MINE·THEIRS)을 추가했다. CHATTING을 벗어나는 모든 UPDATE(취소·거절·종료·요청 수정/삭제·티켓 내리기·차단·정지·시스템 취소)는 같은 문장에서 제안 컬럼을 비운다.
- 알림: `RESERVATION_PROPOSED`(제안받은 쪽), `RESERVATION_REJECTED`(제안자), `CHAT_MESSAGE`(상대)를 추가했다. `MATCH_RESERVED`는 '상대가 예약을 수락했어요' 문구로 바뀌어 제안자에게 간다. 철회는 알림이 없다. `RESERVATION_PROPOSED`·`CHAT_MESSAGE`는 (수신자, 매칭)당 1행을 재사용한다. 채팅 읽음 포인터가 올라가면 그 (수신자, 매칭)의 `CHAT_MESSAGE`를 읽음 처리한다. 알림 신호는 커밋 뒤에 한 건씩 보낸다.
- 프런트: 채팅 화면 상단 예약 블록(예약 제안하기·제안 철회·예약 수락·거절·예약 취소, 종료 매칭은 숨김), 내 매칭 카드의 '예약하기' 제거와 제안 여부 문구, 알림 문구 6종과 클릭 이동(채팅 메시지·예약 제안은 채팅 화면), 벨 위치(`useIsDesktop`). 상대의 제안·수락·거절·취소는 알림 신호와 폴링으로 새로고침 없이 반영한다.

### 설계 메모 (잠금·교착)
- 재사용 알림의 순수 upsert(유니크 인덱스를 먼저 잠금)와 '읽은 알림 삭제'(PK를 먼저 잠금)가 실제 MySQL에서 교착했다. 그래서 재사용 알림은 PK 행을 먼저 갱신하고, 없을 때만 `INSERT … ON DUPLICATE KEY UPDATE`로 만드는 방식으로 통일했다.
- 제안·철회·거절은 매칭 행만 잠근다. 알림 쓰기는 트랜잭션 맨 끝에서만 한다.
- 채팅 읽음 연동은 매칭·users 잠금을 잡은 트랜잭션 밖에서 독립 트랜잭션으로 한다.

### 검증
- 백엔드 기본 `./gradlew test`와 임시 MySQL 컨테이너(고유 이름·포트, DB 이름 `_it`)로 MySQL IT를 포함한 전체 테스트 통과. 신규 동시성 IT `ReserveProposalMysqlTest`는 동시 제안, 제안 vs 철회, 수락 vs 거절·철회, 같은 티켓 두 매칭의 수락 경합, 수락 vs 취소·차단·정지·티켓 내리기·요청 삭제, 예약 취소 vs 재제안, 채팅 전송·읽음·삭제 혼합을 다뤘고 교착 0, 불변식(잠금 행 = 2 × RESERVED, 제안은 CHATTING에만) 유지를 확인했다.
- Fable 최종 검증: 높음 없음. 중간 2건(되살린 알림 정렬, 제안 알림 무제한 증가)과 낮음 6건을 지적받았다. 제안 알림 증가는 재사용 행으로 막았다.
- 프런트 `tsc -b`·`npm run build` 통과. Playwright로 채팅 알림 실시간 반영, 제안→거절→재제안→수락→예약 취소 흐름, 내 매칭 카드의 예약 버튼 제거, 벨 위치(데스크톱·768px·480px)를 확인했다.
- 위 결과는 '통과'로만 기록한다. 테스트 건수는 확정값이 없어 적지 않는다.

### 알려진 한계 (구현과 문서를 대조해 확인)
- Fable 지적 반영: 알림 목록·말풍선 정렬을 `ORDER BY created_at DESC, id DESC`로 바꿨다(되살린 채팅·제안 알림이 최신 맨 위). 정렬용 인덱스는 만들지 않았다(알림이 (수신자, 매칭)당 1행 수준).
- 채팅 읽음 포인터가 올라가면 그 (수신자, 매칭)의 `CHAT_MESSAGE` 알림을 읽음 처리하되, 한 문장 `NOT EXISTS` 가드로 포인터 뒤에 상대 메시지가 남아 있으면 처리하지 않는다(READ_COMMITTED).
- 제안 알림(`RESERVATION_PROPOSED`)도 (수신자, 매칭)당 1행 재사용으로 바꿨다(제안→철회 반복으로 알림이 쌓이는 것 방지). 거절·수락·예약 취소 알림은 반복마다 1건이다.
- RESERVED 상태에서 `reserve/accept`를 다시 누르면 제안자·수락자 모두 멱등 200이다(CHATTING에서 제안자가 누르면 409 `RESERVATION_PROPOSAL_OWN`).
- 예약-취소 남용 방지 없음(차단·신고로 다룸). 정렬용 `(user_id, created_at)` 인덱스 없음(알림이 매칭당 1행 수준이라 불필요로 판단). 읽음 가드와 되살리기가 겹치는 극히 약한 창이 있다. 일부 경로는 REPEATABLE READ 패턴을 유지한다.
- 프런트 `CandidatesPage`의 안내 문구가 아직 "예약은 내 매칭 화면에서 '예약하기'를 누르면"이라고 말한다. 예약 버튼이 채팅 화면으로 옮겨졌으므로 문구 정정이 필요하다(코드 작업, 이 문서 작업 범위 밖).
- 브라우저 수동 점검은 Playwright 확인 수준이다.
