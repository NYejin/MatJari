# 프로필 수정·소셜 계정 연결 설계 근거

마이페이지의 닉네임 수정과 소셜 계정 연결·해제(V16 `users.password_login_enabled`, `social_account`의 사용자당 제공자 1개 유니크, 브랜치 `feature/profile-edit`, 2026-10-13 구현, 병합됨)의 근거를 정리한다. 확정 규칙의 기준은 [CLAUDE.md](../../CLAUDE.md)다. 같은 이메일로 자동 연결하지 않는다는 결정은 [소셜 로그인 설계 근거](social-login-design.md)에 있고, 이 페이지는 그 결정을 뒤집지 않는다.

사용자가 정한 것은 마이페이지에서 소셜 계정을 연결·해제할 수 있다는 범위와 자동 연결을 하지 않는다는 기존 결정이다. 2단계 확정, 플래그, 잠금 순서는 구현 세션에서 정했고, 검증 지적으로 2단계 확정이 한 번 바뀌었다.

## 1. 왜 연결을 2단계로 확정하나 (강제 연결 로그인 CSRF)

처음 구현은 콜백이 곧바로 저장했다. 이 구조에서는 다음 공격이 가능했다.

1. 공격자가 자기 계정 id에 묶인 연결 티켓을 받는다.
2. 피해자의 브라우저를 그 티켓으로 authorize에 보낸다.
3. 피해자가 제공자에서 동의하면 피해자의 소셜 계정이 공격자 계정에 연결된다.
4. 이후 피해자가 '소셜 로그인'을 누르면 공격자 계정으로 로그인된다.

authorize 엔드포인트는 permitAll이라 서버는 티켓을 쓰는 브라우저가 발급받은 사용자와 같은지 알 수 없다. Fable 검증은 이를 높음(H-1)으로 지적했다.

수정: 콜백은 저장하지 않고, (연결 사용자, 제공자, 제공자 사용자 id)를 담은 일회용 **연결 확정 코드**만 발급한다. 저장은 로그인한 세션(Bearer)이 `POST /api/users/me/social/confirm`으로 코드를 제출할 때만 하며, 코드의 사용자와 세션 사용자가 같아야 한다. 피해자의 JWT로 공격자의 코드를 제출하면 400으로 막힌다.

## 2. 대안 비교

| 안 | 내용 | 결과 |
|---|---|---|
| A | 콜백에서 바로 저장 | 로그인 CSRF가 생긴다. 기각(검증 H-1) |
| B | 같은 이메일의 기존 계정에 자동 연결 | 이메일 검증이 불완전한 계정 탈취 위험. 기각(소셜 로그인 설계 3절, 사용자 결정) |
| C | 콜백은 확정 코드만 발급, 로그인 세션이 확정 | 채택 |
| D | 비밀번호를 설정해 소셜 전용 계정을 구제하는 기능 | 범위 밖. 요청 없음, 후속 |
| E | 마지막 로그인 수단을 비밀번호 해시 존재 여부로 판단 | 쓸 수 없음. 소셜 가입자도 무작위 BCrypt 해시를 가진다 |
| F | 해제를 막지 않고 로그인 수단이 0개가 되게 둠 | 계정을 잃을 수 있어 기각. 해제 때 `LAST_LOGIN_METHOD`(409)로 막는다 |

## 3. `password_login_enabled`를 둔 이유

- 소셜 가입자는 비밀번호를 모른다. 연결이 하나뿐인 소셜 전용 계정에서 해제하면 로그인할 방법이 없어진다.
- 해시 값으로는 "비밀번호로 로그인할 수 있는가"를 알 수 없다(E). 그래서 가입 경로에 따라 정하는 명시 플래그를 둔다. 일반 가입 1, 소셜 가입 0.
- 백필: V14 이후 `social_account` 행은 소셜 가입으로만 생겼으므로(연결 UI가 없었다), 그 행이 있는 사용자는 0이다. 백필 UPDATE는 0으로만 바꾸는 멱등 문장이라 중간에 중단되어도 재실행으로 마저 채워진다.
- 인덱스는 두지 않는다. 검색 조건으로 쓰지 않고 한 사용자 행에서 판단한다.
- `canUnlink`는 플래그가 1이거나 연결이 2개 이상일 때 true다. 화면은 이 값으로 해제 버튼을 비활성하고 사유를 보이며, 서버도 해제 때 같은 조건을 다시 본다(화면 값을 믿지 않는다).

## 4. 잠금과 유니크

- 확정과 해제는 `users` 행을 FOR UPDATE로 먼저 잡고 판단한다. 판단을 잠금 전에 하면 두 해제 요청이 서로의 연결을 보지 못하고 둘 다 통과할 수 있다(동시 해제 IT로 확인).
- 티켓·요청·매칭은 잠그지 않는다. `social_account`는 INSERT·DELETE만 하므로 FK 교착 규칙과 충돌하지 않는다.
- `uk_social_account_user_provider (user_id, provider)`는 사용자당 제공자 1개의 최후 방어선이다. 같은 제공자 중복은 `SOCIAL_ALREADY_LINKED`, 한 계정이 다른 사용자에게 붙은 것은 `SOCIAL_LINKED_OTHER`로 응답하며, 제약 이름으로 구분한다.
- 확정 코드는 먼저 소비한다. 다른 사용자의 코드를 내도 코드는 소진된다. 단 속도 제한에 걸린 요청은 코드를 소비하지 않는다.

## 5. 검증에서 나온 지적

Fable 검증은 높음 1건, 중간 3건, 낮음 1건을 냈고 모두 반영했다.

- 높음(§1): 콜백이 바로 저장하던 구조의 강제 연결 로그인 CSRF → 2단계 확정.
- 중간: 콜백 속도 제한이나 쿠키 검증 실패 때 연결하던 사용자가 로그인 화면으로 갔다 → 쿠키의 연결 사용자 칸으로 목적지를 `/me`로 고른다(목적지 선택에만 쓰고 보안 판단에는 쓰지 않는다).
- 중간: 연결 모드 authorize의 실패가 JSON으로 나갔다 → 302로 통일한다.
- 중간: 정지 안내가 항상 무기한으로 보였다 → until을 표시한다.
- 낮음: 티켓이 제공자에 묶이지 않았다 → (사용자, 제공자)에 묶는다.

## 6. 알려진 한계

- 같은 이름 쿠키 `ss_oauth` 하나라, 탭 A에서 연결을 시작하고 탭 B에서 소셜 로그인을 시작하면 A의 콜백이 INVALID_STATE가 된다.
- 연결 티켓이 URL 쿼리에 실린다(1회용, 60초). 사용 뒤에는 쓸모가 없다.
- 티켓·확정 코드·속도 제한은 메모리다(단일 인스턴스). 포화되면 60초간 SERVER_BUSY다.
- JWT 클레임에 자리표시 이메일 원문이 남는다(본인 토큰이며 화면에 나오지 않는다).
- 비밀번호·이메일 변경은 없다. 소셜 가입자는 비밀번호를 설정할 수 없다(D, 후속).
- 실제 카카오·구글·네이버 키로 검증하지 않았다(스텁 기준). 프런트 빌드와 브라우저 점검 기록은 구현 세션에 없다. confidence가 medium인 이유다.
