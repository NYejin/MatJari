# 설계안 초안: [빠른 교환]과 가입 이메일 확인 (2026-11-22, 결정 전)

이 문서는 결정용 초안이다. 아직 구현하지 않았고, 각 절 끝의 "정할 것"을 사용자가 고른 뒤 구현한다. 현재 규칙은 `CLAUDE.md`가 기준이다.

## 1. [빠른 교환]

### 1.1 목표와 핵심 문제
- 지금 흐름은 5단계다. 후보 선택 → 채팅 → 예약 제안 → 예약 수락 → 양쪽 교환 수락.
- 빠른 교환은 조건이 이미 맞는 상대와 채팅 없이 버튼 몇 번으로 예약까지 가는 흐름이다.
- **핵심 문제는 본인 좌석 확인이다.** 지금은 채팅에서 예매내역을 서로 보여 주며 확인한다. 채팅을 빼면 확인할 곳이 없어 거짓 좌석(가짜 티켓 등록) 위험이 커진다. 결제를 중개하지 않으므로 피해는 "좌석을 넘겨받지 못함"이지만, 상대 좌석을 이미 넘긴 사람은 되돌릴 방법이 없다.

### 1.2 안 비교

| | 안 A: 확인 사진 첨부 (권장) | 안 B: 확인 없이 바로 | 안 C: 관리자 확인 |
|---|---|---|---|
| 흐름 | 후보 카드 [빠른 교환 제안] + 내 예매내역 사진 → 상대 [수락] + 상대 사진 → 바로 예약 중(RESERVED) → 서로 사진 확인 → 교환 수락 | 제안 → 수락 → 바로 예약 중 | 제안·수락 뒤 관리자가 두 사진 확인 후 예약 중 |
| 사기 방지 | 중간 (사진 위조 가능, 신고 근거는 남음) | 낮음 | 높음 |
| 운영 부담 | 없음 | 없음 | 큼 (관리자 대기) |
| 구현 | 중간 (사진 저장 규칙은 좌석 인증 사진 재사용) | 작음 | 큼 |

### 1.3 안 A 세부 (권장안)
- **상태**: 새 상태값을 만들지 않는다. 빠른 교환 제안은 매칭을 만들면서 곧바로 예약 제안까지 넣은 상태(CHATTING + `reserve_proposed_*`)로 시작한다. 상대가 수락하면 기존 예약 수락 코드(잠금 순서 그대로)로 RESERVED가 된다. 그 뒤 교환 수락·교환 완료·예약 취소는 기존과 같다.
- **채팅**: 만들어지지만 필요할 때만 쓴다(문제가 생기면 대화, 신고 근거). 채팅을 아예 막지는 않는다.
- **확인 사진**: 각자 예매내역 캡처 1장(예매번호·이름 가리기 안내, jpeg/png/webp 5MB 이하). 상대만 볼 수 있다. 교환 완료·예약 취소·매칭 종료 뒤 삭제한다(좌석 인증 사진과 같은 정리 작업).
- **DB(V28 예정)**: `exchange_match.quick`(빠른 교환 여부) 또는 별도 표시 컬럼 1개 + 사진 표 1개(`exchange_proof`: 매칭, 사용자, 이미지 키, 만든 시각).
- **알림**: '빠른 교환 제안'(`QUICK_PROPOSED`) 1종 추가(알림 CHECK 확장).
- **대상 제한(권장)**: 추가금이 없거나 상관없음(X·ANY)끼리만 빠른 교환을 허용한다. 받을 돈·낼 돈(POS·NEG)이 있으면 금액 합의가 필요해 채팅 흐름으로 보낸다.

### 1.4 정할 것
1. 안 A·B·C 중 무엇으로 할지
2. 확인 사진을 필수로 할지, 선택으로 할지
3. 같은 좌석으로 일반 채팅과 빠른 교환 제안을 동시에 진행할 수 있게 둘지(지금 규칙은 예약 전 여러 채팅을 허용한다)
4. 추가금 있는 조합(POS·NEG)을 빠른 교환에서 뺄지
5. 상대가 일정 시간 수락하지 않으면 제안을 자동으로 거둘지(지금은 자동 취소가 없다)

## 2. 가입 이메일 확인 (인증을 끈 기간의 계정)

### 2.1 현황과 문제
- 2026-10-14부터 가입 이메일 인증번호를 꺼 두었다. 그 뒤 일반 가입한 계정은 **이메일 소유가 확인되지 않았다.**
- **문제 1, 선점**: 남의 이메일로 먼저 가입하면, 진짜 주인이 같은 이메일의 구글·카카오 계정으로 소셜 가입할 때 `EMAIL_EXISTS`로 막힌다.
- **문제 2, 비밀번호 찾기**: 나중에 비밀번호 찾기를 만들면 확인되지 않은 주소로 재설정 메일이 갈 수 있다.
- 지금 DB에는 계정마다 "이메일 확인됨" 표시가 없다. 인증을 통과해야만 가입되는 구조라 표시가 필요 없었기 때문이다.

### 2.2 제안
1. **V28 `users.email_verified_at`**(NULL = 미확인).
   - 채우는 기준: 인증을 켠 상태로 가입한 계정은 가입 시각, 소셜 가입은 제공자가 검증한 이메일이면 가입 시각, 자리표시 이메일은 NULL.
   - 기존 일반 가입 계정은 NULL로 시작한다. 인증을 켰던 기간(2026-10-13~14)에 가입한 계정도 구분할 기록이 없어 NULL로 둔다.
2. **미확인 계정 처리**: 로그인은 막지 않는다. 마이페이지 위에 "이메일을 확인해 주세요" 배너를 두고, 인증번호로 확인하면 `email_verified_at`을 채운다. 비밀번호 찾기는 확인된 이메일에만 보낸다.
3. **소셜 가입 충돌**: 같은 이메일의 기존 계정이 **미확인**이면 `EMAIL_EXISTS`로 막지 않고, 소셜 계정을 자리표시 이메일로 가입시킨다. 충돌은 기록해 관리자 대시보드에 건수로 보인다. 확인된 계정과의 충돌은 지금처럼 막는다.
4. **관리자 점검 표**: 미확인 일반 가입 계정 수, 소셜 가입 충돌 건수, 최근 충돌 목록.

### 2.3 선행 조건
- 실제 메일 발송(SMTP, 운영은 도메인 인증된 발송 서비스 권장) 준비와 `matjari.email-verification.enabled=true`.
- 비밀번호 찾기·변경 기능(같은 메일 발송 경로 사용).

### 2.4 정할 것
1. 미확인 계정에 확인을 **권유만** 할지, 일정 기간 뒤 **강제**(교환 제안 등 일부 기능 제한)할지
2. 소셜 가입 충돌 때 위 3번처럼 자리표시 이메일로 가입시킬지, 지금처럼 막고 안내만 할지
3. 메일 발송 수단(Gmail SMTP는 시연용, 운영은 SES·Resend 등)
