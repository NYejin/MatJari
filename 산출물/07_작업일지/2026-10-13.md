## 예약 제안·수락 + 채팅 알림 + 벨 위치 (브랜치 `feature/reserve-propose`, master `9bc9570` 위, 병합 전)

### 결정 (사용자 지시, 2026-10-12)
- 예약 방식 변경: 한 명이 예약하면 즉시 RESERVED가 되던 방식(2026-10-08 8차 답변, 2026-10-10 구현)을 뒤집는다. 이제 '예약 제안 → 상대 예약 수락'이어야 RESERVED가 된다. 예약 취소 때 CHATTING으로 돌아가는 규칙은 그대로다.
- 예약하기 버튼은 채팅 화면에서만 보인다. 내 매칭 카드에는 예약 버튼이 없고 제안 여부 문구와 '채팅' 버튼만 둔다. RESERVED 카드의 '예약 취소'·'교환 수락'과 거절·채팅 종료 제한 안내는 유지한다.
- 채팅 새 메시지도 헤더 알림 벨에 표시한다(이전 "채팅 알림 행 없음" 결정을 뒤집음). 헤더 메시지 아이콘은 두지 않는다. 알림 행은 (수신자, 매칭)당 1행을 재사용한다.
- 알림 벨 위치: 데스크톱(768px 이상)은 '내 매칭' 바로 오른쪽(관리자 링크 앞), 햄버거 폭에서는 햄버거 버튼 왼쪽. 벨 인스턴스는 하나이고 폭에 따라 위치만 옮긴다(`useIsDesktop`).
- 예약 제안은 새 상태가 아니라 CHATTING 매칭의 부가 정보다. 제안은 티켓을 잠그지 않고 매칭 행만 잠근다.

### 구현
- DB: `V15__reserve_proposal_chat_notification.sql`. `exchange_match.reserve_proposed_by_id`·`reserve_proposed_at`(CHECK 3종: 둘 다 NULL이거나 둘 다 NOT NULL, CHATTING이 아니면 NULL, 제안자는 참여자). `notification.type` CHECK를 6종으로 넓히고 `ck_notification_chat_dedup`을 추가했다. 테이블 수는 20 그대로다.
- 백엔드: 예약 제안(`POST /api/exchange/matches/{id}/reserve`), 예약 수락(`reserve/accept`), 예약 거절(`reserve/decline`), 제안 철회(`reserve/withdraw`)를 추가했다. 예약 취소(`unreserve`)는 그대로다. 수락은 기존 예약 잠금 로직(티켓 id↑ → 요청 id↑ → 매칭)을 재사용하며 `reserved_by_id`는 제안자가 된다. 응답에 `reservationProposal`(NONE·MINE·THEIRS)을 추가했다. CHATTING을 벗어나는 모든 UPDATE(취소·거절·종료·요청 수정/삭제·티켓 내리기·차단·정지·시스템 취소)는 같은 문장에서 제안 컬럼을 비운다.
- 알림: `RESERVATION_PROPOSED`(제안받은 쪽), `RESERVATION_REJECTED`(제안자), `CHAT_MESSAGE`(상대)를 추가했다. `MATCH_RESERVED`는 '상대가 예약을 수락했어요' 문구로 바뀌어 제안자에게 간다. 철회는 알림이 없다. `RESERVATION_PROPOSED`·`CHAT_MESSAGE`는 (수신자, 매칭)당 1행을 재사용한다. 채팅 읽음 포인터가 올라가면 그 (수신자, 매칭)의 `CHAT_MESSAGE`를 읽음 처리한다. 알림 신호는 커밋 뒤에 한 건씩 보낸다.
- 프런트: 채팅 화면 상단 예약 블록(예약 제안하기·제안 철회·예약 수락·거절·예약 취소, 종료 매칭은 숨김), 내 매칭 카드의 '예약하기' 제거와 제안 여부 문구, 알림 문구 6종과 클릭 이동(채팅 메시지·예약 제안은 채팅 화면), 벨 위치(`useIsDesktop`). 상대의 제안·수락·거절·취소는 알림 신호와 폴링으로 새로고침 없이 반영한다.

### 설계 메모 (잠금·교착)
- 재사용 알림의 순수 upsert(유니크 인덱스를 먼저 잠금)와 '읽은 알림 삭제'(PK를 먼저 잠금)가 실제 MySQL에서 교착했다. 그래서 재사용 알림은 PK 행을 먼저 갱신하고, 없을 때만 `INSERT … ON DUPLICATE KEY UPDATE`로 만드는 방식으로 통일했다.
- 제안·철회·거절은 매칭 행만 잠근다. 알림 쓰기는 트랜잭션 맨 끝에서만 한다.
- 채팅 읽음 연동은 매칭·users 잠금을 잡은 트랜잭션 밖에서 독립 트랜잭션으로 한다.

### 검증

### 알려진 한계 (구현과 문서를 대조해 확인)
- Fable 지적 반영: 알림 목록·말풍선 정렬을 `ORDER BY created_at DESC, id DESC`로 바꿨다(되살린 채팅·제안 알림이 최신 맨 위). 정렬용 인덱스는 만들지 않았다(알림이 (수신자, 매칭)당 1행 수준).

- 제안 알림(`RESERVATION_PROPOSED`)도 (수신자, 매칭)당 1행 재사용으로 바꿨다(제안→철회 반복으로 알림이 쌓이는 것 방지). 거절·수락·예약 취소 알림은 반복마다 1건이다.

- (해결) `CandidatesPage` 안내 문구는 '채팅 화면에서 예약 제안 → 상대 수락'으로 고쳤다(3b5929f).
- 브라우저 수동 점검은 Playwright 확인 수준이다.

## 프로필 수정·소셜 계정 연결·해제 (브랜치 `feature/profile-edit`, master `df3365d` 위, 병합 전)

### 결정
- 소셜 계정 연결은 자동 연결 없이, 마이페이지에서 로그인한 본인이 명시적으로 할 때만 한다. 같은 이메일의 기존 계정과 합치지 않는다(2026-10-12 결정 유지).
- 연결은 콜백에서 저장하지 않는다. 콜백은 일회용 연결 확정 코드만 발급하고, 로그인한 세션이 확정 API로 저장한다(2단계 확정, 아래 검증 H-1).
- 닉네임은 가입과 같은 규칙으로 바꾸고 중복은 허용한다. 이메일·비밀번호 변경은 이번 범위가 아니다.
- 자리표시 이메일(소셜 가입자)은 응답에서 `email=null`, `emailPlaceholder=true`로 내린다.

### 구현

### 검증
- 백엔드 `./gradlew test`와 임시 MySQL IT 통과. 신규 `SocialLinkMysqlTest` 8건: 동시 해제 대 해제, 같은 사용자 동시 확정(1건만 성공), 서로 다른 사용자가 같은 계정을 확정(1건 성공, 나머지 `SOCIAL_LINKED_OTHER`), 다른 사용자의 코드를 확정하면 400, 정지 사용자 등.

- 백엔드: `DELETE /api/users/me {password?, confirmText?}`(204). `WithdrawService`가 한 트랜잭션에서 ①PENDING 좌석 인증 요청 거절 ②열린 매칭 시스템 취소와 예약 잠금 해제(`OpenMatchCanceller.cancelAllOf`) ③OPEN 요청 CLOSED·활성 티켓 INACTIVE ④users 행 FOR UPDATE 후 2차 정리 ⑤소셜 연결 전부 삭제·users 익명화 ⑥수신자 알림 삭제를 하고, 커밋 뒤 STOMP 연결을 끊는다(`WebSocketSessionRegistry.closeAllOf`, 실패는 삼킴). 본인 확인은 비밀번호(BCrypt, 트랜잭션 밖) 또는 '탈퇴합니다' 확인 문구다. ADMIN은 409 `ADMIN_CANNOT_WITHDRAW`, 분당 5회 429 `WITHDRAW_RATE_LIMITED`.
- 익명화 값: 이메일 `withdrawn.{id}@withdrawn.seatswap.invalid`, 닉네임 `탈퇴한 회원`, 무작위 BCrypt, `password_login_enabled`=0, `withdrawn_at`=KST 현재 시각, role 유지. 원래 이메일이 비워져 같은 이메일로 재가입할 수 있다.
- 인증 차단: `CustomUserDetailsService`의 `loadUserById`·`loadUserByUsername`이 탈퇴 계정을 거절한다. 기존 액세스 토큰은 401, STOMP CONNECT는 거부, 로그인·refresh 400, 소셜 exchange 400 `INVALID_LOGIN_CODE`, 소셜 연결 확정 400 `INVALID_LINK_CODE`, 소셜 연결 해제 401.
- 관리자: 탈퇴한 대상에게 제재를 걸면 409 `TARGET_WITHDRAWN`. 탈퇴 대상 좌석 인증 요청은 같은 트랜잭션에서 거절한다.
- 프런트: 마이페이지 '회원탈퇴' 버튼 → `WithdrawDialog`(role=dialog, 포커스 트랩·Esc·바깥 클릭 닫기, 모바일 하단 시트, 프로필 로딩 전 비활성). 성공하면 홈으로 이동해 로그아웃하고 "탈퇴가 완료됐어요" 안내를 한 번 보인다(`HomePage`가 notice를 최상위에서 읽도록 바꿨다).
- 푸터(`Footer`, AppLayout): '개인정보처리방침' 링크와 ©. 채팅 화면에서는 레이아웃 때문에 숨긴다.
- 공개 라우트 `/privacy`(`PrivacyPolicyPage`): 표준 작성지침 순서(처리 목적·항목·14세 미만·보유 기간 표·파기·제3자 제공 없음·위탁 없음·권리 행사·쿠키·보호책임자·안전성 확보 조치·변경·시행일). 쿠키는 소셜 한시 쿠키 `ss_oauth`와 localStorage 토큰을 적었다.
- 가입 화면: 방침 링크와 "가입하면 동의한 것으로 봐요, 만 14세 미만은 가입할 수 없어요" 한 줄(동의 체크박스·기록 없음).

### 잠금 순서 (구현 중 바뀐 점)
- 설계 초안은 'users FOR UPDATE를 먼저'였으나 폐기했다. 제안(propose)은 티켓을 잠근 뒤 `exchange_match`를 INSERT하는데, 이때 users 행에 FK 공유 잠금을 요청한다. 탈퇴가 users를 X로 먼저 잡으면 제안과 교착한다. 이용 정지도 같은 이유로 users 잠금 없이 취소한다.
- 최종 순서: 인증 요청(id↑) → 티켓 id↑ → 요청 → 매칭 id↑ → users → 알림.
- users 잠금 뒤에는 새 활성 티켓·PENDING 인증·소셜 연결이 생기지 않는다. 티켓 등록·인증 요청·공연 수정 제안·소셜 연결이 모두 users FOR UPDATE로 시작하며 탈퇴 여부를 확인하기 때문이다. 그래서 2차 정리가 1차 정리와 users 잠금 사이에 생긴 것을 마저 정리한다.

### 방침의 보유 기간 (권장 초안, 법률 자문 전)
- 계정 정보는 탈퇴 즉시 삭제·익명화, 인증 사진은 처리가 끝나면 삭제, 받은 알림은 탈퇴할 때 삭제.
- 채팅·교환 이력·차단·신고·제재는 익명화해 서비스 운영 기간 동안 보관하고 서비스 종료 때 파기한다. 자동 파기 스케줄은 없다.
- 보관 기간의 법적 근거는 조사만 했다(전자상거래법 시행령 6조는 이 서비스에 직접 적용된다고 확인되지 않음, 신고·제재 보존 근거 없음). 세부는 위키 결정 페이지를 본다.

### 검증
- 전체 `./gradlew test`와 임시 MySQL IT 1010건 통과(실패 0, skip 0).
- 신규 `WithdrawMysqlTest` 7건: 탈퇴 vs 새 제안, 탈퇴 vs 예약 수락·철회, 탈퇴 vs 교환 수락, 탈퇴 vs 탈퇴, 탈퇴 vs 소셜 연결 확정, 탈퇴 vs 티켓 등록(15라운드). 불변식(활성 티켓 0, 열린 매칭 0, OPEN 요청 0, 잠금 행 = 2×RESERVED, social_account 0, 알림 0, PENDING 인증 0, 익명화 이메일 형식)을 매 라운드 확인했다.
- Fable 검증: 높음 없음. 중간 2건은 코드 버그가 아니라 정책이라 한계로 남겼다(정지 중 탈퇴 불가, 소셜 전용 계정의 재인증 없음). 낮음은 반영했다: `loadUserByUsername` 탈퇴 검사, 탈퇴 대상 제재 409, 방침 §2·§8 문구 보정.

- STATS.md는 훅이 자동 수정하므로 건드리지 않았다.

### 알려진 한계 (8개, 상세는 `wiki/decisions/withdraw-privacy-design.md`)
1. 이용 정지 중인 사용자는 탈퇴할 수 없다(인증 필터 403). 방침 §8은 문의처 요청으로 안내한다. 정책 확정 필요.
2. 소셜 전용 계정은 재인증 없이 확인 문구만으로 탈퇴한다. 액세스 토큰 탈취 시 되돌릴 수 없다. 후속 검토.
3. 인증 사진 삭제는 커밋 뒤 1회 시도하고 실패하면 로그만 남긴다(재시도·정리 작업 없음, 고아 파일 가능). 방침의 "처리 끝나면 삭제"와 완전히 일치하지 않으므로 정리 작업을 후속으로 둔다.
4. 교착 창 2개: 본인이 두 탭에서 요청 수정·삭제와 탈퇴를 동시에 실행하는 경우(요청→매칭 vs 티켓→매칭→요청), 1차 정리와 users 잠금 사이에 새 티켓을 등록하고 상대가 제안하는 밀리초 창. 감지기(MySQL 교착 → 503, 재시도)에 의존하며 불변식은 깨지지 않는다.
5. 보관 기간의 법적 근거가 확정되지 않았다. 익명화의 법적 충분성도 미확인이다. 공개 운영 전 전문가 검토가 필요하다(법률 자문 아님). 이 한계는 방침 페이지가 아니라 문서에만 둔다.
6. 가입 시 동의 기록과 14세 미만 확인 수단이 없다(문구만).
7. 방침의 '외부 위탁 없음'은 배포 형태(클라우드 호스팅·메일 등) 확정 후 재확인한다. JWT 클레임에 원래 이메일이 남지만 본인 브라우저에만 있고 로그아웃 때 지워진다. 인증 요청 거절 처리자 칸에 '탈퇴한 회원'이 표시된다.
8. 탈퇴 속도 제한은 서비스 내부 메모리다(재시작 시 초기화, 단일 인스턴스).

## 공연 포스터 표시 (브랜치 `feature/poster`, `feature/withdraw` 위, 미병합)

- 백엔드: `GET /api/performances/preview` 응답에 `sessionCandidates: [{date:"yyyy-MM-dd", time:null}]` 추가(항상 배열). 시작·종료가 모두 있고 2일 이하일 때만 날짜를 담는다(`PerformancePreviewResponse.candidatesFromPeriod`). 실패·NO_INFO 응답은 빈 배열이다. 포스터 스위치가 꺼져도 후보는 유지한다(`withoutPoster`). 새 외부 요청은 없다.
- 프런트: 등록 2단계(`pages/PerformanceRegisterPage.tsx`)가 status OK일 때 첫 후보 날짜를 회차 날짜 칸에 채우고, '날짜 바로 채우기' 버튼으로 바꾼다. '회차 추가'를 누르면 아직 회차가 없는 다음 후보 날짜를 채운다. `SessionDateTimePicker`에 `datePreset({date, nonce})` 속성을 추가해 날짜 칸만 채운다(nonce가 바뀔 때 한 번 적용, 값이 "" 인 부분 선택 상태에서도 동작). 후보가 있으면 안내 문구를 "회차 시각은 링크에서 읽을 수 없어 직접 골라 주세요. 날짜는 공연 기간에 맞춰 미리 채워 뒀어요."로 바꾼다. 새 링크로 바꾸면 후보와 미리 채움을 초기화한다. 회차는 자동 등록하지 않는다.

### 검증
- 백엔드 단위(`PerformancePreviewResponseTest`): 하루·이틀은 날짜만, 3일 이상·없음·역전은 빈 배열, `withoutPoster`가 후보 유지. 컨트롤러 슬라이스로 JSON 형태(`sessionCandidates`)를 확인했다. 백엔드 전체 테스트 수치는 이 기록에 남기지 않았다(최종 실행 결과는 별도 확인 대상).
