## 0. 읽는 법

**라벨**

| 라벨 | 뜻 | 구현 시 |
|---|---|---|
| [확정] | 사용자가 직접 요청·결정한 것 | 그대로 구현 |
| [기본안] | 구현하려고 제안한 세부 사항. 사용자 확인 전 | 구현 전에 사용자에게 확인하고, 확인되면 CLAUDE.md '확정된 핵심 결정'으로 옮긴다 |
| [후속] | 지금 구현하지 않는 것 | 사용자가 착수를 지시하기 전에는 만들지 않는다 |

- 이 문서에는 **현재 코드에 없는 것만** 적었다. 이미 구현된 것은 '현재 동작'에 사실로만 적는다.
- 질문이 필요한 항목은 **§7 확인 필요**에 모았다. §7의 `블로킹` 표시 항목은 답을 받기 전에 해당 작업을 시작하지 않는다.
- 작업 규칙은 CLAUDE.md를 따른다: 새 파일은 한 번에 5개 이내로 만들고 역할을 한 줄로 설명한 뒤 확인을 기다린다. 브랜치는 `타입/이름`, 커밋은 `타입: 한국어 요약`. docx/xlsx 원본은 직접 수정하지 않는다.
- 코드·SQL 이름(`EXCLUSIONS` 등)은 2026-10-09 master에서 확인한 것이다. 구현 전에 한 번 더 읽어서 달라졌으면 알려준다.

## 2. R1 — 받은 제안 가시화

사용자 원문 요약: 상대가 나에게 교환 제안을 보내면, ① 내 매칭 후보 카드에 뱃지를 붙이고 ② 내 매칭 '받은 제안' 탭에 N 뱃지를 붙이고 ③ 헤더에 알림 뱃지를 붙인다. 지금은 제안이 오면 그 상대가 내 후보에서 사라지는데, 사라지게 하지 말고 옆에 제안 뱃지나 새 채팅 뱃지를 달아 달라.

### 2.1 현재 동작 (코드 근거)

- 제안은 `POST /api/exchange/requests/{id}/proposals`이고, `exchange_match` 1건을 `CHATTING`으로 만든다. `a`=제안자, `b`=제안받은 쪽이다. 받은 쪽에 알림이나 표시 수단은 없다. (2026-10-11 알림 3종 구현 후에는 헤더 벨과 알림 페이지로 표시된다, §2.4)
- 후보 SQL(`repository/ExchangeCandidateRepository.java`)의 `EXCLUSIONS` 상수가 두 가지를 제외한다.
  1. 같은 요청 쌍의 열린 매칭 (`exchange_match.open_flag = 1`, 즉 CHATTING·RESERVED)
  2. 예약 잠금이 걸린 상대 티켓 (`exchange_ticket_lock`)
  그래서 제안을 주고받으면 서로의 후보에서 사라진다. 별칭은 `a`=내 요청, `b`=상대 요청, `ta`/`tb`=각 티켓이다.
- 같은 쌍의 열린 매칭은 DB 제약 `uk_exchange_match_open_pair`로 1건만 가능하다. 제안하기는 이미 열려 있으면 409 `MATCH_ALREADY_OPEN`이다.
- 내 매칭(`pages/MatchesPage.tsx`): 탭 `TABS`(전체·보낸 제안·받은 제안, `role`=ALL/SENT/RECEIVED), 개수·뱃지 없음.
- 헤더(`components/Header.tsx`): `MENU`(내 티켓·내 매칭)와 로그인 영역뿐이다.
- 백엔드에 `spring-boot-starter-websocket`은 있고 `SecurityConfig`에 `/ws/**` permitAll이 있지만, `WebSocketConfig`는 비어 있다. 프론트 `package.json`에 STOMP 계열 라이브러리는 없다. (2026-10-09 기준 기록이다. 이후 `WebSocketConfig`는 채팅(V11)에서 구현됐고, 프론트는 `@stomp/stompjs`를 쓴다.)

### 2.2 R1-1 후보 카드 뱃지

**[확정]** 후보에서 사라지게 하지 말고 카드 옆에 제안 뱃지·새 채팅 뱃지를 단다.

**[기본안]**

- **SQL**: `EXCLUSIONS`에서 1번(같은 쌍 열린 매칭 NOT EXISTS)을 제거하고, 같은 조건의 `LEFT JOIN exchange_match mo`로 열린 매칭을 같이 조회한다. 2번(예약 잠금 제외)은 그대로 둔다. 쌍당 열린 매칭이 1건이라 행이 중복되지 않는다. 내가 제안자인지는 `mo.request_a_id = a.id`로 판정한다.
- **COUNT**: `countSql()`도 같은 제외 조건으로 맞춘다. 목록 행 수와 COUNT가 같아야 하고 기존 테스트가 이를 검증한다. `ExchangeCandidateSqlGuardTest`가 SQL 구조를 지키고 있으므로, 이 테스트를 의도적으로 갱신해야 한다.
- **응답**: `dto/response/ExchangeCandidateResponse`에 `openMatch`를 추가한다 (열린 매칭이 없으면 null).
  ```
  openMatch: { matchId: number, status: "CHATTING" | "RESERVED", role: "SENT" | "RECEIVED" }
  ```
  ~~채팅 구현 후에 `unreadChat`을 추가한다(R1-4).~~ 채팅 뱃지는 **내 매칭 카드에만** 단다(`unreadChatCount`, V11, Q-8 확정). 후보 응답에는 `unreadChat`을 추가하지 않았다.
- **프론트** (`pages/CandidatesPage.tsx`의 `CandidateCard`, `types/exchange.ts`의 `ExchangeCandidate`):
  - `openMatch.role === "RECEIVED"` → 뱃지 "제안 받음"(강조색), `"SENT"` → "제안함".
  - ~~`openMatch.status === "RESERVED"`이면 뱃지 "예약 중"(R3). 이때 버튼은 같은 '내 매칭에서 보기'다.~~ **폐기(2026-10-11)**: 후보 카드에 '예약 중' 뱃지를 달지 않는다. 후보 목록은 예약으로 잠긴 티켓을 계속 제외하며(후보 SQL·422 `TICKET_LOCKED` 변경 없음), 예약 중 정보는 예약한 두 사람의 내 매칭 카드에서만 보인다. 예약 전부터 같은 자리로 채팅 중이던 다른 사용자의 내 매칭 카드에는 "(다른 사용자와 예약 중인 좌석)" 문구만 띄운다.
  - 이때 '제안하기' 버튼은 '내 매칭에서 보기'(`/exchange/matches`)로 바꾼다. 서버의 409 `MATCH_ALREADY_OPEN`은 그대로 유지한다.
  - 색만으로 구분하지 않고 텍스트를 포함한다. 카드 `aria-label`에 상태를 넣는다.
- **정렬**: 변경 없음 (내 희망 회차 priority → 상대 요청 최신순).
- **예약된 쌍** [폐기, 2026-10-11 — 아래는 폐기된 안이다. 예약 잠긴 티켓은 후보에서 계속 제외한다]: 같은 쌍이 RESERVED가 되어도 '예약 중' 뱃지로 후보에 남긴다 [확정, 9차 답변 A-1]. 이를 위해 예약 잠금 제외 조건(`exchange_ticket_lock`)에서 **이 쌍의 매칭이 건 잠금은 예외**로 둔다 (`l.match_id <> mo.id`). 다른 사람과의 예약으로 잠긴 티켓은 현행대로 제외한다(6차 확정). §7 Q-1 확정. 이 구현은 R1-1 작업에서 하며 `feature/exchange-reserve`에서는 후보 SQL을 바꾸지 않는다.

**수용 기준**

- 같은 쌍의 CHATTING 매칭이 있으면 양쪽 후보 목록에 모두 남고 `openMatch`가 채워진다 (SENT/RECEIVED 각각).
- CANCELED 매칭만 있으면 `openMatch`는 null이고 '제안하기'가 다시 가능하다.
- ~~같은 쌍이 RESERVED면 `openMatch.status`가 `RESERVED`로 남고, 다른 사람과의 예약으로 잠긴 후보는 제외된다.~~ **폐기(2026-10-11)**: 예약으로 잠긴 티켓은 같은 쌍이든 아니든 후보에서 제외된다.
- 후보 행이 중복되지 않는다. 목록 행 수 = COUNT.
- EXPLAIN에 `type=ALL`이 없고, 후보 대량 규모 테스트(작업일지의 4,000건 기준 응답 시간)가 이전 수준을 유지한다.
- 프론트: 뱃지·버튼 전환·접근성 이름 테스트, `npx tsc --noEmit`, `npx vite build` 통과.

### 2.3 R1-2 '받은 제안' 탭 N 뱃지

**[확정]** 나에게 교환 제안이 들어오면 내 매칭 '받은 제안' 탭에 N 뱃지를 단다.

**[기본안]**

- **N의 정의**: 내가 아직 확인하지 않은 받은 제안 수. 헤더 알림(R1-3)의 `PROPOSAL_RECEIVED` 읽지 않은 수와 같은 원천을 쓴다. 후보 카드 뱃지(R1-1)는 '열린 매칭이 있다'는 상태 표시이고 읽음과 무관하다.
- **표시**: `TABS`의 '받은 제안' 라벨 옆에 숫자 뱃지, 99 초과는 `99+`, 0이면 숨긴다. 접근성 이름에 개수를 넣는다(예: "받은 제안, 새 제안 3개").
- **읽음 처리**: 받은 제안 탭을 열어 목록이 표시되면 `PROPOSAL_RECEIVED` 알림을 일괄 읽음으로 처리한다. 카드별 'NEW' 표식은 만들지 않는다.
- R1-3의 알림 REST가 먼저 있어야 하므로 작업 순서는 R1-3 뒤다.

### 2.4 R1-3 헤더 알림

**[확정]** 헤더에 알림을 추가한다. 새 제안이 오면 실시간으로 뜬다.

  - **구현(2026-10-11)**: `propose`(수신자 = b측), `reserve`·`unreserve`(수신자 = 호출자의 반대편)에서 상태가 실제로 바뀐 경우에만 트랜잭션 맨 끝에서 `NotificationService.notify`(MANDATORY, 일반 INSERT)로 수신자당 1건을 쓴다. 멱등·오류 경로에서는 쓰지 않는다. 잠금 순서는 티켓 → 요청 → 매칭 → users(S, FK) → notification이며, notification 행을 잠근 뒤에는 다른 행을 잠그지 않는다.

### 2.5 R1-4 채팅 연동 — [확정] + 구현 완료 (2026-10-11, V11, `feature/chat`)

**결정**

- 채팅은 매칭(한 쌍)마다 1:1 텍스트 대화다. 한 요청에 채팅을 여러 개 열 수 있다(§3).
- 헤더 메시지 아이콘은 만들지 않는다. **2026-10-13 사용자 지시(Q-8 뒤집음, V15)**: 새 메시지는 `CHAT_MESSAGE` 알림으로 헤더 벨에 표시한다((수신자, 매칭)당 1행 재사용). 매칭 카드의 안 읽은 메시지 뱃지(`unreadChatCount`)는 그대로 둔다.
- 메시지는 텍스트만 보낸다(이미지·첨부 없음, 예매번호 등 민감정보는 가려서 보내도록 안내). 1000자 이하(코드 포인트 기준), 무기한 보관, 수정·삭제 없음.
- 시스템 메시지는 저장하지 않는다. 매칭 상태(예약 중·교환 완료·취소 등)는 채팅 화면 상단 배너로 보여준다.
- 종료(CANCELED·COMPLETED) 매칭은 이전 대화 열람과 읽음만 허용하고 전송은 막는다(409 `MATCH_STATE_CONFLICT`). CHATTING·RESERVED에서는 읽기·쓰기를 모두 허용한다.
- 읽음은 마지막으로 읽은 메시지 포인터로 기록한다. 내가 보낸 마지막 메시지 아래에 상대가 읽었으면 '읽음'으로 표시한다.
- 실시간 수신(STOMP 연결)은 채팅 구현(`feature/chat`) 때는 채팅 화면에 있는 동안만 연결했다. 알림 실시간 푸시(`feature/notifications-realtime`, 2026-10-11)부터는 로그인한 앱 전체가 탭당 연결 1개를 공유하고, 채팅 구독은 그 연결 위에서 한다. 새 메시지는 매칭의 `updated_at`을 바꾸지 않는다.
- 차단은 2026-10-12 `feature/block-report`(V13)에서 구현했다. 차단하면 두 사람 사이의 열린 매칭(CHATTING·RESERVED)은 시스템 취소되어 읽기 전용이 되고(새 메시지 전송은 409), 이후 두 사람은 서로 후보에 나오지 않는다. 차단당한 쪽에는 알리지 않는다. 이미 연결된 STOMP 세션은 강제로 끊지 않는다(CONNECT 거부와 매칭 취소로 막는다).

**구현 결과**

- REST 3종(`POST`·`GET /api/exchange/matches/{id}/messages`, `PUT .../messages/read`)과 STOMP `/ws`의 사용자 큐 `/user/queue/chat`(클라이언트 SEND는 전부 거부, 보내기는 REST). 상세는 `SeatSwap/backend/README.md`의 '채팅 (V11)' 절.
- DB: V11 `chat_message`(append-only), `chat_read_state`(읽음 포인터, 단조 증가).
- 화면: `/exchange/matches/:matchId/chat`, 내 매칭 카드의 '채팅' 링크와 안 읽은 메시지 뱃지(종료된 매칭도 열람 링크).
- 알려진 한계: 브라우저 수동 점검과 실서버 STOMP 연동 점검은 아직 하지 않았다. 속도 제한과 연결 제한은 서버 한 대 메모리 기준이다.

## 3. R2 — 매칭 → 예약 → 교환 완료, 교환 완료는 취소 불가

**[확정 — 2026-10-09 사용자 답변]**

1. 한쪽이 제안하면 **[매칭]** 이 된다 (채팅이 열린다).
2. 매칭 후 채팅에서 **한 명이 예약을 제안하고 상대가 수락하면 [예약]** 이 된다 (뱃지 생성, 2026-10-12 사용자 지시로 '한 명이 예약하면'에서 바꿈). **둘 중 한 명이 예약을 취소하면** 예약이 없던 상태로 돌아간다. → 지금 구현된 '양쪽 동의' 규칙과 달라지는 부분이라 **§3A(R3)** 에 따로 정리했다.
3. 실제 티켓/좌석을 교환한 뒤 **양쪽이 '교환 수락' 버튼을 누르면 [교환 완료]** 가 된다 (9차 답변: 버튼 이름만 '교환 완료' → '교환 수락', 상태·뱃지·이력 라벨은 '교환 완료' 유지; API `complete`·컬럼 `a_completed_at`/`b_completed_at`도 그대로). (이전 요청의 '교환됨'은 이 시점이다 — 해석 A 확정.)
4. 교환 완료된 것은 취소할 수 없다.
5. 교환 완료 때 티켓은 **안 2**로 처리한다: 기존 두 티켓을 '교환됨'으로 바꾸고, 각자 새 자리의 **새 티켓**을 만든다.
6. 교환 완료된 기존 티켓은 더 이상 내 자리가 아니므로 그 티켓의 교환 요청은 같은 트랜잭션에서 `CLOSED`로 닫는다. 그 티켓에 걸린 다른 `CHATTING` 매칭은 **자동 취소하지 않는다** (Q-15 확정, §3.4).

### 3.1 상태 용어와 화면 라벨

| 사용자 용어 | 내부 값 | 전환 조건 | 화면 라벨 |
|---|---|---|---|
| 매칭 | `ExchangeMatchStatus.CHATTING` | 후보에서 제안 (`proposals`) | 현재 "진행 중" → **"매칭"** [기본안] |
| 예약 | `RESERVED` | **한 명이 `reserve`(예약 제안) → 상대가 `reserve/accept`(수락)** → 두 티켓 `exchange_ticket_lock` (R3, Q-22, **구현 완료 2026-10-13, V15**; 2026-10-10 '한 명이 예약' 방식은 폐기, 이전 V5는 양쪽 `accept`) | 이전 "예약됨" → **"예약 중"** [확정, 9차 답변, 구현 완료] (이전 '예약' 라벨 제안은 정정) |
| 예약 제안 | `CHATTING` (부가 정보, 새 상태 아님) | 한 명이 `reserve` → 상대가 `reserve/accept`(RESERVED), 상대 `reserve/decline`·제안자 `reserve/withdraw`(제안 해제) | 채팅 화면 예약 블록 ('예약 제안하기' / '상대의 수락을 기다려요' / '상대가 예약을 제안했어요') |
| 예약 취소 | `RESERVED` → `CHATTING` | **둘 중 한 명이 `unreserve`** → 잠금 해제, 매칭·채팅 유지 (R3, 구현 완료; `cancel`은 `CANCELED`) | 버튼 "예약 취소" |
| 교환 완료 | `COMPLETED` | 예약 후 양쪽이 `complete` (**구현 완료 2026-10-11**, V9, `feature/exchange-complete`). **버튼 이름은 '교환 수락'** [확정, 9차 답변] | 상태·뱃지·이력 라벨은 "교환 완료" 유지 |
| (취소) | `CANCELED` | 완료 전 누구든 취소 | "취소됨" 유지 |
| 티켓 교환됨 | `TicketStatus.EXCHANGED` (신규) | 교환 완료 시 기존 티켓에 적용 | **"교환됨"** [기본안] |

이전 판의 "COMPLETED 라벨을 '교환됨'으로 통일" 제안은 철회한다. 매칭 라벨은 '교환 완료', 티켓 라벨이 '교환됨'이다. 버튼은 '교환 수락'이다(9차 답변, 사용자가 이해하기 쉽도록 이름만 변경).

### 3.2 현재 동작 (코드 근거)

- **2026-10-11 구현 완료**: `COMPLETED`는 `complete` API(`ExchangeMatchService.complete`)로 전이한다(§3.4). 아래 문장은 구현 전(2026-10-09) 기록이다: `COMPLETED`는 정의만 있었고 `exchange_match.a_completed_at`/`b_completed_at` 컬럼은 있었지만 **전이·API·화면이 없었다**.
- `TicketStatus`는 `ACTIVE`, `INACTIVE`, `EXCHANGED`(V9)다. `Ticket`의 좌석 컬럼(`zone_*`, `row_*`, `col_*`)은 JPA `updatable = false`이고, `uk_ticket_active_seat`는 (회차, 구역키, 열키, 번키, `active_flag`) 유니크다. `active_flag`는 `ACTIVE`일 때만 1이다.
- 후보 SQL은 `tb.active_flag = 1`인 티켓만 후보로 삼는다. 따라서 `EXCHANGED`가 되면 후보에서 자동 제외된다.
- 현재 '취소'에 해당하는 경로:

  | 경로 | 예약(RESERVED) 중 | 완료(COMPLETED) 후 |
  |---|---|---|
  | `POST /matches/{id}/cancel` | 허용 | 허용 상태 아님 (`ExchangeMatch.isAllowed`에서 막혀야 함 — 테스트로 고정) |
  | `DELETE /api/tickets/{id}` (내리기) | 409 `TICKET_RESERVED` | EXCHANGED면 409 `TICKET_EXCHANGED`(V9), 그 밖에는 제한 없음 |
  | 요청 수정·삭제 (`ExchangeRequestService`) | 409 `ACTIVE_MATCH_EXISTS` | 삭제 허용 (코드 주석에 명시) |

### 3.3 교환 완료 시 티켓 처리 — 안 2 확정 (2026-10-09)

기존 확정(3차 답변)은 "내 티켓의 좌석·회차를 새 자리로 **갱신**"이었고, 기존 설계 문서(`산출물/08_ERD/exchange-schema-design.md` (g))는 유니크 충돌을 **임시 INACTIVE 순서**(A를 임시 INACTIVE → B를 A 자리로 → A를 B 자리 + ACTIVE)로 풀도록 정해 두었다. 이번 확정은 이를 **대체**한다.

| 안 | 방식 | 결과 |
|---|---|---|
| 1 (기존 설계) | 기존 티켓 행의 좌석·회차를 UPDATE | 티켓 id 유지. `updatable=false` 해제 또는 네이티브 UPDATE, 임시 INACTIVE 순서 필요 |
| **2 (확정)** | 기존 두 티켓을 `EXCHANGED`로 바꾸고 각자 새 자리 티켓을 INSERT | 티켓 행이 불변이다. '교환됨'과 취소 불가를 상태값으로 표현한다. 교환 전 자리가 매칭·이력에 그대로 남는다. 티켓 id가 바뀐다 |
| 3 | 두 티켓의 `user_id` 교환 | 기각 (티켓에 붙은 요청·매칭이 다른 사람 것이 됨) |

안 2의 이점은 '불변성과 상태 표현'이다. 유니크 충돌 자체는 기존 설계의 임시 INACTIVE 순서로도 풀 수 있었다. 2026-10-11에 안 2로 구현했다(V9).

### 3.4 구현 스케치 (구현 완료 2026-10-11)

**교환 완료 API**

- `POST /api/exchange/matches/{id}/complete` (화면 버튼 이름은 '교환 수락'): `RESERVED`에서 호출자 쪽 완료(수락)를 기록한다 (`a_completed_at`/`b_completed_at`, 이미 눌렀으면 멱등 200). 양쪽이 모두 눌렀을 때만 아래 트랜잭션을 실행한다. 한쪽만 눌렀으면 `RESERVED`를 유지한다.

**교환 완료 트랜잭션** (두 번째 사람이 누르는 순간, 한 트랜잭션)

1. 잠금 순서 규칙대로 두 티켓(id 오름차순) → 두 요청 → 매칭을 `FOR UPDATE`한다 (`ExchangeMatchService`의 `lockTickets`·`lockRequests`와 같은 방식).
2. 재검증: 매칭 `RESERVED`, 양쪽 완료 기록, 두 티켓 `ACTIVE`.
3. **기존 두 티켓을 먼저 `ACTIVE → EXCHANGED`로 UPDATE한다.** `active_flag`가 NULL이 되어 `uk_ticket_active_seat`에서 빠지고 좌석 슬롯이 비워진다.
4. 각 사용자에게 **새 `ACTIVE` 티켓을 INSERT**한다: 소유자 = 원래 소유자, 회차·구역·열·번(label/key) = **상대의 기존 티켓 값**. 3번이 먼저여야 유니크 충돌이 없다. 사용자당 활성 20개 상한은 이 경로에서 검사하지 않는다 (활성 수가 늘지 않는다).
5. 두 기존 요청을 `CLOSED`로 바꾼다. 기존 티켓은 `EXCHANGED`가 되어 더 이상 내 자리가 아니기 때문이다. 그 티켓에 걸린 **다른 `CHATTING` 매칭은 자동 취소하지 않는다** (시스템 취소 없음). 해당 매칭 카드는 아래 '화면'대로 처리한다. [확정, §7 Q-15]
6. 교환 이력 스냅샷 2행(사용자별 `(기존 자리) -> (바꾼 자리)`)과 기존 티켓 id ↔ 새 티켓 id 연결을 남긴다.
7. `exchange_ticket_lock` 2행을 삭제한다.

**스키마** (Flyway `V9`, 구현 완료. V8은 예약 방식 변경에 사용됨. 설계는 `db-schema-architect`)

- `TicketStatus.EXCHANGED` 추가(구현 완료). `ticket.status`의 `ck_ticket_status`를 V9에서 EXCHANGED를 포함하도록 확장했다.
- `exchange_history`(확정된 요구: 마이페이지 교환 이력, 자리 스냅샷). 기존 설계 문서의 `ticket_id`('갱신된 내 티켓')는 `old_ticket_id`/`new_ticket_id`로 바꾼다.

**취소 불가 규칙**

- `COMPLETED` 매칭에 `reserve`/`unreserve`/`reject`/`cancel`/`complete`를 다시 호출하면 409 `MATCH_STATE_CONFLICT`.
- `EXCHANGED` 티켓은 내리기·되살리기·교환 요청 생성이 모두 불가하다 (409 새 코드 `TICKET_EXCHANGED`, 요청 생성은 기존 `TICKET_NOT_ACTIVE`와 정리).
- 요청 수정·삭제 경로의 시스템 취소는 `COMPLETED` 매칭을 건드리지 않는다 (`CHATTING`만 취소). 교환 완료 트랜잭션이 요청을 `CLOSED`로 닫는 것은 이 경로와 달리 다른 매칭을 취소하지 않는다.

**화면**

- 라벨은 §3.1대로 바꾼다. 예약된 매칭 카드에 '교환 수락' 버튼을 추가한다 (9차 답변: 이름만 변경). 2026-10-11 `feature/exchange-complete`에서 '교환 수락'을 2단계 확인 뒤 동작하게 했고 교환 완료 트랜잭션·교환 이력을 구현했다. 이력 조회 화면은 다음 브랜치다.
- 완료된 매칭 카드는 `(내 기존 자리) -> (받은 자리)`로 보여 준다. 매칭 행의 `ticket_a_id`/`ticket_b_id`가 교환 전 티켓을 계속 가리키므로 응답의 좌석은 **교환 전 자리**가 된다. (CLAUDE.md의 "COMPLETED 이후의 좌석은 교체 후 자리"는 더 이상 맞지 않다 — 부록 A.)
- **이미 교환된 좌석 처리** [확정, Q-15]: 교환 완료된 기존 티켓(`EXCHANGED`)에 걸린 다른 `CHATTING` 매칭 카드는 예약·교환 수락·교환 완료 버튼을 비활성화하고, 카드 아래에 "이미 교환된 좌석이에요" 메시지를 **본인과 상대방 모두에게** 보여준다. '교환됨' 여부는 티켓 상태 `EXCHANGED`로 판단한다. 채팅 종료는 사용자가 직접 한다.
- 내 티켓(`MyTicketsPage`)에는 `ACTIVE`만 둔다. 교환됨 티켓은 교환 이력(마이페이지)에서 본다. 교환으로 받은 새 티켓은 일반 활성 티켓으로 보인다.
- 교환 이력 조회 API(`GET /api/exchange/history`)와 마이페이지 '교환 이력' 화면(`/exchange/history`)은 2026-10-12 `feature/exchange-history`에서 구현했다(DB 변경 없음; 본인 이력만, 최신순, 스냅샷 표시, 읽기 전용). `exchange_history`는 교환 완료 때 채워진다(V9).

### 3.5 수용 기준 (구현 완료 2026-10-11)

- 한쪽만 완료하면 `RESERVED` 유지, 양쪽이 완료하면 `COMPLETED`와 티켓 처리·이력이 같은 트랜잭션에서 일어난다. 동시 완료 경쟁에서도 처리는 1회다 (MySQL 실DB 테스트).
- 처리 도중 `uk_ticket_active_seat` 위반이 없고, 끝난 뒤에도 같은 활성 좌석이 중복되지 않는다. 사용자당 활성 티켓 수가 늘지 않는다.
- 교환된 두 사용자 각각 새 자리의 `ACTIVE` 티켓 1개를 갖고, 기존 티켓은 `EXCHANGED`이며 후보에서 제외된다.
- 기존 요청 `CLOSED`와 잠금 삭제가 한 트랜잭션에서 일어난다. 그 티켓에 걸린 다른 `CHATTING` 매칭은 취소되지 않고 `CHATTING`으로 남으며, 카드에서 예약·교환 수락·교환 완료가 비활성이고 "이미 교환된 좌석이에요"가 양쪽에게 보인다 (판단 기준: 티켓 `EXCHANGED`).
- `COMPLETED` 이후 모든 취소·재동의 시도가 409이고 `EXCHANGED` 티켓은 내릴 수 없다.
- 이력에 `(기존 자리) -> (바꾼 자리)`가 스냅샷으로 남고, 이후 티켓이 바뀌어도 이력 값은 변하지 않는다.

## 3A. R3 — 예약·예약 취소 (당근마켓 방식)

> **2026-10-13 개정 (Q-22, 사용자 지시 2026-10-12)**: 아래 '한 명이 예약하면 즉시 RESERVED'를 전제로 한 서술(§3A 첫 목록의 예약 규칙, §3A.1의 `reserve` 행, §3A.2의 RESERVE 열, §3A.3의 '예약(`reserve`)' 규칙, §3A.4 API 표의 `reserve`, §3A.6의 '예약하기' 버튼)은 **§3A.8로 대체됐다**. 예약 취소(`unreserve`)·잠금 규칙·CHECK·교환 수락 표시 초기화·'예약 중 채팅 종료·거절 차단' 규칙은 그대로 유효하다.

**[확정 — 2026-10-09 사용자 답변]**

- 둘 중 **한 명이 예약하면 [예약 중]** 뱃지가 생긴다 (9차 답변으로 라벨 '예약 중' 확정; V15에서 예약 제안→수락으로 대체되어 지금은 상대가 수락해야 생긴다). 둘 중 **한 명이 예약을 취소하면** 예약이 없던 상태로 돌아간다.
- 예약 전까지는 **한 좌석 당 여러 명과 채팅**할 수 있다. 예약은 **한 좌석 당 한 사람과만** 가능하다.
- 예약을 취소하면 **예약하지 않았던 다른 상대와 예약**할 수 있고, **예약을 취소했던 상대와도 재예약**할 수 있다. (V15에서 예약 제안→수락으로 대체)

사용자가 설명한 두 흐름:

1. **교환 완료 경로**: 티켓 등록 → 원하는 자리 등록 → 매칭 제안받음 → 후보 중 마음에 드는 자리를 골라 채팅 → 예약 → (예약이 취소되지 않고 실제 교환 성사) → 양쪽이 '교환 수락'을 누름 → 매칭 종료 [교환 완료]
2. **예약 취소 경로**: 같은 과정에서 예약 후 둘 중 한 명이 예약을 취소 → 예약이 없던 상태로 복귀 → 다른 상대 또는 같은 상대와 다시 예약 가능

### 3A.2 허용 상태 전이 (`ExchangeMatch.isAllowed` 개정안)

```
            PROPOSE  RESERVE    UNRESERVE  REJECT(b측)  CANCEL(채팅 종료)    COMPLETE
CHATTING    불허     허용       멱등 200   허용         허용                 불허(예약 전)
RESERVED    불허     멱등 200   허용         불허[확정]   불허[확정]           허용
COMPLETED   허용     불허       불허       불허         불허                 불허
CANCELED    허용     불허       불허       불허         불허                 불허
```

- `RESERVED`에서 `REJECT`·`CANCEL`을 막는 것은 [확정, 9차 답변 Q-17, 구현 완료]이다: 채팅을 끝내려면 먼저 예약을 취소한 뒤 종료한다(409 `MATCH_STATE_CONFLICT`). 이전(V5)은 `RESERVED`에서도 `REJECT`·`CANCEL`이 허용됐다.
- `ACCEPT` 액션은 `RESERVE`로 바꾸고 `UNRESERVE`를 추가했다 (`ExchangeMatchAction`, 구현 완료).

### 3A.3 규칙

- **예약(`reserve`)**: 두 티켓 모두 다른 매칭의 예약으로 잠겨 있지 않아야 한다 (현행 `lockRepository.existsAnyByTicketIds` → 409 `TICKET_ALREADY_RESERVED` 유지). 통과하면 **한 트랜잭션**에서 `CHATTING → RESERVED`, 예약자·예약 시각 기록, `exchange_ticket_lock` 2행 INSERT(티켓 id 오름차순). 이미 `RESERVED`면 누가 눌렀든 멱등 200.
- **예약 취소(`unreserve`)**: 한 트랜잭션에서 `RESERVED → CHATTING`, 잠금 2행 삭제, 예약자·예약 시각 비움, **양쪽 교환 수락(완료) 표시(`a_completed_at`/`b_completed_at`) 초기화** (9차 답변 A-18 확정: 한쪽이 '교환 수락'을 눌렀어도 양쪽 완료 전이면 예약 취소 허용). 매칭이 계속 열린 상태(`open_flag` 유지)라 `uk_exchange_match_open_pair`와 충돌하지 않는다. 양쪽이 모두 '교환 수락'을 누르기 전까지만 가능하다 (2차 확정 "양쪽 완료 전에는 누구든 취소할 수 있다"와 같음).
- **예약 취소 뒤**: 두 티켓이 다시 후보·예약 대상이 된다. 다른 `CHATTING` 매칭에서 예약할 수 있고, 같은 쌍도 다시 예약할 수 있다. 횟수·쿨다운 제한은 두지 않는다 (사용자 확정).
- **예약된 티켓**: 새 제안·새 예약은 막힌다 (현행 `TICKET_LOCKED` 422, `TICKET_ALREADY_RESERVED` 409 유지). 이미 열려 있던 다른 채팅은 유지한다 [확정, 9차 답변 Q-16].
- **상대의 동의 없이 상대 티켓도 잠긴다.** 그래서 ① 예약·예약 취소 때 상대에게 알림을 보내고(R1-3, `MATCH_RESERVED`/`RESERVATION_CANCELED`; reserve 브랜치에서는 알림을 만들지 않았고, 2026-10-11 `feature/notifications`에서 구현 완료) ② 상대는 언제든 예약을 취소할 수 있고 ③ 예약-취소를 반복하는 남용은 차단·신고(후속)로 다룬다(9차 답변 A-20: 남용 방지 장치를 두지 않는다). 이 위험은 사용자가 알고 선택한 것이다 — 구현이 임의로 제한을 추가하지 않는다.
- 회차 마감 검사는 예약·예약 취소에도 하지 않는다 (6차 확정, 공연 시작 후에도 예약·취소 가능).

### 3A.5 DB (Flyway `V8` 구현 완료 `V8__exchange_match_single_reserve.sql`)

- `exchange_match`에 `reserved_by_id`(FK users, NULL), `reserved_at`(NULL) 추가. `a_reserved_at`/`b_reserved_at`는 삭제하지 않고 미사용(레거시)으로 유지한다 (9차 답변 A-19, DEPRECATED 컬럼 주석). 기존 RESERVED 행은 이른 쪽을 예약자로 백필한다.
- CHECK: `status = 'RESERVED'`이면 `reserved_by_id`·`reserved_at`이 NOT NULL, 아니면 둘 다 NULL.

### 3A.6 화면

- 매칭 카드 상태 뱃지: "매칭"(`CHATTING`) / **"예약 중"**(`RESERVED`) / "교환 완료" / "취소됨". 예약한 사람을 표시한다 ("OOO님이 예약했어요").
- 버튼(V15에서 예약 제안→수락으로 대체, "예약하기"는 채팅 화면으로 옮김): `CHATTING` → "예약하기" (받은 쪽은 "거절", 공통 "채팅 종료"). `RESERVED` → "예약 취소", **"교환 수락"** (예약하면 '교환 수락' 버튼이 생긴다). `RESERVED`에서는 "거절"·"채팅 종료"를 막고 먼저 예약을 취소하게 한다. '교환 수락'은 2단계 확인 뒤 동작한다(2026-10-11 구현).
- 예약 취소 확인 문구는 기존 것을 재사용한다 ("취소하면 예약이 풀리고 두 티켓을 다시 쓸 수 있어요").
- 후보 카드: ~~같은 쌍이 `RESERVED`면 "예약 중" 뱃지~~ **폐기(2026-10-11, §2.2·Q-1)**. 예약으로 잠긴 티켓은 후보에서 계속 제외한다.

### 3A.7 수용 기준

- 한 명이 `reserve`하면 `RESERVED`와 두 티켓 잠금이 한 트랜잭션에서 일어나고, 상대에게 알림이 간다. 두 명이 동시에 `reserve`해도 처리는 1회이고 나머지는 멱등 200이다 (MySQL 실DB 테스트).
- 같은 티켓을 다른 매칭에서 `reserve`하면 409 `TICKET_ALREADY_RESERVED`이고 상태가 바뀌지 않는다.
- `unreserve`하면 `CHATTING` 복귀, 잠금 삭제, 교환 수락(완료) 표시 초기화. 그 뒤 같은 쌍 재예약과 다른 매칭 예약이 모두 된다.
- 사용자가 설명한 두 흐름(교환 완료 경로, 예약 취소 경로)을 통합 테스트로 재현한다.
- `RESERVED`에서 `cancel`/`reject`는 409, `COMPLETED` 이후 모든 동작은 409.
- 한쪽만 '교환 수락'을 누른 상태에서 `unreserve`가 가능하고 완료 표시가 초기화된다.
- 기존 테스트 중 `accept` 기반 시나리오(서비스·도메인·슬라이스·MySQL 테스트)를 새 동작으로 고쳐 모두 통과한다.

## 3A.8 예약 제안 → 상대 수락 (구현 2026-10-13, V15 `feature/reserve-propose`, Q-22)

- **결정(사용자 지시 2026-10-12)**: 예약도 교환 수락과 같은 쌍방 합의다. 한쪽이 예약을 **제안**하면 상대가 **수락**해야 RESERVED가 된다. 예약 버튼은 **채팅 화면에서만** 보이고, 내 매칭 카드에는 예약하기 버튼이 없다. 한 명이 즉시 RESERVED로 만드는 방식(2026-10-10 구현)은 폐기한다.
- **상태**: 새 상태값은 없다. CHATTING 매칭의 부가 정보 `reserve_proposed_by_id`·`reserve_proposed_at`(V15, 둘 다 NULL이거나 둘 다 NOT NULL, CHATTING이 아니면 둘 다 NULL)이다. 응답 `reservationProposal` = `NONE`·`MINE`(내가 제안)·`THEIRS`(상대가 제안), RESERVED·종료 매칭은 항상 `NONE`.
- **API** (모두 `/api/exchange/matches/{id}/…`, 참여자만, 비참여자는 404):

| 메서드·경로 | 누가 | 동작 | 오류·멱등 |
|---|---|---|---|
| `POST /reserve` | 참여자 | 예약 제안 (CHATTING, 제안 기록, 매칭 행만 잠금) | 내가 이미 제안: 멱등 200. 상대가 제안: 409 `RESERVATION_PROPOSAL_PENDING`. RESERVED: 409 `MATCH_STATE_CONFLICT`. 다른 매칭에서 잠긴 티켓: 409 `TICKET_ALREADY_RESERVED`. EXCHANGED: 409 `TICKET_EXCHANGED` |
| `POST /reserve/accept` | 제안받은 쪽 | 수락 → RESERVED (기존 예약 잠금 로직, `reserved_by_id`=제안자, `reserved_at`=수락 시각, 제안 컬럼 비움) | 제안 없음: 409 `RESERVATION_PROPOSAL_NOT_FOUND`. 제안자 본인: 409 `RESERVATION_PROPOSAL_OWN`. RESERVED에서 수락한 쪽이 다시 누르면 멱등 200. 잠금 충돌: 409 `TICKET_ALREADY_RESERVED` |
| `POST /reserve/decline` | 제안받은 쪽 | 거절 → 제안 삭제, CHATTING 유지, 제안자에게 `RESERVATION_REJECTED` | 제안 없음: 멱등 200. 제안자 본인: 409 `RESERVATION_PROPOSAL_OWN`. 닫힌 매칭: 409 `MATCH_STATE_CONFLICT` |
| `POST /reserve/withdraw` | 제안자 | 철회 → 제안 삭제, CHATTING 유지, 알림 없음 | 제안 없음(RESERVED 포함): 멱등 200. 상대가 낸 제안: 409 `RESERVATION_PROPOSAL_NOT_OWN`. 닫힌 매칭: 409 `MATCH_STATE_CONFLICT` |
| `POST /unreserve` | 참여자 누구나 | RESERVED → CHATTING (잠금 해제, 교환 수락 표시 초기화) | §3A.3 그대로 |

- **제안 컬럼 정리**: CHATTING을 벗어나는 모든 UPDATE(취소·거절·종료·요청 수정/삭제·티켓 내리기·차단·정지·시스템 취소·수락으로 RESERVED 전이)는 같은 문장에서 제안 컬럼을 NULL로 비운다(안 비우면 CHECK 위반). 제안·철회·거절은 `updated_at`을 갱신한다(내 매칭 목록 정렬이 바뀌는 것은 의도).
- **잠금**: 제안·철회·거절은 매칭 행만 `FOR UPDATE`한다(티켓을 잠그지 않는다). 수락은 §3A.3 예약과 같은 순서(티켓 id↑ → 요청 id↑ → 매칭)와 격리로 기존 예약 코드를 재사용한다. 알림 쓰기는 트랜잭션 맨 끝이다. 예약 제안·수락은 회차 마감 검사를 하지 않는다(이미 시작한 채팅 규칙과 같음).
- **알림**: 제안 → 제안받은 쪽 `RESERVATION_PROPOSED`(재사용 1행), 거절 → 제안자 `RESERVATION_REJECTED`, 수락 → 제안자 `MATCH_RESERVED`(문구 "상대가 예약을 수락했어요. 내 티켓도 예약 중으로 잠겼어요."), 철회 → 알림 없음, 예약 취소 → 상대 `RESERVATION_CANCELED`.
- **화면**: 채팅 화면 상단 예약 블록(NONE '예약 제안하기'(확인 한 번) / MINE '상대의 수락을 기다려요' + '제안 철회' / THEIRS '상대가 예약을 제안했어요' + '예약 수락'(확인) · '거절' / RESERVED '예약 중' + '예약 취소'(확인), 종료 매칭은 숨김). 다른 매칭에서 잠긴 좌석이면 수락 버튼을 비활성화하고 안내한다. 상대의 제안·수락·거절·취소는 알림 신호(`/user/queue/notifications`)와 폴링으로 새로고침 없이 반영한다. 내 매칭 카드(CHATTING)는 제안 여부 문구("내가 예약을 제안했어요" / "상대가 예약을 제안했어요 — 채팅에서 수락하세요")와 '채팅' 버튼만 두고 '예약하기' 버튼은 두지 않는다. RESERVED 카드의 '예약 취소'·'교환 수락'과 거절·채팅 종료 제한 안내는 그대로다.
- **검증**: 기본 `./gradlew test`와 MySQL IT(임시 컨테이너) 전체 통과. 동시성 IT `ReserveProposalMysqlTest`: 동시 제안(하나만 성공), 제안 vs 철회, 수락 vs 거절·철회, 같은 티켓 두 매칭의 수락 경합(한쪽만 성공), 수락 vs 취소·차단·정지·티켓 내리기·요청 삭제, 예약 취소 vs 재제안, 채팅 전송·읽음·삭제 혼합 — 교착 0, 잠금 행 수 = 2 × RESERVED 매칭 수, 제안은 CHATTING에만 존재. 프런트 tsc·build 통과, Playwright 확인(채팅 알림 실시간, 제안→거절→재제안→수락→예약 취소, 벨 위치 데스크톱·768·480px).
- **알려진 한계(구현과 대조해 확인, 2026-10-13)**:
  - 알림 목록·말풍선 정렬은 `ORDER BY created_at DESC, id DESC`다(되살린 알림이 최신 맨 위). 정렬용 인덱스는 만들지 않았다(알림이 (수신자, 매칭)당 1행 수준).
  - 채팅 읽음 연동(`markChatRead`)은 포인터가 올라가면 그 (수신자, 매칭)의 `CHAT_MESSAGE` 알림을 읽음 처리하되, 한 문장 `NOT EXISTS` 가드로 포인터 뒤에 상대 메시지가 남아 있으면 처리하지 않는다(READ_COMMITTED).
  - 수락(`reserve/accept`)은 RESERVED에서 다시 누르면 제안자·수락자 모두 멱등 200이다(CHATTING에서 제안자가 누르면 409 `RESERVATION_PROPOSAL_OWN`).
  - 예약-취소 남용 방지 없음(차단·신고로 다룸), 정렬용 `(user_id, created_at)` 인덱스 없음(알림이 매칭당 1행 수준이라 불필요로 판단), 읽음 가드와 되살리기가 겹치는 극히 약한 창, 일부 경로는 REPEATABLE READ 패턴 유지.

## 3B. 관리자 페이지 — 공연 수정 제안·내 티켓 인증 (구현 완료 2026-10-12, V12, `feature/admin`)

- **공연 수정 제안**: 공연 상세의 '정보가 틀렸어요'에서 제목·공연장 중 하나 이상과 사유를 낸다. 관리자는 현재 값과 제안 값을 비교해 승인(공연에 반영, 이전 값 스냅샷) 또는 거절(사유)한다. 사용자당 PENDING 3건까지. 알림은 만들지 않고, 제안자는 `/my/edit-proposals`에서 결과를 본다.

  - 요청자는 승인 뒤 일반 티켓 등록으로 직접 등록한다(자동 등록 없음).
- **사진 보관**: 승인·거절 뒤 커밋 후에 파일을 지우고 처리 시각을 남긴다. 처리된 요청의 사진은 보여주지 않는다(410). 파일은 웹에서 직접 서빙하지 않는다.
- **권한**: 관리자는 기존대로 DB에서 `users.role = 'ADMIN'`을 직접 부여한다. 프론트 가드(`AdminRoute`)와 서버 `/api/admin/**` 검사를 둘 다 둔다.
- **알려진 한계**: 커밋 뒤 사진 삭제 실패 시 고아 파일이 남는다(정리 스케줄러 없음). 저장소가 서버 로컬 디스크라 다중 인스턴스에서는 쓸 수 없다. 자기 제안 승인은 막지 않는다.

## 3C. 소셜 로그인 — 구현 완료 (2026-10-12, V14 `social_account`, `feature/social-login`)

- **범위**: 카카오·구글·네이버 3종. 로그인·가입 화면 하단에 활성 제공자 버튼만 보인다. 가입 후에는 일반 사용자와 같은 JWT로 로그인한다. 기존 계정에 소셜을 붙이는 연결은 자동이 아니며, 2026-10-13 마이페이지에서 본인이 명시적으로 한다(§3D).
- **사용자 결정(2026-10-12)**: 같은 이메일의 기존 계정은 **자동 연결하지 않는다.** 제공자가 준 검증된 이메일이 `users`에 있으면 가입을 막고 `EMAIL_EXISTS`("이미 같은 이메일로 가입한 계정이 있어요. 이메일과 비밀번호로 로그인해 주세요.")로 안내한다.
- **가입·로그인 규칙**: 같은 소셜 계정이면 그 사용자로 로그인한다(이메일이 바뀌었는지는 보지 않음). 없으면 가입한다. 이메일이 없거나 미검증이면 `{provider}.{providerUserId}@social.seatswap.invalid` 자리표시 이메일과 무작위 비밀번호 해시를 쓰므로 비밀번호 로그인은 불가능하다. 정지·차단·신고 규칙은 일반 사용자와 같다.
- **보안**: 토큰을 URL에 싣지 않는다. 콜백은 60초·1회용 로그인 코드를 `/auth/callback#code=`로 넘기고, 프런트가 `POST /api/auth/social/exchange`로 JWT를 받는다. state는 HMAC 서명 HttpOnly 쿠키(`ss_oauth`)로 검증하며 1회용이다. 제공자 엔드포인트는 설정으로 고정하고 리다이렉트 목적지는 `frontend-base-url`만 쓴다. 콜백은 예외 상황에서도 항상 302다.
- **검증 한계**: 실제 카카오·구글·네이버 키로는 아직 검증하지 못했다(스텁 제공자 테스트와 브라우저 스텁 점검만). 연동 때 카카오 PKCE·is_email_verified, 네이버 client_secret 필수 여부를 확인한다.
- (예약 방식 변경은 2026-10-13 구현 완료, §3A.8·§6 항목 11.)

## 3D. 프로필 수정 — 닉네임·소셜 계정 연결·해제 — 구현 완료 (2026-10-13, V16, `feature/profile-edit`)

- **범위**: 닉네임 수정, 소셜 계정 연결·해제. 이메일·비밀번호 변경은 요청이 없어 범위 밖이다.
- **닉네임**: `PATCH /api/users/me`. 가입과 같은 규칙(trim 뒤 2~20자, 보이지 않는 문자 불가), 중복 허용, 같은 값이면 멱등 200. 저장하면 헤더 이름도 바로 바뀐다.
- **자리표시 이메일**: 소셜 가입자는 이메일이 없다(`emailPlaceholder=true`, 응답 `email`은 null). 마이페이지에는 "소셜 계정으로 가입해 이메일이 없어요"를 보인다.
- **비밀번호 로그인 가능 여부**: `users.password_login_enabled`(일반 가입 1, 소셜 가입 0). 마지막 로그인 수단 판단에 쓴다. 소셜 가입자가 비밀번호를 설정하는 기능은 없다.
- **연결 규칙**: 같은 이메일로 자동 연결하지 않는다(§3C 결정 유지). 마이페이지에서 로그인한 본인이 제공자를 골라 연결을 시작하면, 제공자 인증 뒤 **로그인 세션이 연결을 확정**해야 저장된다. 콜백은 저장하지 않고 일회용 연결 확정 코드(60초)만 넘긴다. 확정 API는 코드를 발급받은 사용자와 로그인한 사용자가 같을 때만 저장한다. 이메일 일치는 보지 않는다.
- **연결 한도**: 사용자당 제공자 1개(DB UNIQUE(user_id, provider)). 같은 제공자가 이미 연결돼 있으면 409 `SOCIAL_ALREADY_LINKED`, 그 계정이 다른 사용자에게 있으면 409 `SOCIAL_LINKED_OTHER`.
- **해제 규칙**: 마지막 로그인 수단이면 409 `LAST_LOGIN_METHOD`(비밀번호 로그인 불가이고 연결이 하나뿐). 연결이 없으면 멱등 204. 제공자가 지금 꺼져 있어도 해제는 된다. 화면은 `canUnlink`가 false이면 해제 버튼을 비활성하고 사유를 보인다.
- **화면**: '소셜 계정 연결' 카드는 활성 제공자를 `SOCIAL_PROVIDER_ORDER` 순서로 보여준다. 활성 제공자가 없으면 카드를 숨긴다. 해제는 확인 한 번을 거친다. 연결 실패는 `socialLinkError`를 한국어 문구로 안내한다.
- **보안**: 연결 시작 티켓은 (사용자, 제공자)에 묶인 1회용이고, 쿠키에 연결 사용자 id가 서명돼 들어간다. 연결·확정·해제 응답은 `Cache-Control: no-store`. 티켓·코드·이메일은 로그에 남기지 않는다. 연결 시작과 확정은 각각 사용자당 분당 10회로 제한한다.
- **검증**: 백엔드 전체 테스트와 임시 MySQL IT를 통과했다. Fable 검증 결과 높음 1건(강제 연결 로그인 CSRF, 2단계 확정으로 수정), 중간 3건(콜백 속도 제한 시 로그인 화면으로 가던 문제, 연결 모드 authorize의 비-302 JSON 응답, 정지 안내가 항상 무기한으로 보이던 문제), 낮음 1건(티켓의 제공자 미바인딩)을 반영했다. 실제 카카오·구글·네이버 키로는 미검증이고 스텁 제공자 기준이다. 프런트 빌드와 브라우저 점검 기록은 구현 기록에 없어 미확인이다.
- **알려진 한계**: 같은 이름 쿠키 하나라 탭 A의 연결 시작과 탭 B의 소셜 로그인이 겹치면 A의 콜백이 `INVALID_STATE`가 된다. 티켓·확정 코드·속도 제한은 메모리(단일 인스턴스)다. 티켓이 URL 쿼리에 실린다(1회용·60초). JWT 클레임에 자리표시 이메일 원문이 남는다(화면에는 나오지 않는다). 비밀번호·이메일 변경은 없다.

## 3E. 회원탈퇴·개인정보처리방침 — 구현 완료 (2026-10-13, V17, `feature/withdraw`)

- **결정(사용자, 2026-10-13)**: 진행 중 교환은 모두 자동 정리한다(예약 중이어도 시스템 취소·잠금 해제 후 탈퇴). 채팅·신고·제재 기록은 지우지 않고 익명화해 유지하며 방침에 명시한다. 운영자 정보는 자리표시 + 빌드 환경변수(`VITE_PRIVACY_OPERATOR`·`VITE_PRIVACY_CONTACT_EMAIL`·`VITE_PRIVACY_EFFECTIVE_DATE`).
- **API**: `DELETE /api/users/me {password?, confirmText?}`, 성공 204. 비밀번호 로그인 계정은 비밀번호, 소셜 전용 계정은 확인 문구 '탈퇴합니다'로 본인 확인한다. ADMIN은 409 `ADMIN_CANNOT_WITHDRAW`. 사용자당 분당 5회(초과 429).
- **처리(한 트랜잭션)**: PENDING 좌석 인증 요청 거절 → 열린 매칭(CHATTING·RESERVED) 시스템 취소와 예약 잠금 해제 → OPEN 요청 CLOSED·활성 티켓 INACTIVE(2차 정리 포함) → 소셜 연결 전부 삭제 → 계정 익명화(이메일 `withdrawn.{id}@withdrawn.seatswap.invalid`, 닉네임 '탈퇴한 회원', 무작위 비밀번호, 비밀번호 로그인 불가, `withdrawn_at` 기록) → 수신자 알림 삭제 → 커밋 뒤 실시간 연결 종료.
- **보존**: 채팅·읽음 상태·교환 이력·차단·신고·제재·PENDING 공연 수정 제안은 지우지 않는다. 닉네임은 '탈퇴한 회원'으로 보인다. 교환 이력 화면에는 상대 정보가 없다.
- **인증 차단**: 기존 액세스 토큰·실시간 연결·로그인·재발급·소셜 로그인·소셜 연결 확정과 해제가 모두 막힌다. 같은 이메일·같은 소셜 계정으로 새로 가입할 수 있다.
- **이용 정지 중 탈퇴**: API는 허용한다(결정 2026-10-13, Q-23 해결). 정지 중에는 로그인이 막혀 정지 전 토큰이 있을 때만 쓸 수 있고, 토큰이 없으면 방침 §8의 문의처로 요청한다.
- **화면**: 마이페이지 '회원탈퇴' 버튼 → 모달(진행 중 교환 자동 취소·티켓 내려감·익명화·되돌릴 수 없음 안내, 방침 링크, 본인 확인). 성공하면 홈에서 "탈퇴가 완료됐어요" 안내를 한 번 보인다. 푸터 '개인정보처리방침' 링크(채팅 화면 제외), 공개 `/privacy`, 가입 화면의 방침 링크와 "만 14세 미만은 가입할 수 없어요" 안내(동의 체크박스·기록 없음).
- **방침 보유 기간**: 계정 정보는 탈퇴 즉시 삭제·익명화, 인증 사진은 처리가 끝나면 삭제, 받은 알림은 탈퇴할 때 삭제, 채팅·교환 이력·차단·신고·제재는 익명화해 서비스 운영 기간 동안 보관하고 종료 때 파기(자동 파기 스케줄 없음).
- **잠금 순서**: 설계 초안의 'users 먼저 잠금'은 폐기했다. 제안이 티켓을 잠근 뒤 매칭을 INSERT하면서 users에 FK 공유 잠금을 걸기 때문에 교착한다. 탈퇴는 users를 티켓·요청·매칭 뒤에 잡는다.
- **검증**: 전체 테스트와 임시 MySQL IT 통과. `WithdrawMysqlTest`(탈퇴 vs 제안·예약·교환 수락·탈퇴끼리·소셜 연결·티켓 등록, 15라운드)에서 교착 없이 불변식 유지. Fable 검증 높음 없음, 중간 2건은 정책 사항이라 Q-23·Q-24로 남김, 낮음은 반영. 브라우저는 Playwright 수준만 확인(방침 공개 접근, 푸터, 모달, 탈퇴 후 기존 토큰 401, 같은 이메일 재가입).
- **알려진 한계**: 8개 전부는 `wiki/decisions/withdraw-privacy-design.md`에 있다. 핵심은 정지 중 탈퇴는 토큰 보유자만 가능, 소셜 전용 계정 재인증 없음(Q-24), 인증 사진 삭제 실패 시 고아 파일 가능, 보관 기간의 법적 근거 미확인(Q-25), 가입 동의 기록 없음이다.

## 3F. 공연 포스터 표시 — 구현 완료 (2026-10-13, DB 변경 없음, `feature/poster`)

- **결정**: 사용자 지시(2026-10-12)에 따라 포스터를 공연 정보 오른쪽에 띄운다. 저작권 판단은 메인이 조사해 정했다(법률 자문 아님). 근거와 대안은 위키 `wiki/decisions/poster-display-design.md`에 있다.
  - 정한 것: 서버는 포스터를 저장·복제·프록시하지 않는다. 이미지 주소 문자열만 읽고 브라우저가 원 사이트에서 직접 불러온다(인라인 링크). DB에 저장하지 않는다. 포스터 아래에는 출처를 텍스트로만 적고 새 링크는 두지 않는다. 로드 실패(핫링크 차단 포함) 시 영역을 숨기고 대체 링크는 두지 않는다(사용자 지시 2026-10-12).
- **API**: `GET /api/performances/preview` 응답에 `posterUrl`(문자열 또는 null)을 추가했다. 새 `GET /api/performances/{id}/poster` → `{posterUrl}`(로그인 필요, 공연이 없으면 404, 공연의 sourceUrl로 같은 읽기 경로를 쓴다). 실패·제한·스위치 꺼짐은 오류 없이 null이다.
- **허용 호스트(2026-10-13 실측)**: YES24 `tkfile.yes24.com`, 티켓링크 `image.toast.com`, 멜론 `cdnticket.melon.co.kr`. 사이트별로 고정하고 https만 인정한다(`//`는 https로 보정). userinfo·비표준 포트·공백·제어 문자·비ASCII 문자·2048자 초과를 거부하고, 경로에 `noimage`가 든 자리표시 이미지(YES24는 포스터가 없을 때 `_noimage.gif`를 준다)를 거부한다.
- **속도 제한·스위치**: 상세용 조회는 미리보기와 같은 캐시(10분)·사이트 분당 30회·동시 4개를 쓰고, 사용자 제한은 별도(`seatswap.poster.user-per-minute`, 분당 60)다. 제한에 걸리면 조용히 null이다. 설정 `seatswap.poster.enabled`(기본 true, 환경변수 `SEATSWAP_POSTER_ENABLED`)가 false면 포스터 요청과 주소를 전혀 내지 않는다.
- **화면**: 공연 상세는 공연 정보 카드 오른쪽(좁은 화면은 아래), 등록 2단계는 제목·공연장 입력 오른쪽에 둔다. `PosterImage`가 주소를 프런트에서도 다시 검증하고 `referrerpolicy="no-referrer"`, 3:4 고정 비율 박스(object-contain)로 불러온다. 출처 캡션: "포스터 이미지 출처: {YES24|티켓링크|멜론티켓} · 저작권은 원 권리자에게 있어요".
- **검증**: 백엔드 단위·슬라이스(파서의 호스트 허용·거부와 JSON-LD 폴백, 서비스 `poster()`와 스위치 꺼짐 시 이미지 요청 0회, 컨트롤러 JSON 형태). 브라우저(Playwright): 티켓링크·멜론 미리보기에서 실제 포스터 주소 확인, 멜론 공연 상세에서 실제 로드(naturalWidth 420, referrerPolicy no-referrer)와 캡션, 모바일 폭 레이아웃, 등록 2단계 표시, 이미지 요청을 차단하면 영역이 사라짐, YES24 자리표시 이미지는 숨김.
- **알려진 한계**: ①인라인 링크의 저작권 확정 판례가 없고, 포스터 저작물성과 티켓 3사 약관은 확인하지 못했다. 공개 운영 전 약관 확인과 전문가 검토가 필요하며(Q-26), 요청이 오면 스위치를 끈다. ②허용 호스트는 실측 기준이라 CDN이 바뀌면 포스터가 안 뜬다(화면은 숨김). ③YES24는 포스터가 없는 공연이 많다. ④인터파크는 robots.txt 때문에 지원하지 않는다. ⑤사이트가 핫링크를 막으면 포스터는 보이지 않는다. ⑥삭제·표시 중단 요청은 개인정보처리방침의 문의처로 받는데, 방침에는 아직 문구가 없다.
- 열린 질문: §7 Q-26.

## 3G. 회차 날짜 미리 채우기 — 구현 완료 (2026-10-13, DB 변경 없음, `feature/session-prefill`)

- **결정 (사용자 요청, 2026-10-13)**: 하루·이틀짜리 공연은 공연 기간의 날짜로 회차 날짜를 미리 채우고, 시각은 사용자가 직접 고른다(세 사이트 회차 시각은 Ajax라 읽지 못한다). 뮤지컬처럼 회차가 많은 공연은 나중에 AI가 상세정보를 읽어 채우는 방식을 붙일 예정이므로, 이번에는 구조만 열어 둔다.
- **정한 것**:
  - 백엔드: `GET /api/performances/preview` 응답에 `sessionCandidates: [{date:"yyyy-MM-dd", time:null}]`를 추가한다(항상 배열). 공연 기간의 시작·종료가 모두 있고 시작~종료가 **2일 이하**(시작·종료 포함, 상수 `MAX_PERIOD_DAYS_FOR_CANDIDATES`=2)일 때만 날짜를 담는다. 3일 이상·기간 없음·시작>종료면 빈 배열이다.
  - `time`은 지금 항상 null이다. 나중에 AI 등 상세정보 출처가 붙으면 같은 필드를 채운다(구현 없음).
  - 새 외부 요청은 없다. 기존 파싱 결과의 기간으로 계산하므로 SSRF 규칙·속도 제한·캐시는 그대로다. 포스터 스위치가 꺼져도 후보는 유지된다.
  - 프런트: 2단계는 첫 후보 날짜를 회차 날짜 칸에 미리 채우고, 후보 날짜별 '날짜 바로 채우기' 버튼으로 날짜 칸을 바꾼다. 회차를 추가하면 아직 회차가 없는 다음 후보 날짜를 채운다. 시각은 사용자가 고르고 회차는 자동 등록하지 않는다. 후보가 있으면 안내를 "회차 시각은 링크에서 읽을 수 없어 직접 골라 주세요. 날짜는 공연 기간에 맞춰 미리 채워 뒀어요."로 바꾸고, 새 링크로 바꾸면 후보와 미리 채움을 초기화한다.
- **검증**: 백엔드 단위(`PerformancePreviewResponseTest`: 하루·이틀은 날짜만, 3일 이상·없음·역전은 빈 배열, `withoutPoster`가 후보 유지), 컨트롤러 JSON 형태. 브라우저(Playwright): 실제 티켓링크 2일 공연에서 날짜 칸이 첫 날짜로 채워지고 칩 클릭으로 바뀜, 모의 미리보기로 회차 추가 뒤 다음 날짜가 채워지고 둘째 추가 뒤 비워짐.
- **알려진 한계**: ①시각은 직접 입력한다(세 사이트 회차 시각은 Ajax). ②3일 이상 공연(뮤지컬 등)은 날짜 후보도 없다. ③하루 여러 회차(낮·밤)인 2일 공연은 날짜당 후보 1개라 같은 날짜를 직접 추가해야 한다. ④공연 기간과 실제 회차 날짜가 다를 수 있다(휴연일 등). 미리 채운 날짜는 확인 후 고치라는 문구로 안내한다.
- AI 상세정보 출처의 설계는 착수 지시가 오면 정한다(이 문서에서는 열린 질문으로 올리지 않았다).

## 4. Q1 — 링크 등록 시 공연정보 자동 입력: 현황

**답: 구현 완료 (2026-10-12, `feature/link-autofill`).** 아래 '(2026-10-09 시점)' 표기 항목은 구현 전 현황으로 남겼다.

- **구현 사실 (2026-10-12)**: `GET /api/performances/preview?sourceUrl=`(로그인 필요)가 링크의 공개 HTML에서 제목·공연장·공연 기간(시작·끝 날짜)을 읽어 돌려주고, 공연 등록 2단계에 미리 채운다. 자동 등록은 하지 않고 직접 입력은 항상 가능하다. 저장하지 않으며 DB 변경은 없다(V12 아님). 규칙·SSRF 방어·속도 제한·캐시는 백엔드 README '링크 공연정보 미리보기' 절.
- **실측 결과 (2026-10-12, 실제 공개 페이지 raw HTML)**: ① YES24(`ticket.yes24.com/Perf/{id}`)와 ② 티켓링크(`ticketlink.co.kr/product/{id}`)는 JSON-LD `Event`의 name·location.name·startDate/endDate(날짜만)를 쓴다. ③ 멜론(`ticket.melon.com/performance/index.htm?prodId={id}`)은 JSON-LD·og:title이 없어 본문 `.box_consert_txt p.tit`(제목), `dt.tit_info`가 공연장인 dd(비어 있는 상품도 있음), `#periodInfo`(기간)를 읽는다. 세 사이트 파서를 실제 페이지에 돌려 제목·공연장·기간이 맞게 나옴을 확인했다. 인터파크는 robots.txt 때문에 제외(UNSUPPORTED_SITE). 로그인·캡차 우회·내부 API 호출은 하지 않는다.

- **회차 시각은 읽지 못한다 (실측 확정, 2026-10-12)**: 세 사이트 모두 회차 목록·시각이 공개 HTML에 없고 Ajax(예매 달력)로만 온다. 그래서 회차는 자동으로 채우지 않고, 기간이 있으면 회차 입력 근처에 기간만 안내한다(시작=끝이면 날짜 하나). 원래 요구의 '제목·공연장·회차' 중 **회차는 자동 입력 대상에서 빠진다**. 단, 공연 기간이 2일 이하이면 **날짜만** 미리 채운다(2026-10-13, §3G). 시각은 여전히 직접 입력한다. Ajax를 읽는 것은 CLAUDE.md의 '내부 API 조사는 하지 않는다' 규칙에 걸리므로 하지 않는다.

- (2026-10-09 시점) 근거: `PerformanceService`·`SourceKeyResolver`·`TicketingSite` 어디에도 외부 HTTP 호출 코드가 없다. `GET /api/performances/lookup`은 그 링크로 **이미 등록된 공연이 있는지(중복)** 만 확인한다. 링크의 현재 역할은 중복 방지 키(`source_key`)다.

## 5. P1 — 캡처·티켓 사진 AI 읽기: 후속 과제 제안

**제안**: 티켓팅 화면 캡처나 티켓 사진을 AI가 읽어 공연정보(공연명·공연장·일시, 선택으로 구역·열·번)를 채워주는 기능을 **후속 과제로 기록**한다. **[후속]** 착수를 지시하기 전에는 구현하지 않는다.

**후속 과제 목록에서의 위치**: 링크 자동 입력(Q1) 다음, 또는 Q1이 사이트별 제약으로 막힐 때의 대안. 링크 읽기는 사이트별 어댑터·robots/약관·마크업 변경에 취약하고 인터파크는 제외인 반면, 이미지 읽기는 사이트와 무관하다. 대신 비용과 개인정보 부담이 생긴다.

**착수 전에 정해야 할 조건**

| 항목 | 제약 |
|---|---|
| 이미지 보관 | **저장하지 않는다.** 메모리에서만 처리하고 폐기 (CLAUDE.md '이미지 보관' 방침과 같음). 로그에도 이미지·추출 원문을 남기지 않는다 |
| 개인정보 | 티켓 이미지에는 예매번호·QR·이름이 있을 수 있다. 외부 AI API로 보내기 전에 사용자에게 고지·동의를 받고, 호출은 **서버에서만** 한다 (API 키를 프론트에 노출하지 않는다) |
| 결과 처리 | 항상 '미리 채우기 + 사용자 확인'. 자동 등록 금지 (오독 가능) |
| 비용·남용 | 사용자당 일일 횟수·파일 크기·형식 제한, 레이트 리밋. 사용할 모델과 월 비용 상한을 사용자가 정한다 |
| 증빙 아님 | 이미지를 올렸다고 티켓 소유가 검증되는 것이 아니다. CLAUDE.md의 '내 티켓 인증'(사진 업로드 → 관리자 확인 예정)과는 목적·보관 정책이 달라 분리한다 |
